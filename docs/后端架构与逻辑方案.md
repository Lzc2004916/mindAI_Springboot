## 0. 先看全局：这个后端到底是干什么的

一句话：**它给一个「心理健康 AI 助手」小程序/网站提供后台服务**，核心就 5 件事。

| 编号 | 业务能力 | 用户看到的是什么 | 主要表 |
|---|---|---|---|
| ① | **账号与鉴权** | 注册、登录、看自己的资料、改密码、退出 | `user` |
| ② | **AI 心理对话** | 跟「宁渡 AI 助手」聊天，回复一个字一个字往外蹦 | `consultation_session` + `consultation_message` |
| ③ | **情绪花园（会话情绪分析）** | 聊完天后左边卡片显示「平静 10 分 · 正常」 | 复用上面两张表（缓存字段直接存在 session 上） |
| ④ | **情绪日记** | 每天写一篇日记、自评情绪，后台自动用 AI 分析出风险等级 | `emotion_diary` + `ai_analysis_task` |
| ⑤ | **知识库 / 文件 / 数据统计** | 看文章、上传图片、管理端看数据大屏 | `knowledge_article`、`knowledge_category`、`sys_file_info` |

还有两张**存在但没接进代码**的表：`user_favorite`（收藏，零 Java 引用）、以及 `knowledge_category.parent_id` 的自关联（分类树接口有，用户端改用了平铺接口）。

### 1.2 每个包一句话说清

| 包 | 文件数 | 职责（大白话） | 允许依赖谁 |
|---|---|---|---|
| `controller` | 6 | **门面**。只负责接 HTTP、做参数格式校验（`@Valid`）、把结果包成 `Result`。**不应该有业务判断** | service、common |
| `service` | 10 | **业务大脑**。所有「必须怎么做」的规则都在这里：谁有权删、密码怎么加密、分页怎么拼、VO 怎么组装 | mapper、entity、AiService |
| `AiService` | 5 | **AI 能力**。提示词、调用大模型、结构化出参、异步任务调度 | service（少量）、Spring AI |
| `mappper` | 8 | **数据访问**。MP 的 `BaseMapper` 给好了增删改查；统计类查询手写 SQL 放这里 | entity |
| `entity` | 8 | **数据库表的 Java 影子**，字段用 `@TableField` 对齐列名 | 无 |
| `response` / `common/Dto` | 7 + 11 | **出参与入参的形状**。分开是为了「数据库长什么样」不影响「接口长什么样」 | 无 |
| `common` | 3 | `Result`（统一响应外壳）、`ResultCode`（错误码字典） | 无 |
| `config` | 5 | Spring 装配：Security 规则、ChatClient、JWT 属性、MP 分页插件、静态资源映射 | 全部 |
| `util` | 4 | JWT 工具、鉴权过滤器、鉴权判定、响应写出 | entity、service |
| `Aop` | 2 | `@GetToken` 注解 + 切面，把当前登录用户塞进 `ThreadLocal` | util |
| `GlobarException` | 1 | 全局异常 → 统一 `Result` 的翻译层 | common |
| `enumClass` / `exception` | 3 + 1 | 枚举常量；业务异常 | 无 |

**核心规矩（记住这一条就不会乱）：依赖只能从上往下。**
`controller → service → mapper → entity`。
反过来（mapper 调 service、entity 调 controller）一次都不该出现。

### 1.3 一次请求的完整旅程（建议背下来）

以「用户点开一个会话，拉历史消息」为例：

```
① 浏览器  GET /api/psychological-chat/sessions/session_3/messages   Header: token=xxx
② SecurityConfig      → 不在 PUBLIC_MATCHERS 里，需要认证
③ JwtAuthticationFilter（OncePerRequestFilter）
     - 从 Header 取 token（先 Authorization 去 Bearer 前缀，再兼容旧的 token 头）
     - 验签 + 验签发者 + 验过期 → 失败：401 + A0230
     - 查用户、看 status 是否正常 → 不正常：403 + A0231
     - 比对 tokenVersion（改密码会 +1）→ 不符：401 + A0230
     - 通过 → SecurityContext 里放 Authentication（权限是 ROLE_1 或 ROLE_2）
④ Token_Aspect（@GetToken 切面）→ 再解析一次 token，把 userId 放进 ThreadLocal
⑤ Controller.listMessages()
     - Token_Aspect.getUserId() 拿到 userId
     - extractDbSessionId("session_3") → 3
     - checkOwnership(3)  → 不是自己的会话 → 抛 BusionessException("无权操作该会话")
     - consultationMessageService.listBySession(3)
⑥ Service → Mapper → SQL：select * from consultation_message where session_id=3 order by created_at asc
⑦ 转成 ConsultationMessageResponseDTO 列表 → Result.success(list) → JSON 返回
⑧ 切面 finally 里清掉 ThreadLocal（必须！线程会被复用）
```

这 8 步是**所有需要登录的接口都走的路**，只是 ⑤⑥⑦ 换成各自业务。看懂这一遍，其余接口都是同一套骨架。

## 2. 五个核心业务的数据流

### 2.1 登录（含失败限流）

```
POST /api/user/login {username, password}
  ↓
UserService.login()
  ├─ ① 查限流表 LOGIN_FAIL（内存 ConcurrentHashMap）：该账号 5 分钟内失败 ≥5 次 → 直接拒绝
  ├─ ② 先按 username 查 user 表；查不到再按 email 查
  │     ⚠️ 故意不写 eq(username).or().eq(email)：若甲的用户名 = 乙的邮箱，会查出两行直接抛异常
  ├─ ③ BCrypt.matches 比密码
  │     用户不存在 / 密码错 → 统一返回「用户名或密码错误」（防止探测账号是否存在）
  │     失败 → recordFail() 累加计数
  ├─ ④ 密码对了才看 status（顺序不能反，否则「已被禁用」本身也泄露账号存在）
  ├─ ⑤ 成功 → LOGIN_FAIL.remove() 清零
  └─ ⑥ JwtTokenUtil.generateToken(id, username, userType, tokenVersion) → 24 小时有效
  ↓
返回 Result<{token, roleType, userInfo}>
```

**关键理解**：`tokenVersion` 从第一天就写进了 JWT，但**只在改密码时才会变**。它是「让旧 token 立刻作废」的开关。

### 2.2 AI 流式对话（本项目最复杂的一条链路）

```
① POST /session/start {sessionTitle, initialMessage}
     → 建 consultation_session 记录（标题为空则生成「宁渡AI助手 - 09-27-2026 15:03:12」）
     → 把 initialMessage 存成第一条用户消息
     → 返回 sessionId = "session_" + 数据库自增id

② POST /stream {sessionId, userMessage}   ← 返回 SSE 流，不是普通 JSON
     ├─ Token_Aspect 取 userId；extractDbSessionId + checkOwnership 防越权写入
     └─ PsychologicalSupportService.streamPsychologicalChat()
          ① 若 messageCount == 1 且最后一条消息内容 == 本次 userMessage
             → 判定为「start 时已存过的初始消息」，**跳过保存**（防重复）
          ② 否则 saveUserMessage 入库（senderType=1）
          ③ conversationId = "conversation_" + sessionId
          ④ chatClient("open-ai").prompt().user(内容)
               .advisors(spec -> spec.param("chat_memory_conversation_id", conversationId))
               .stream().content()
               → 每个片段：拼进 fullResponse 并 sink.next(片段)
               → doOnComplete：把完整回复存库（senderType=2, ai_model="openai"）
          ⑤ 回到 Controller：片段包成 event=message 的 SSE 帧
               + 末尾补一帧 event=done
               + onErrorResume → event=error 帧
               + delayElements(50ms) 让"流式感"看得见
```

前端拿到 `done` 帧后会做两件事：**关掉「正在输入」状态**，然后**调情绪花园接口**。这也是 2.3 的起点。

**两个必须记住的设计约束**：
1. `open-ai` 这个 ChatClient 挂了 `MessageChatMemoryAdvisor`，它**强制要求**每次调用都传 `chat_memory_conversation_id`，不传直接抛异常 → 一次性分析（情绪日记/情绪花园）必须用 `analysis` 那个 bean。
2. ChatMemory 是**内存实现**（`MessageWindowChatMemory`，最多 30 条）。**重启即丢**，而且 key 只增不减（`conversation_session_1`、`_2`… 永不释放）。

### 2.3 情绪花园（会话情绪分析 + 24 小时缓存）

```
GET /session/session_3/emotion
  ├─ 归属校验（非管理员只能看自己的）
  ├─ 查缓存条件：last_emotion_analysis 非空
  │             ｜ last_emotion_updated_at 在 24 小时内
  │             ｜ last_emotion_msg_count == 当前消息条数
  │   → 三个都满足 → 反序列化直接返回（实测 0.01 秒）
  └─ 不满足 → analyzeSessionEmotion()
       ① 取出会话全部消息，拼成「用户：xxx\nAI：yyy\n…」
       ② 只取**最后 8000 字**（太长会超模型上下文，且越靠后越重要）
       ③ analysisChatClient.system(EMOTION_ANALYSIS_PROMPT).user(text).call()  ← 阻塞式！
       ④ normalize() 兜底：AI 漏字段、分数越界、riskLevel 与 isNegative 矛盾，全部修正
       ⑤ 把结果 JSON 写回 session 的三个字段（下次就能命中缓存）
```

**⚠️ 这条链路有个已知性能陷阱**：缓存失效时那个 `.call()` 是**同步阻塞**的，实测 1 条消息就要 ~10 秒，消息多会更久。所以「AI 对话后第一次刷新情绪花园」必定慢。
（前端已把该接口单请求超时放宽到 60 秒；根治方案是改成异步任务，见第 4 章。）

### 2.4 情绪日记 + 异步 AI 分析（本项目的「任务队列」）

用户写日记时**不等 AI**，接口立刻返回；AI 分析交给后台调度器：

```
POST /api/emotion-diary {diaryDate, moodScore, ...}
  ├─ 按 (user_id, diary_date) 查：有就更新、没有就插入  ← 表上有组合唯一键，天然幂等
  ├─ analysisTaskService.enqueue(diaryId, userId)
  │    → 若已有 PENDING 任务，直接复用（防重复入队）；否则插一条 PENDING
  └─ 返回日记本体（秒回）

后台（AnalysisTaskScheduler，@Scheduled fixedDelay=30s，启动后 10.1s 开始）
  ├─ ① recycleStuck()      把 PROCESSING 且 started_at 超 5 分钟、重试没用完的 → 退回 PENDING（retry+1）
  ├─ ② markStuckAsFailed() 把上面那类但重试已耗尽的 → 直接 FAILED
  └─ ③ 捞最多 20 条 PENDING（priority 降序、id 升序）
       逐条：
         markProcessing(id)   ← 带 where status='PENDING' 的条件更新，抢到才返回 1（防并发重复执行）
         查日记本体的内容 → EmotionDiaryAnalysisService.analyzeEmotionDiary(diaryId, force=true)
                            → 调 AI → normalize → 写回 diary.ai_emotion_analysis
         markCompleted(id) 或 markFailed(id, msg)（retry_count+1，未到上限退回 PENDING）
```

**为什么值得学这一套**：它是「接口快、耗时活后台干、失败能重试、进程被杀也能自愈」的标准做法。
`recycleStuck` 用 `started_at < now - 5min` 判定「卡死」，正是为了处理「服务重启导致任务永远停在 PROCESSING」。

### 2.5 文件上传与访问

```
POST /api/file/upload  (multipart)
  ├─ 校验：非空 → 大小 ≤10MB → 扩展名在白名单（图片 + pdf/txt/doc/xls/ppt）
  ├─ 存盘：{file.upload-dir}/yyyy-MM/{uuid}.{ext}
  ├─ 入库 sys_file_info：file_path="/files/yyyy-MM/uuid.ext"、business_type/business_id 多态关联业务
  └─ 返回 FileUploadVO

访问：GET /files/yyyy-MM/uuid.ext
  → WebMvcConfig.addResourceHandlers 把 /files/** 映射到磁盘 uploadDir
  → 注意：/files/** 在 SecurityConfig 白名单里，**无需登录即可访问**
```

## 3. 优化后的架构方案（to-be）

### 3.1 目标：把「混在一起的东西」拆开

| 现状问题 | 具体表现 | 优化动作 |
|---|---|---|
| 包名拼写错误 | `mappper`(3 个 p)、`Consultaion`、`Consultion`、`Busioness`、`Globar`、`Authtication`、`AiService`/`Aop` 大写 | 一次性改名（见 3.2 目标结构），改完跑全量回归 |
| Controller 有业务逻辑 | `checkOwnership`、`extractDbSessionId`、`describe`、`errorStream` 写在 Controller | 下沉到 service / 独立工具类；`checkOwnership` 目前 Controller 与 Service 各写一份，合并为一份 |
| 鉴权判定散落四处 | SecurityConfig 白名单 + Filter + `@GetToken` 切面 + `@PreAuthorize` | 保留 Filter（认证）+ `@PreAuthorize`（授权），**去掉 `@GetToken` 切面**，改从 SecurityContext 取 userId |
| 同一请求 JWT 解析两次 | Filter 验一遍，切面又验一遍 | Filter 解析后把 userId 放进 `Authentication` 的 principal，业务层直接读 |
| userId 从静态 ThreadLocal 取 | 忘了加 `@GetToken` 就拿到 null，且是隐藏依赖 | 改成 `HandlerMethodArgumentResolver`，Controller 方法签名直接写 `@CurrentUserId Long userId` |
| 缺事务 | `deleteSession`（先删消息→再删会话）中途失败会留半截数据 | 加 `@Transactional` |
| 错误码两套语义 | `ResultCode` 是 `"200"/"6010"`，而 `BusionessException` 的 code 硬编码字符串 `BUSINESS_ERROR`，且 HTTP 恒 200 | 统一走 `ResultCode`，并明确「HTTP 状态码 vs 业务码」的分工 |
| 没有异常兜底 | 未预期异常返回 Spring 默认 `{timestamp,status,error,path}`，没有 code | 恢复 `@ExceptionHandler(Exception.class)` |
| 查询接口不分页 | `/emotion-diary/admin/page` 返回裸 List，最多 500 条 | 换成 `Page<EmotionDiaryAdminVO>` |

### 3.2 建议的目标目录结构

```
com.lzc.mindaispringboot
├── MindAiSpringBootApplication.java
├── common/                     # 全项目共用的「词汇表」
│   ├── Result.java             #   统一响应外壳（建议只留 code / msg / data，去掉重复的 message、success）
│   ├── ResultCode.java         #   错误码字典
│   └── exception/              #   BusinessException（原 BusionessException）+ GlobalExceptionHandler（原 Globar…）
├── config/                     # Spring 装配
│   ├── SecurityConfig.java
│   ├── ChatClientConfig.java
│   ├── JwtConfig.java
│   ├── MybatisPlusConfig.java
│   └── WebMvcConfig.java
├── security/                   # 鉴权相关（原 util 里的一半 + Aop）
│   ├── JwtAuthenticationFilter.java   # 只做「认人」，不做业务
│   ├── CurrentUserId.java             # 注解
│   ├── CurrentUserIdResolver.java     # 参数解析器（取代 ThreadLocal 切面）
│   └── AuthUtil.java                  # isAdmin()
├── controller/                 # 只收参数、只包 Result
├── service/                    # 业务规则
│   ├── …Service.java           # 建议「接口 + impl」或至少保持单类
│   └── ai/                     # AI 能力单独一包：PromptManage / AiChatService / EmotionAnalysisService
├── task/                       # 后台任务：AnalysisTaskScheduler
├── mapper/                     # 原 mappper
├── entity/                     # 与表一一对应
├── dto/                        # 入参：xxxRequest / xxxQuery
├── vo/                         # 出参：xxxVO
└── util/                       # 纯工具（JwtTokenUtil、ResponseUtil）
```

**改动顺序（从安全到激进，每步都能单独验证）**：
1. 先补 `@Transactional`、恢复异常兜底、修 `Result` 冗余字段 —— 纯增量，零破坏面。
2. 再把 `@GetToken` 切面换成参数解析器 —— 接口签名变了，但对外行为不变，回归一遍所有接口即可。
3. 最后做包名/类名大改名 —— 全项目机械替换，改完必须全量回归（尤其是 `@MapperScan` 路径和 `@ConfigurationProperties` 前缀）。

### 3.3 分层职责表（照这个表 review 代码就不会跑偏）

| 层 | 该做 | 不该做 |
|---|---|---|
| Controller | 接参、`@Valid`、调 service、`Result.success()`、HTTP 语义（状态码、内容类型） | 写 if-else 业务判断、直接调 Mapper、拼 SQL 条件 |
| Service | 业务规则、权限校验、事务边界、实体↔VO 转换、编排多个 Mapper | 处理 `HttpServletRequest`、直接返回 `Result` |
| Mapper | 数据访问，复杂统计可手写 `@Select` | 写业务逻辑（哪怕是「状态判断」） |
| AI 层 | 提示词、调用模型、结构化解析、兜底 normalize | 直接操作数据库以外的业务表（写回由 service 负责更清晰） |
| 任务层 | 调度、并发抢占、重试与回收 | 内联业务规则（应调 service） |

## 4. 已知问题与优化路线（按优先级）

### P0 —— 会真实影响用户/数据的

| # | 问题 | 现状与现象 | 建议 |
|---|---|---|---|
| 1 | **会话情绪分析同步阻塞** | 缓存失效时 `.call()` 阻塞，实测 10 秒起；AI 对话后第一次刷新必然慢 | 改成「先返回旧缓存/分析中状态 + 异步任务重算」（直接复用 `ai_analysis_task` 那一套，把 `diaryId` 换成 `sessionId`） |
| 2 | **`deleteSession` 无事务** | 先删消息再删会话，中间抛异常 → 会话还在、消息没了 | 加 `@Transactional` |

## 6. 一句话总结

这个后端的骨架是**标准的「Controller → Service → Mapper」三段式**，额外长出了两条自己的枝：
**一条 AI 能力枝**（`AiService` + 两个 ChatClient + 提示词 + 结构化出参）和
**一条任务枝**（`ai_analysis_task` + `@Scheduled` 消费者 + 重试/回收）。

它目前最值得改的三件事，按性价比排序：
① **把阻塞式 AI 分析异步化**（体验直接变好，且已有现成模式可抄）；
② **补齐事务与异常兜底**（防脏数据、防排查失明，改动极小）；
③ **把隐藏契约变显式**（`@GetToken` + ThreadLocal → 参数解析器；包名改对）——这步是「半年后自己还能看懂」的关键。
