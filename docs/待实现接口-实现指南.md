### 0.3 全项目通用约定（写代码前先记住这 5 条）

**① 统一响应体 `Result<T>`**（`common/Result.java`）

```json
{ "code": "200", "msg": "操作成功", "data": { } }
```

失败用 `Result.error(code, msg, data)`，业务异常直接 `throw new BusionessException("提示语")`，由 `GlobarExceptionHandler` 兜住。

> **第 7 章会给 `Result` 再加 `success` / `message` 两个字段**（前端样例里要求的），
> 属于纯新增，不影响老接口。加了之后返回体形如：
> `{ "code":"200", "msg":"操作成功", "success":true, "message":"操作成功", "data":{ } }`

**② 鉴权：请求头 `token`，裸 JWT（不带 Bearer）**

这是**当前代码的实际行为**，务必注意：

```java
// JwtTokenUtil.extractTokenFromRequest —— 写死读 "token" 头
String token = request.getHeader("token");
```

而 `application.yml` 里配的是 `header: Authorization` + `token-prefix: "Bearer "` —— **这两个配置目前完全没被使用**。

> ⚠️ 联调前必须和前端定死是哪一种。改法见 [附录 A.1](#a1-jwttokenutil-不读-yaml-配置)，改完前端就能用标准的 `Authorization: Bearer xxx`。

**③ 登录态用户 ID 从 AOP 拿**

```java
@GetToken                          // 标注在 Controller 方法上，触发切面解析 token
Long userId = Token_Aspect.getUserId();
```

**④ 管理员判定**

```java
// 方式一：方法级注解（Spring Security 的 @PreAuthorize）
@PreAuthorize("hasRole('2')")      // 对应 User.userType = 2，内部会拼成 ROLE_2

// 方式二：代码内分支（适合"管理员看全部、用户看自己"这类同一接口两种行为）
boolean isAdmin = AuthUtil.isAdmin();
```

注意区分：**`@PreAuthorize` 不满足直接 403；`AuthUtil.isAdmin()` 是你自己在代码里分流。**
管理端专用接口用①，用户端/管理端共用接口用②。

**⑤ 分页已就绪**

`MybatisPlusConfig` 里已注册 `PaginationInnerInterceptor`，直接用 `new Page<>(pageNum, pageSize)` 即可。
返回类型是 MyBatis-Plus 的 `Page<T>`，前端拿 `records`（数据）+ `total`（总数）。

> ⚠️ **例外**：**第 8 章的管理端情绪日志已决定「不做分页」**，直接返回 `List<EmotionDiaryAdminVO>`，
> 前端拿到的 `data` 就是数组（见 8.3② / 8.5）。别把这里的通用约定套到那个接口上。

### 0.4 ⚠️ 命令行编译：`JAVA_HOME` 必须是 JDK 17+（2026-09-20 实测踩坑）

**症状**：在项目根目录跑 `mvnw.cmd compile`，报一堆看起来像"语法错误"的错，而且**位置很怪**：

```
[ERROR] service/FileService.java:[104,45] 非法的表达式开始
[ERROR] service/FileService.java:[105,23] 需要:
[ERROR] util/ResponseUtil.java:[20,13] 孤立的case
```

但打开那两行看，代码完全合法 —— 它们是 **Java 14+ 的 switch 表达式**（`case "jpg", "jpeg" -> "IMG";`）。

**真正原因：`JAVA_HOME` 指向了 JDK 1.8**，Maven 用 Java 8 编译，而 Java 8 **不认识** switch 表达式、
`record`、`var` 这些新语法 → 全部报成"非法的表达式开始 / 需要: / 孤立的case"。

**先自查**：

```bash
java -version        # 看输出是不是 1.8
echo %JAVA_HOME%     # Windows；Git Bash 用 echo $JAVA_HOME
```

**本项目实测环境（2026-09-20）**：

| 项 | 值 |
|---|---|
| 系统 `JAVA_HOME` | `C:\Program Files\Java\jdk1.8.0_202` ← ❌ 编译必失败 |
| 实际可用的高版本 JDK | `D:\openjdk-26.0.1` ← ✅ 用这个 |

**临时解决（只对当前这条命令生效，不改系统设置）**：

```bash
# Windows cmd
set JAVA_HOME=D:\openjdk-26.0.1 && mvnw.cmd -DskipTests compile

# Git Bash
JAVA_HOME="D:/openjdk-26.0.1" ./mvnw.cmd -DskipTests compile
```

**永久解决**（二选一）：

1. 系统环境变量把 `JAVA_HOME` 改成 `D:\openjdk-26.0.1`（注意：有些别的工具依赖 1.8，改前想清楚）；
2. 不改系统变量，在 IDEA 里把项目的 **Project SDK** 设为 17/26，日常用 IDEA 编译运行即可 ——
   这时 **IDEA 能跑但命令行编译失败是正常的**，不用怀疑代码。

**为什么 IDE 里是好的**：IDEA 用自己的 Project SDK 编译，跟命令行 `JAVA_HOME` 没关系。
所以「IDEA 能启动、命令行 `mvnw` 报一堆语法错」这种组合，**几乎一定是 JDK 版本不一致**，不是代码问题。

> 编译成功后仍会看到 Lombok 的 `WARNING: sun.misc.Unsafe` —— 那是 Lombok 在高版本 JDK 上的兼容告警，
> **不影响编译结果**，可以忽略。

## 2. 会话列表改分页

> **状态（2026-09-20 更新）**：本章**分页已改完** —— `SessionPageQuery`、`ConsultationSessionService.pageSessions`、
> `PsychologicalChatController.listSessions` 都已带上了分页。
> **但还差两件事，做完才闭环：**
> 1. **§2.5**：返回的还是裸实体 `Page<ConsultationSession>`，缺 `userNickname` / `lastMessageContent` /
>    `messageCount` / `lastMessageTime` —— 前端列表这几列现在是空的；
> 2. **附录 A.4**：页码参数名两端不匹配（用户端发 `pageNum`、管理端发 `currentPage`，后端字段却是错拼的
>    `pargeNum`）—— 翻页点了没反应。

### 2.1 现状与差距

现在 `PsychologicalChatController.listSessions` 是这样的：

```java
@GetToken
@GetMapping("/sessions")
public Result<List<ConsultationSession>> listSessions(@RequestParam(value = "userId", required = false) Long userId){
    Long currentUserId = Token_Aspect.getUserId();
    Long filterUserId = AuthUtil.isAdmin() ? userId : currentUserId;   // 管理员可传 userId 查别人
    return Result.success(consultationSessionService.listSessions(filterUserId));
}
```

问题只有一个：**返回 `List`，规格要的是分页**。数据量小的时候没感觉，但会话是持续增长的表——用户聊三个月就是几百条，一次全返回会把前端列表拖垮，也无法做"第 2 页"。

好消息：分页插件已经配好了（`MybatisPlusConfig`），改动只需要 3 处。

#### ② 改 Service：`service/ConsultationSessionService.java`

在现有 `listSessions` 后面追加（**不要删** `listSessions`，其他地方可能还在用）：

```java
    /** 分页查询会话列表 */
    public Page<ConsultationSession> pageSessions(SessionPageQuery query) {
        LambdaQueryWrapper<ConsultationSession> qw = new LambdaQueryWrapper<>();
        // userId 为空表示"查全部"，只有管理员会走到这里（Controller 层已做收窄）
        if (query.getUserId() != null) {
            qw.eq(ConsultationSession::getUserId, query.getUserId());
        }
        // 标题模糊
        if (StrUtil.isNotBlank(query.getKeyword())) {
            qw.like(ConsultationSession::getSessionTitle, query.getKeyword());
        }
        qw.orderByDesc(ConsultationSession::getStartedAt);   // 最近的会话排前面
        return consultationSessionMapper.selectPage(new Page<>(query.getPageNum(), query.getPageSize()), qw);
    }
```

```java
import com.baomidou.mybatisplus.extension.plugins.pagination.Page;
import com.lzc.mindaispringboot.common.Dto.SessionPageQuery;
```

#### ③ 改 Controller：`controller/PsychologicalChatController.java`

把 `listSessions` 整个方法替换成下面这段：

```java
    /**
     * 会话列表（分页）
     * - 管理员：可传 userId 查指定用户，不传则查全部
     * - 普通用户：无论传什么都只能看自己的（防止越权）

    @GetToken

        return Result.success(consultationSessionService.pageSessions(query));
```

要点：**不要在 for 里逐条查消息/用户**（N+1），改成"先批量查一次，再在内存里分组拼装"。

```java
    /** 分页查询会话列表（带用户昵称 + 消息数 / 最后消息预览） */
    public Page<SessionAdminVO> pageSessions(SessionPageQuery query) {
        // ① 只查会话本身（分页 + 条件 + 排序）
        LambdaQueryWrapper<ConsultationSession> qw = new LambdaQueryWrapper<>();
        if (query.getUserId() != null) {
            qw.eq(ConsultationSession::getUserId, query.getUserId());
        }
        if (StrUtil.isNotBlank(query.getKeyword())) {
            qw.like(ConsultationSession::getSessionTitle, query.getKeyword());
        }
        qw.orderByDesc(ConsultationSession::getStartedAt);   // 最近的在最前

        Page<ConsultationSession> page = consultationSessionMapper.selectPage(
                new Page<>(query.resolvePage(), query.getPageSize()), qw);   // ← 双端页码兼容

        List<ConsultationSession> records = page.getRecords();
        Page<SessionAdminVO> result =
                new Page<>(page.getCurrent(), page.getSize(), page.getTotal());
        if (records.isEmpty()) {
            result.setRecords(List.of());
            return result;
        }

        List<Long> sessionIds = records.stream().map(ConsultationSession::getId).toList();

        // ② 一次查出这批会话的全部消息，按 sessionId 分组（避免 N+1）
        List<ConsultationMessage> allMessages = consultionMessageMapper.selectList(
                new LambdaQueryWrapper<ConsultationMessage>()
                        .in(ConsultationMessage::getSessionId, sessionIds)
                        .orderByAsc(ConsultationMessage::getCreatedAt));   // 升序，最后一条是末位
        Map<Long, List<ConsultationMessage>> msgGroup = allMessages.stream()
                .collect(Collectors.groupingBy(ConsultationMessage::getSessionId));

        // ③ 一次查出这批用户
        List<Long> userIds = records.stream().map(ConsultationSession::getUserId).distinct().toList();
        Map<Long, User> userMap = userMapper.selectBatchIds(userIds).stream()
                .collect(Collectors.toMap(User::getId, u -> u));

        // ④ 内存拼装
        List<SessionAdminVO> voList = new ArrayList<>();
        for (ConsultationSession s : records) {
            List<ConsultationMessage> msgs = msgGroup.getOrDefault(s.getId(), List.of());
            ConsultationMessage last = msgs.isEmpty() ? null : msgs.get(msgs.size() - 1);
            User u = userMap.get(s.getUserId());
            voList.add(SessionAdminVO.builder()
                    .id(s.getId())
                    .userId(s.getUserId())
                    .userNickname(u == null ? null : u.getDisplayName())   // 昵称优先，没昵称退用户名
                    .sessionTitle(s.getSessionTitle())
                    .lastMessageContent(last == null ? null : SessionAdminVO.preview(last.getContent()))
                    .messageCount((long) msgs.size())
                    .lastMessageTime(last == null ? null : last.getCreatedAt())
                    .startedAt(s.getStartedAt())
                    .build());
        }
        result.setRecords(voList);
        return result;
    }
```

### 4.2 四个必须注意的地方（跟我之前暂定的不一样）

| # | 我之前暂定 | 你前端实际 | 后果 |
|---|---|---|---|
| 1 | `riskLevel` 是字符串「正常/关注/预警/**紧急**」 | **整数 0/1/2/3**，文案第四档是「**危机**」 | 按暂定值写，前端 `riskTextMap[2]` 找不到 → 显示「未知风险等级」，颜色掉 `info` |
| 2 | `emotionNature` 是「正面/中性/负面情绪」三个值 | **`isNegative` 布尔值**，只有 true/false | 没有"中性"这一档，中性只能归 `false`（显示正面情绪） |
| 3 | 字段叫 `dominantEmotion` / `emotionIntensity` / `professionalAdvice` | `primaryEmotion` / `emotionScore` / `suggestion` | 名字全不对，前端读到 `undefined`，卡片七项全空 |
| 4 | `dominantEmotion`（列表页那列）和 AI 的「主要情绪」是同一个映射 | **两个映射表不一样** | 见下方说明 |

**关于第 4 点**，你前端其实有两张「主要情绪」映射表：

```js
// 列表页那列，读的是日记自带字段 dominantEmotion（7 个值）
getEmotionTagType:  快乐 / 开心 / 平静 / 兴奋 / 愤怒 / 悲伤 / 焦虑

// AI 卡片里，读的是 primaryEmotion（10 个值）
getAiEmotionTagType: 快乐 / 平静 / 兴奋 / 满足 / 愤怒 / 悲伤 / 焦虑 / 恐惧 / 沮丧 / 压力
```

所以提示词里要把 `primaryEmotion` 限定在那 **10 个值**里，这样标签颜色全部对得上。

**关于 `emotionScore` 的语义**：你的颜色函数里**分数越高越红**（≥80 红色）。
所以这个分数不能是"开心程度"，否则一个人很开心（90 分）会显示成红色危险条。
建议定义为**情绪强度 + 负面程度**的综合分：越强烈、越负面 → 分数越高。
（如果你本意是"强度"而不含正负，那颜色函数要反过来写，告诉我我再调。）

### 4.4 结构定义（为什么必须用 `record`）

```java
package com.lzc.mindaispringboot.AiService;

import java.util.List;

public class StructOutPut {
    // ... 原有 StreamChatSession / EmotionAnalysis 保持不变 ...

    /**
     * 情绪日记的 AI 分析结果 —— 字段名严格对齐管理端「AI情绪分析结果」卡片。
     *
     * 必须用 record，不能用 class + @Data：
     * 字段 isNegative 如果用 Lombok @Data 生成，getter 会变成 getIsNegative()/isNegative()，
     * Jackson 序列化出来的 key 可能是 "negative" 而不是 "isNegative"，前端就取不到值。
     * record 的 component 名就是 JSON key，不会走 getter 命名规则。
     */
    public record DiaryEmotionAnalysis(
            String primaryEmotion,              // 主要情绪：快乐/平静/兴奋/满足/愤怒/悲伤/焦虑/恐惧/沮丧/压力
            Integer emotionScore,               // 情绪强度 0~100（越高越负面/越强烈）
            Integer riskLevel,                  // 风险等级：0正常 1关注 2预警 3危机
            Boolean isNegative,                 // 是否负面情绪
            String suggestion,                  // 专业建议（一句话）
            String riskDescription,             // 风险描述（一句话）
            List<String> improvementSuggestions // 改善建议 2~4 条
    ) {}
}
```

> 如果你坚持用 class + `@Data`，那就必须给 `isNegative` 加 `@JsonProperty("isNegative")`，
> 否则序列化出来的 key 对不上。**用 record 省事，推荐。**

> ℹ️ **7 字段 vs 11 字段**：你库里已有的老数据（如 id=1804）是 **11 字段**
> （多出 `keywords` / `icon` / `label` / `timestamp`），而这里按前端实际读取的 **7 个字段**定义。
> 前端详情弹窗只解析这 7 个 key，**多出来的字段它无视**，所以新老数据都能正常渲染，不影响功能。
> 想让新数据和老数据同构的话，把那 4 个字段也加进 record + 提示词即可（**可选，非必须**）。

#### 4.4.1 ⚠️ 别用 Hutool 的 `JSONUtil` 处理 record（实测结论）

**Hutool 5.8.25 完全不支持 Java record** —— 不是"不稳妥"，是直接不能用。
下面是我用项目里的 `hutool-all-5.8.25.jar` 真跑出来的结果：

| 操作 | Hutool `JSONUtil` 实测结果 |
|---|---|
| `JSONUtil.toJsonStr(record)` | ⚠️ **只输出 `{"isNegative":false}`**，其余 6 个字段全丢。原因：Hutool 只认 `getXxx()` / `isXxx()` 命名，而 record 的访问器是 `primaryEmotion()` 这种无前缀写法，它找不到 |
| `JSONUtil.toBean(json, 记录类.class)` | 💥 抛 `ConvertException: Can not Converter from [JSONObject] to [...]` |
| `JSONUtil.toBean(null, 记录类.class)` | 💥 同样抛 `ConvertException`（不会返回 null） |

**结论：改用 Jackson 的 `ObjectMapper`。** 直接注入，Spring Boot 已经自动配好这个 bean：

```java
    @Resource
    private ObjectMapper objectMapper;   // import tools.jackson.databind.ObjectMapper;
```

> ⚠️ **本项目的 Spring Boot 4 用的是 Jackson 3，包名是 `tools.jackson.*`**
> （**不是** `com.fasterxml.jackson.*`）。包名写错会在启动时直接炸：
>
> ```
> APPLICATION FAILED TO START
> A component required a bean of type 'com.fasterxml.jackson.databind.ObjectMapper'
> that could not be found.
> ```
>
> 原因：Boot 4 把 Jackson 自动配置挪到了独立的 `spring-boot-jackson` 模块，
> 它注册的 bean 类型是 **`tools.jackson.databind.json.JsonMapper`**（Jackson 3）。
> 而 `com.fasterxml.jackson.core:jackson-databind:2.21.5` 只是被其他依赖捎带进来的，
> **根本没有被注册成 bean**，按类型注入必然找不到。
>
> **唯一例外是注解**：Jackson 3 的 `jackson-annotations` 仍留在 `com.fasterxml.jackson.annotation`
> 包下（官方 pom 里写着「Annotations remain at Jackson 2.x group id」），
> 所以 `@JsonInclude`、`@JsonProperty` 这些照旧写在 `com.fasterxml.jackson.annotation`，不用改。

Jackson 3.1.5 的实测结果（拿项目自己的 classpath 真跑）：

| 操作 | 结果 |
|---|---|
| `objectMapper.writeValueAsString(record)` | ✅ 7 个字段完整输出，`isNegative` 的 key 也对 |
| `objectMapper.readValue(json, 记录类.class)` | ✅ 正常还原，含 `List<String>` |
| `readValue("{}", 记录类.class)` | ⚠️ **不抛异常**，返回字段全为 `null` 的 record —— 最阴的一条，见下 |
| `readValue(旧格式 json, 记录类.class)` | ✅ 忽略不认识的字段（Jackson 3 默认就关掉了 `FAIL_ON_UNKNOWN_PROPERTIES`） |

> ⚠️ **上面那个 ⚠️ 是"看起来安全、其实静默出错"的典型。**
> 旧 Hutool 写进去的缓存就是 `{}`（`EmotionAnalysis` 没有 `isXxx` 字段，一个字都写不出来）
> 或 `{"isNegative":false}`（`DiaryEmotionAnalysis` 只写出这一个）。Jackson 读到它们**不会报错**，
> 而是给你一个**字段全 null 的合法对象**。
>
> 后果：**缓存分支只写 try-catch 是不够的** —— 你会把空对象当有效缓存返回给前端，
> 前端拿到一张空卡片，而且 `last_emotion_updated_at` 在 24 小时内一直"新鲜"，
> **不会自愈，只能等 24 小时或手工清库**。
>
> 正确做法：`readCache()` 里解析完再校验一个关键字段
> （日记级看 `primaryEmotion() != null`，会话级看 `overallMood() != null`）。
> 本指南 4.6 与 7.5.3 的 `readCache()` 都是这么写的。
>
> 注意：Jackson 3 的 `JacksonException` 是**非受检异常**（`extends RuntimeException`，已实测），
> 所以**方法签名上不用写 `throws`**。`readCache()` 里那个 `catch (Exception e)` 照样有效。
> （Jackson 2 时代是要写 `throws JsonProcessingException` 的，从别处抄代码时留意这条差别。）
>
> 这个坑不只影响日记级 —— **第 7 章的会话级情绪分析同样中招**
> （`PsychologicalSupportService` 里那两行 `JSONUtil`），那条链路已经在跑了，
> 表现是：第一次调用正常（走 AI），第二次调用（走缓存）直接 500。

### 4.6 Service：`AiService/EmotionDiaryAnalysisService.java`（新建）

```java
package com.lzc.mindaispringboot.AiService;

import cn.hutool.core.text.StrBuilder;
import tools.jackson.databind.ObjectMapper;   // Jackson 3，注意是 tools.jackson
import com.lzc.mindaispringboot.entity.EmotionDiary;
import com.lzc.mindaispringboot.exception.BusionessException;
import com.lzc.mindaispringboot.mappper.EmotionDiaryMapper;
import jakarta.annotation.Resource;
import org.springframework.ai.chat.client.ChatClient;
import org.springframework.beans.factory.annotation.Qualifier;
import org.springframework.stereotype.Service;

import java.time.LocalDateTime;
import java.util.List;

/**
 * 情绪日记的 AI 分析：分析一条日记，把结构化结果写回 emotion_diary.ai_emotion_analysis。
 */
@Service
public class EmotionDiaryAnalysisService {

    /** 送给 AI 的文本上限 */
    private static final int MAX_TEXT_LENGTH = 8000;

    private final ChatClient chatClient;

    @Resource
    private EmotionDiaryMapper emotionDiaryMapper;
    /** Spring Boot 已自动配置，直接注入即可 */
    @Resource
    private ObjectMapper objectMapper;

    public EmotionDiaryAnalysisService(@Qualifier("open-ai") ChatClient chatClient) {
        this.chatClient = chatClient;
    }

    /**
     * 分析指定日记并把结果写回数据库。
     * @param force true 表示忽略"近期已分析过"的判断，强制重算
     */
    public StructOutPut.DiaryEmotionAnalysis analyzeEmotionDiary(Long diaryId, boolean force) {
        EmotionDiary diary = emotionDiaryMapper.selectById(diaryId);
        if (diary == null) throw new BusionessException("情绪日记不存在");

        // 24 小时内分析过就不重复烧 token
        if (!force
                && diary.getAiAnalysisUpdatedAt() != null
                && diary.getAiAnalysisUpdatedAt().isAfter(LocalDateTime.now().minusHours(24))) {
            StructOutPut.DiaryEmotionAnalysis cached = readCache(diary.getAiEmotionAnalysis());
            // 读到「有效」缓存才返回；解析失败或关键字段缺失都会得到 null，落到下面重新分析
            if (cached != null) return cached;
        }

        String text = buildText(diary);
        if (text.isBlank()) throw new BusionessException("该日记暂无可分析的内容");

        StructOutPut.DiaryEmotionAnalysis result = chatClient.prompt()
                .system(PromptManage.DIARY_ANALYSIS_PROMPT)
                .user(text)
                .call()                                        // 阻塞式，非流式
                .entity(StructOutPut.DiaryEmotionAnalysis.class);

        // 兜底：AI 偶尔漏字段或缺省，保证前端不会渲染出 undefined
        result = normalize(result);

        diary.setAiEmotionAnalysis(objectMapper.writeValueAsString(result));
        diary.setAiAnalysisUpdatedAt(LocalDateTime.now());
        emotionDiaryMapper.updateById(diary);
        return result;
    }

    /** 组装送给 AI 的文本：只取日记自身的内容，不去读会话消息 */
    private String buildText(EmotionDiary diary) {
        // 一个字都没写的日记没有分析价值，返回空串交给上层抛业务异常
        if (!hasText(diary.getDiaryContent()) && !hasText(diary.getEmotionTriggers())) {
            return "";
        }

        StrBuilder text = new StrBuilder();
        text.append("【日记日期】").append(diary.getDiaryDate()).append("\n");
        if (hasText(diary.getDominantEmotion()))
            text.append("【自评情绪】").append(diary.getDominantEmotion()).append("\n");
        if (diary.getMoodScore() != null)    text.append("【情绪评分(1-10，越高越好)】").append(diary.getMoodScore()).append("\n");
        if (diary.getSleepQuality() != null) text.append("【睡眠质量(1-5)】").append(diary.getSleepQuality()).append("\n");
        if (diary.getStressLevel() != null)  text.append("【压力水平(1-5)】").append(diary.getStressLevel()).append("\n");
        if (hasText(diary.getEmotionTriggers()))
            text.append("【情绪触发因素】").append(diary.getEmotionTriggers()).append("\n");
        if (hasText(diary.getDiaryContent()))
            text.append("【日记内容】").append(diary.getDiaryContent()).append("\n");

        return text.length() > MAX_TEXT_LENGTH
                ? text.subString(text.length() - MAX_TEXT_LENGTH)   // 尾部截断，保留最近内容
                : text.toString();
    }

    /** AI 漏字段时补默认值，避免前端显示 undefined 或进度条异常 */
    private StructOutPut.DiaryEmotionAnalysis normalize(StructOutPut.DiaryEmotionAnalysis r) {
        if (r == null) {
            return new StructOutPut.DiaryEmotionAnalysis("平静", 30, 0, false, "保持当下的节奏就好", "情绪稳定", List.of());
        }
        Integer score = r.emotionScore() == null ? 50 : Math.max(0, Math.min(100, r.emotionScore()));
        Integer risk = r.riskLevel() == null ? 0 : Math.max(0, Math.min(3, r.riskLevel()));
        // 保证 riskLevel 与 isNegative 不矛盾
        Boolean negative = r.isNegative() != null ? r.isNegative() : risk >= 2;
        if (risk >= 2) negative = true;
        if (risk == 0) negative = false;
        return new StructOutPut.DiaryEmotionAnalysis(
                r.primaryEmotion(), score, risk, negative,
                r.suggestion(), r.riskDescription(),
                r.improvementSuggestions() == null ? List.of() : r.improvementSuggestions());
    }

    /**
     * 读缓存：解析失败、或解析出来是「残缺对象」时返回 null，交给调用方重新分析。
     *
     * ⚠️ 只 try-catch 是挡不住的：Jackson 读 "{}" 不会抛异常，
     * 而是返回一个字段全为 null 的合法 record。旧 Hutool 写入的缓存正是这种，
     * 所以必须再校验一个关键字段（详见 4.4.1 实测）。
     */
    private StructOutPut.DiaryEmotionAnalysis readCache(String json) {
        if (!hasText(json)) return null;
        try {
            StructOutPut.DiaryEmotionAnalysis cached =
                    objectMapper.readValue(json, StructOutPut.DiaryEmotionAnalysis.class);
            // primaryEmotion 为空 = 旧格式脏数据（Hutool 只会写出 {"isNegative":false}）
            return hasText(cached.primaryEmotion()) ? cached : null;
        } catch (Exception e) {
            return null;
        }
    }

    private boolean hasText(String s) {
        return s != null && !s.isBlank();
    }
}
```

> **2026-09-19 更正**：这里原来有一段「日记内容为空时回退取最近 3 个会话消息」的逻辑，**已删除**。
> 本项目的 AI 调用只有三个方向——**流式对话 / 会话级情绪花园 / 日记级分析**——
> 日记分析的数据源就该只有日记本身，越界去读会话消息会让两套结果互相打架。

### 4.7 接入保存流程：`service/EmotionDiaryService.java`

两处改动，都在 `saveOrUpdate` 里。

**【改动 1】查完日记立刻记下「这次是新建还是修改」**，下一步的 `force` 参数要用它：

```java
        EmotionDiary emotionDiary = emotionDiaryMapper.selectOne(qw);

        // 必须在 if (emotionDiary == null) 之前取：
        // 进了 else 分支后它已经被覆盖成同一个对象，就判断不出"原来有没有"了
        boolean exists = emotionDiary != null;

        LocalDateTime now = LocalDateTime.now();
        // ... 下面的 if / else 原样不动 ...
```

**【改动 2】保存成功后触发 AI 分析**，加在 `return emotionDiary;` **之前**。
关键是 **try-catch 包住**：AI 调用可能超时或失败，**绝不能连累日记保存本身**。

```java
        try {
            // exists=false（新建）→ 走「24 小时内不重复分析」的缓存规则
            // exists=true （修改）→ 强制重算，为什么见 4.7.1
            emotionDiaryAnalysisService.analyzeEmotionDiary(emotionDiary.getId(), exists);
        } catch (Exception e) {
            // 记日志即可，不要往外抛：日记已经存好了，不能因为 AI 挂了就告诉用户"保存失败"
            System.err.println("AI情绪分析失败，diaryId=" + emotionDiary.getId() + "：" + e.getMessage());
        }
        return emotionDiary;
```

> ⚠️ 两个位置都不能错
> ① `analyzeEmotionDiary` 必须在 `insert()` **之后**——自增 id 是 insert 完才回填的，早了 `getId()` 是 null；
> ② 别忘了给 `EmotionDiaryService` 注入 `@Resource private EmotionDiaryAnalysisService emotionDiaryAnalysisService;`

#### 4.7.1 为什么 `force` 传的是 `exists`，而不是固定的 `false`

**结论先说：用户端能改日记，而且不用加任何新接口。**

`saveOrUpdate` 里的 `else` 分支就是"改"—— 用户端没有单独的"编辑"接口，
同一个 `POST /api/emotion-diary` 再提交一次同一个 `diaryDate` 就是覆盖更新；
表上的唯一键 `(user_id, diary_date)` 保证了「一个用户一天只有一条」，第二次提交只可能是改。

你的真实数据里就有证据：id=1804 那条 `createdAt` 11:35:55、`updatedAt` 13:11:12，
中间差了一个半小时 —— 它被改过。

**所以问题不是「要不要支持改」（后端已经支持，禁改反而更麻烦），
而是「改了之后要不要让 AI 重算」。固定写 `false` 会漏：**

| 时间 | 用户动作 | 实际结果 |
|---|---|---|
| 上午 10:00 | 写「今天很开心」 | 分析完成，`riskLevel=0` |
| 下午 15:00 | 改成「其实很难受，什么都不想做」 | 间隔 5 小时 < 24 小时 → **直接返回旧缓存**，库里还是 `riskLevel=0` |

而且这不是小概率事件——看这个窗口的分布，"今天写完再改"正好全落在出事的那一格：

| 改动时间 | 距上次分析 | 固定 `force=false` 的结果 |
|---|---|---|
| 同一天内改（最常见：早上写一半、晚上接着补） | < 24 小时 | 命中缓存，看到旧结论 ❌ |
| 隔几天才改 | > 24 小时 | 条件不成立，自动重算 ✔ |

用户补充了更严重的情绪内容，`riskLevel` 却还是旧的偏低值 —— **这是安全向的漏判，必须堵。**

**为什么用 `exists` 而不是逐个字段比对**

精确判断"内容有没有变"要 4 个 `Objects.equals`（`diaryContent` / `emotionTriggers` /
`dominantEmotion` / `moodScore`）外加 `import java.util.Objects;`。
而 `exists` 一行就够，且覆盖全部修改场景：

| 场景 | `exists` | 结果 |
|---|---|---|
| 新建日记 | `false` | `aiAnalysisUpdatedAt` 本来就是 null，照常分析 ✔ |
| 改了内容再提交 | `true` | 强制重算，结论跟得上 ✔ |
| 手抖重复点保存（内容其实没变） | `true` | 多算一次，**结果正确**，只白花一次 token |

唯一"亏"的是第三行，而它本来就不常见。真要抠掉这一次调用，再升级成字段比对版（可选）：

```java
    // 可选升级：同样放在 if (emotionDiary == null) 之前，另需 import java.util.Objects;
    boolean contentChanged = emotionDiary != null && (
            !Objects.equals(emotionDiary.getDiaryContent(),    emotionDiarySaveDTO.getDiaryContent())
         || !Objects.equals(emotionDiary.getEmotionTriggers(), emotionDiarySaveDTO.getEmotionTriggers())
         || !Objects.equals(emotionDiary.getDominantEmotion(), emotionDiarySaveDTO.getDominantEmotion())
         || !Objects.equals(emotionDiary.getMoodScore(),       emotionDiarySaveDTO.getMoodScore()));
    // 然后把 4.7 改动 2 里的 exists 换成 contentChanged
```

**可选：要不要限制"只能改最近几天"**

现在**完全没有任何时间限制**，用户可以改上个月、去年的日记。想收紧的话在 `else` 分支里加一行
（需要 `import java.time.LocalDate;`）：

```java
    // 放在 else 分支里（只拦"改"，不拦"新建"）
    if (emotionDiary.getDiaryDate().isBefore(LocalDate.now().minusDays(7))) {
        throw new BusionessException("只能修改最近 7 天的日记");
    }
```

日记类产品的常见做法是「当天可改、隔天锁死」，也有「永久可改」的（当情绪记录本用）。
按你的产品定位定，不加就是永久可改。

> 顺带说清两端的权限边界：**管理端只有删除（`DELETE /admin/{id}`），没有编辑接口**，
> 这一点是对的，别给管理端加改日记的能力 —— 谁的情绪日记谁写。

**同步 vs 异步的取舍（⚠️ 2026-09-20 重新结论：必须异步）**

> 🔴 **硬约束：前端 `request.js` 的 `timeout` 只有 5000（5 秒）**
> ```js
> const service = axios.create({ baseURL: '/api', timeout: 5000 })
> ```
> 而一次 AI 分析实测要 **5~15 秒**。所以：
> **按上面这份"同步执行"写完，用户点保存 → 前端 5 秒必然超时报错**（而日记其实已存、AI 还在跑，
> 用户以为没保存成功，会重复点 —— 这是最糟糕的一种"看起来坏了"）。

| | 同步 | 异步（**推荐**） |
|---|---|---|
| 表现 | 保存接口会多等几秒到十几秒 | 保存立刻返回，分析在后台跑 |
| 和前端 5s 超时 | ❌ **必然超时报错** | ✅ 不冲突 |
| 前端体验 | 打开详情结果已就绪 | 刚保存完打开详情可能还没有分析结果 |
| 改动量 | 0 | 启动类 `@EnableAsync`，方法加 `@Async` |

**结论：走异步。** 两种落地方式（二选一，都在第 9 章给了完整代码）：

| 方式 | 做法 | 适用 |
|---|---|---|
| A. `@Async` | `analyzeEmotionDiary` 加 `@Async`，调用点不变 | 最省事，任务表只当记账用（9.6 模式一 + 异步化） |
| B. 定时扫描 | 保存时**只入队**，`@Scheduled` 每 30 秒捡任务 | 要"失败自动重试"就选这个（9.6 模式二） |

⚠️ `@Async` 生效的两个前提（缺一个都还是同步，且不报错，最难查）：
1. 启动类（或配置类）加 `@EnableAsync`；
2. **必须跨类调用** —— 从 `EmotionDiaryService` 调 `EmotionDiaryAnalysisService`（两个 Bean）才生效；
   同一个类里 `this.analyzeEmotionDiary(...)` 这种自调用**不会**走代理，等于没加。

> 另一种权宜做法：把前端 `timeout` 调到 `30000`，同步方案就能跑。
> 但这只是把"失败"变成"转 15 秒圈"，**用户还是会等**，而且以后别处再加 AI 接口又要调一次。
> 所以更推荐后端异步，前端保持 5 秒。

>
> `saveOrUpdate` 返回的是**保存时手里那个实体实例（A）**；`analyzeEmotionDiary` 内部重新

> |---|---|---|
> | 新建（首次） | `builder()` 新建，AI 字段本来就是 null | **`null`** |
> | 修改（同一天再提交） | `selectOne` 读到行，里面是**上一次**的分析结果 | **上一次的旧结论** |
>

> 实际是上一版的结论，比 `null` 更容易骗过人（正文已经改严重了，返回的却是旧的低风险判断）。
> 而且 `updatedAt` 是新的、`aiAnalysisUpdatedAt` 是旧的，看着很像对的。

### 4.10 踩坑清单

| # | 坑 | 说明 |
|---|---|---|
| 1 | **`isNegative` 用 class 会序列化错** | 必须用 `record`，或加 `@JsonProperty("isNegative")`。这是最容易踩的一个 |
| 2 | **`riskLevel` 必须是整数** | 提示词要写"只能是整数 0、1、2、3"。AI 若返回字符串 `"2"`，Jackson 不一定能转 |
| 3 | **`riskLevel` 与 `isNegative` 会矛盾** | 比如 AI 返回 `riskLevel=0` 但 `isNegative=true`，前端会一边绿一边红。`normalize()` 已做强制对齐 |
| 4 | **`emotionScore` 语义** | 你前端是"越高越红"，所以这个分要表示"强烈 + 负面"，不是"开心程度" |
| 5 | **AI 调用别放事务里** | 一次调用几秒到十几秒，放 `@Transactional` 里会长时间占着数据库连接 |
| 6 | **分析失败不能连累保存** | `saveOrUpdate` 里必须 try-catch，日记先存下来 |
| 7 | **调用位置在 `insert()` 之后** | 否则 `getId()` 是 null |
| 8 | **24h 去重只对"新建"生效** | 判断依据是 `ai_analysis_updated_at`。**修改日记必须强制重算**——4.7 传的是 `exists` 而不是写死的 `false`，否则 24 小时内改了内容还会看到旧结论（见 4.7.1） |
| 9 | **空日记不要硬送 AI** | 正文和触发因素都为空时 `buildText` 返回 `""`，上层抛业务异常。别把「只有日期和评分」的日记送进去，AI 会编出随机结论 |
| 10 | **`ai_emotion_analysis` 是 text 不是 json** | 存什么都行；但 `consultation_session.last_emotion_analysis` 是 json 列，写入必须合法 |
| 11 | **`moodScore` 与 `emotionScore` 方向相反** | 前者是用户自评的心情（1 差 → 10 好），后者是 AI 的「强度+负面」分（0 好 → 100 需关注）。提示词里已写明，漏了 AI 会把「心情 9 分」当成「风险 9 级」 |
| 12 | **自评情绪会和正文打架** | 用户可能选了「开心」但正文写得很丧（样例数据里就有）。提示词已要求以正文为准，**别为了让用户看着舒服就放宽 `riskLevel`** |
| 13 | **Jackson 读 `{}` 不抛异常** | 它返回字段全 `null` 的 record，看着"解析成功"其实是个空壳。**缓存分支只写 try-catch 挡不住，必须再校验关键字段**（`primaryEmotion() != null`）。旧 Hutool 写入的缓存正是这种 |
| 14 | **改完必须清脏缓存** | 库里已存的旧格式 JSON 不会自己消失，不清就会一直命中"陈旧但新鲜"的坏缓存。两边各查一次（SQL 见下） |
| 15 | **Spring Boot 4 用的是 Jackson 3，包名变了** | 核心类从 `com.fasterxml.jackson.databind` 搬到了 **`tools.jackson.databind`**（注解包 `com.fasterxml.jackson.annotation` 不变）。写错包名启动即崩：`required a bean of type 'com.fasterxml.jackson.databind.ObjectMapper' that could not be found`。另外 Jackson 3 的 `JacksonException` 是**非受检**的，方法签名不用写 `throws` |
| 16 | **`open-ai` 那个 ChatClient 只能用来做对话** | 它挂了 `MessageChatMemoryAdvisor`，该顾问**强制**每次调用都带参数 `chat_memory_conversation_id`，否则抛 `conversationId cannot be null`。一次性分析必须用 **`analysis`** 这个不带记忆的 bean（见 4.11） |

### 4.11 两个 ChatClient：`open-ai`（带记忆，对话用）与 `analysis`（无记忆，一次性分析用）

**现象**：日记保存后控制台打印 `AI情绪分析失败，diaryId=30：conversationId cannot be null`
（被 4.7 的 try-catch 吃掉，所以接口照样返回 200，只有日志里有线索）。

**原因**：`config/ChatClientConfig.java` 里 `open-ai` 这个 bean 装了消息记忆顾问：

```java
.defaultAdvisors(MessageChatMemoryAdvisor.builder(chatMemory()).build())
```

该顾问在 `BaseChatMemoryAdvisor.getConversationId()` 里写死了：

```java
Object conversationId = context.get("chat_memory_conversation_id");
Assert.notNull(conversationId, "conversationId cannot be null");
```

（反编译 `spring-ai-client-chat-2.0.1` 实测确认。）所以**凡是走 `open-ai` 的调用都必须传这个参数**：
流式对话传了，日记分析、会话情绪分析都没传 → 必崩。

**为什么不能"随便补一个 conversationId"**：`MessageWindowChatMemory` 底下是
`InMemoryChatMemoryRepository`，本质是

```java
Map<String, List<Message>> chatMemoryStore;   // key = conversationId，只增不减
```

| 方案 | 后果 |
|---|---|
| 所有分析共用一个 key | 后一篇日记会看到前一篇的正文，AI 结论串味 |
| 每个日记一个 key（`diary_<id>`） | key 永不回收，长期运行内存单调上涨 |

日记分析本来就是「喂一段文本 → 出 JSON」的一次性请求，不需要多轮上下文。
**正确做法：给它一个不带记忆顾问的 ChatClient。**

**改动 1：`config/ChatClientConfig.java` 加一个 bean**（`open-ai` 原样不动）

```java
    /**
     * 一次性结构化分析专用（情绪日记分析、会话情绪分析）：不带 ChatMemory 顾问。
     */
    @Bean("analysis")
    public ChatClient analysisChatClient(OpenAiChatModel openAiChatModel) {
        return ChatClient.builder(openAiChatModel).build();
    }
```

**改动 2：两处注入换成 `analysis`**

| 文件 | 改什么 |
|---|---|
| `AiService/EmotionDiaryAnalysisService.java` | 构造器参数 `@Qualifier("open-ai")` → `@Qualifier("analysis")`（见 4.6） |
| `AiService/PsychologicalSupportService.java` | 新增 `@Qualifier("analysis")` 字段，`analyzeSessionEmotion()` 改用它；`streamPsychologicalChat()` **仍用 `open-ai`**，因为流式对话就是要记忆 |

**两个 bean 的职责边界**

| bean | 带记忆顾问 | 用途 | 要传 `chat_memory_conversation_id` 吗 |
|---|---|---|---|
| `open-ai` | 是 | 流式心理对话（多轮上下文） | 必须传 |
| `analysis` | 否 | 日记情绪分析、会话情绪分析（一次性出 JSON） | 不用传，传了也无害 |

> 顺带澄清一个容易担心的点：`.system(...)` 是**覆盖**默认 system，不是追加
> （`DefaultChatClientRequestSpec.system()` 直接 `putfield systemText`，javap 反编译确认无拼接逻辑）。
> 所以用 `analysis`（没有 defaultSystem）时，每次显式传
> `.system(PromptManage.DIARY_ANALYSIS_PROMPT)` 依旧单独生效，
> 不会把心理支持的角色设定混进情绪分析。

### 5.2 实现思路

统计类接口最容易写砸的地方是「查一堆数据回 Java 里算」。
正确做法是**让数据库做聚合**（`COUNT` / `AVG` / `GROUP BY`），Java 只负责组装。

本项目里两类手段混用：
- **简单计数**：直接用 MyBatis-Plus 的 `selectCount(new LambdaQueryWrapper<>())`，一行搞定。
- **分组统计 / 趋势**：自定义 `@Select` 写 SQL，返回 `List<Map<String, Object>>`。

#### 5.5.5 Service：`service/DataAnalyticsService.java`（新建，**替换 5.3④**）

核心是「**日期骨架 + 查表填值**」：先造出连续 7 天的 key，再用 SQL 结果去填，缺的天就是 0 / null。

```java
package com.lzc.mindaispringboot.service;

import com.baomidou.mybatisplus.core.conditions.query.LambdaQueryWrapper;
import com.lzc.mindaispringboot.mappper.ConsultationSessionMapper;
import com.lzc.mindaispringboot.mappper.EmotionDiaryMapper;
import com.lzc.mindaispringboot.mappper.UserMapper;
import com.lzc.mindaispringboot.response.DataAnalyticsVO;
import jakarta.annotation.Resource;
import org.springframework.stereotype.Service;

import java.time.LocalDate;
import java.time.format.DateTimeFormatter;
import java.util.ArrayList;
import java.util.HashMap;
import java.util.List;
import java.util.Map;

@Service
public class DataAnalyticsService {

    /** 趋势窗口天数（含今天） */
    private static final int DAYS = 7;
    private static final DateTimeFormatter FMT = DateTimeFormatter.ofPattern("yyyy-MM-dd");

    @Resource private UserMapper userMapper;
    @Resource private ConsultationSessionMapper consultationSessionMapper;
    @Resource private EmotionDiaryMapper emotionDiaryMapper;

    public DataAnalyticsVO overview() {
        LocalDate today = LocalDate.now();

        // ① 日期骨架：连续 7 天，保证前端 X 轴不断档
        List<String> days = new ArrayList<>();
        for (int i = DAYS - 1; i >= 0; i--) days.add(today.minusDays(i).format(FMT));

        // ② 三条日聚合结果转成 Map<date, row>，方便按骨架取值
        Map<String, Map<String, Object>> diaryDaily   = toMap(emotionDiaryMapper.selectDiaryDaily7d());
        Map<String, Map<String, Object>> sessionDaily = toMap(consultationSessionMapper.selectSessionDaily7d());
        Map<String, Map<String, Object>> newUserDaily = toMap(userMapper.selectNewUserDaily7d());
        Map<String, Map<String, Object>> activeDaily  = toMap(userMapper.selectActiveUserDaily7d());

        // ③ 按骨架组装三条趋势（缺的天补 0 / null）
        List<DataAnalyticsVO.EmotionTrendPoint> emotionTrend = new ArrayList<>();
        List<DataAnalyticsVO.DailySessionPoint> dailyTrend = new ArrayList<>();
        List<DataAnalyticsVO.UserActivityPoint> userActivity = new ArrayList<>();

        for (String day : days) {
            Map<String, Object> d = diaryDaily.get(day);
            Map<String, Object> s = sessionDaily.get(day);
            Map<String, Object> n = newUserDaily.get(day);
            Map<String, Object> a = activeDaily.get(day);

            emotionTrend.add(DataAnalyticsVO.EmotionTrendPoint.builder()
                    .date(day)
                    .avgMoodScore(toDouble(d == null ? null : d.get("avgMoodScore")))
                    .recordCount(toLong(d == null ? null : d.get("recordCount")))
                    .build());

            dailyTrend.add(DataAnalyticsVO.DailySessionPoint.builder()
                    .date(day)
                    .sessionCount(toLong(s == null ? null : s.get("sessionCount")))
                    .userCount(toLong(s == null ? null : s.get("userCount")))
                    .build());

            userActivity.add(DataAnalyticsVO.UserActivityPoint.builder()
                    .date(day)
                    .activeUsers(toLong(a == null ? null : a.get("activeUsers")))
                    .newUsers(toLong(n == null ? null : n.get("newUsers")))
                    .diaryUsers(toLong(d == null ? null : d.get("diaryUsers")))
                    .consultationUsers(toLong(s == null ? null : s.get("userCount")))  // 与会话用户数同源
                    .build());
        }

        // ④ 概览卡片
        String todayKey = today.format(FMT);
        long totalSessions = consultationSessionMapper.selectCount(new LambdaQueryWrapper<>());
        DataAnalyticsVO.SystemOverview overview = DataAnalyticsVO.SystemOverview.builder()
                .totalUsers(userMapper.selectCount(new LambdaQueryWrapper<>()))
                .activeUsers(userMapper.countActiveUsers7d())
                .totalDiaries(emotionDiaryMapper.selectCount(new LambdaQueryWrapper<>()))
                .todayNewDiaries(fromMap(diaryDaily, todayKey, "recordCount"))
                .totalSessions(totalSessions)
                .todayNewSessions(fromMap(sessionDaily, todayKey, "sessionCount"))
                .avgMoodScore(emotionDiaryMapper.selectAvgMood())
                .build();

        // ⑤ 咨询统计块（avgDurationMinutes 见 5.5.7，当前恒 0）
        DataAnalyticsVO.ConsultationStats stats = DataAnalyticsVO.ConsultationStats.builder()
                .totalSessions(totalSessions)
                .avgDurationMinutes(0L)
                .dailyTrend(dailyTrend)
                .build();

        return DataAnalyticsVO.builder()
                .systemOverview(overview)
                .emotionTrend(emotionTrend)
                .consultationStats(stats)
                .userActivity(userActivity)
                .build();
    }

    // ==================== 工具方法 ====================

    /** List<Map> → Map<date, Map> */
    private Map<String, Map<String, Object>> toMap(List<Map<String, Object>> rows) {
        Map<String, Map<String, Object>> map = new HashMap<>();
        for (Map<String, Object> row : rows) {
            Object date = row.get("date");
            if (date != null) map.put(String.valueOf(date), row);
        }
        return map;
    }

    private Long fromMap(Map<String, Map<String, Object>> daily, String day, String key) {
        Map<String, Object> row = daily.get(day);
        return row == null ? 0L : toLong(row.get(key));
    }

    /** 统一按 Number 处理：COUNT(*) 可能被驱动映射成 Long / BigInteger，强转会 ClassCastException */
    private static Long toLong(Object o) {
        return o == null ? 0L : ((Number) o).longValue();
    }

    private static Double toDouble(Object o) {
        return o == null ? null : ((Number) o).doubleValue();
    }
}
```

## 6. 退出登录

### 6.1 先理解：JWT 退出为什么麻烦

JWT 是**无状态**的——服务端不保存 token，只靠签名校验。这意味着：
**服务端没有任何"开关"能让一个已经发出去的 token 立刻失效。**

所以「退出登录」在 JWT 体系里的标准做法是 **黑名单**：

```
用户点退出 → 服务端把该 token 记进黑名单 → 之后每次请求先查黑名单
          → 命中就返回 401（哪怕签名有效、没过期）
```

### 6.2 代码

#### ① `util/TokenBlacklist.java`（新建）

```java
package com.lzc.mindaispringboot.util;

import com.auth0.jwt.JWT;
import com.auth0.jwt.interfaces.DecodedJWT;

import java.util.Date;
import java.util.Iterator;
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;

/**
 * token 黑名单（内存版）。
 *
 * 存 token → 过期时间戳。过期时间戳用来做自动清理：
 * 一个 token 过了有效期，本来也就验不过了，没必要永远留在内存里。
 */
public class TokenBlacklist {

    private static final Map<String, Long> BLACKLIST = new ConcurrentHashMap<>();

    /** token 无法解析过期时间时的兜底保留时长：24 小时 */
    private static final long DEFAULT_KEEP_MILLIS = 24 * 60 * 60 * 1000L;

    /** 加入黑名单 */
    public static void add(String token) {
        if (token == null || token.isBlank()) return;
        Long exp = extractExpiration(token);
        BLACKLIST.put(token, exp == null ? System.currentTimeMillis() + DEFAULT_KEEP_MILLIS : exp);
        // 顺手清一次过期的，避免内存无限增长
        cleanExpired();
    }

    /** 是否在黑名单中 */
    public static boolean contains(String token) {
        if (token == null || token.isBlank()) return false;
        Long exp = BLACKLIST.get(token);
        if (exp == null) return false;
        // 已过期的 token 本来也验不过，直接当不在黑名单，省一次判断
        if (exp < System.currentTimeMillis()) {
            BLACKLIST.remove(token);
            return false;
        }
        return true;
    }

    /** 清理已过期的记录 */
    public static void cleanExpired() {
        long now = System.currentTimeMillis();
        Iterator<Map.Entry<String, Long>> it = BLACKLIST.entrySet().iterator();
        while (it.hasNext()) {
            if (it.next().getValue() < now) it.remove();
        }
    }

    /**
     * 解析 token 的过期时间。
     * 这里只 decode 不 verify —— 目的只是拿到过期时间做内存清理，
     * 真正的合法性校验在 JwtTokenUtil.validateToken 里做。
     */
    private static Long extractExpiration(String token) {
        try {
            DecodedJWT jwt = JWT.decode(token);
            Date expiresAt = jwt.getExpiresAt();
            return expiresAt == null ? null : expiresAt.getTime();
        } catch (Exception e) {
            return null;
        }
    }
}
```

```java
    private StructOutPut.EmotionAnalysis normalize(StructOutPut.EmotionAnalysis r) {
        String primary = (r == null || r.primaryEmotion() == null) ? "平静" : r.primaryEmotion();

        int score = 50;
        if (r != null && r.emotionScore() != null) {
            score = Math.max(0, Math.min(100, r.emotionScore()));
        }

        int risk = 0;
        if (r != null && r.riskLevel() != null) {
            risk = Math.max(0, Math.min(3, r.riskLevel()));
        }

        Boolean negative = (r != null && r.isNegative() != null) ? r.isNegative() : (risk >= 2);
        if (risk >= 2) negative = true;
        if (risk == 0) negative = false;

        List<String> keywords = (r == null || r.keywords() == null) ? List.of() : r.keywords();
        List<String> improves  = (r == null || r.improvementSuggestions() == null)
                ? List.of() : r.improvementSuggestions();

        return new StructOutPut.EmotionAnalysis(
                primary,
                score,
                negative,
                risk,
                keywords,
                r == null || r.suggestion() == null ? "保持当下的节奏就好" : r.suggestion(),
                r == null || r.icon() == null ? "\uD83D\uDE42" : r.icon(),
                r == null || r.label() == null ? "calm" : r.label(),
                r == null || r.riskDescription() == null ? "情绪稳定" : r.riskDescription(),
                improves,
                System.currentTimeMillis()   // ← timestamp 由后端填
        );
    }
```

> 需要 import：`java.util.List`。
> `analyzeSessionEmotion` 那个方法**不用改**，它最后已经 `.entity(StructOutPut.EmotionAnalysis.class)`，
> 结构换了它自动跟着变。

### 7.6 缓存兼容：改造后旧数据怎么办

数据库里可能已经存了**旧格式的 JSON**（`{"overallMood":...,"emotions":...}`）。
用**新的 record 结构**去解析它时，新字段全为 `null`——前端就会收到一张全空的卡片。

所以 7.5.3 里加了 `readCache()`：解析异常、或解析出来是残缺对象，都返回 `null` 自动重新分析。
但为了让旧格式**当场失效**（不用等 24 小时），建议改完先清一次缓存。

先查有哪些是脏数据（`last_emotion_analysis` 里没有 `overallMood` 的就是坏数据）：

```sql
SELECT id, LEFT(last_emotion_analysis, 60) AS head, last_emotion_updated_at
  FROM consultation_session
 WHERE last_emotion_analysis IS NOT NULL
   AND last_emotion_analysis NOT LIKE '%overallMood%';
```

只清坏的那几条（推荐，好的缓存留着省 token）：

```sql
UPDATE consultation_session
   SET last_emotion_analysis = NULL,
       last_emotion_updated_at = NULL
 WHERE last_emotion_analysis IS NOT NULL
   AND last_emotion_analysis NOT LIKE '%overallMood%';
```

不想分辨就全清（反正会重新分析，只是多烧几次 token）：

```sql
UPDATE consultation_session
   SET last_emotion_analysis = NULL,
       last_emotion_updated_at = NULL;
```

> ⚠️ `consultation_session.last_emotion_analysis` 是 **`json`** 列，写入必须是合法 JSON，
> 否则 MySQL 直接报错（跟 `emotion_diary.ai_emotion_analysis` 的 `text` 列不一样）。

另外提醒：`JSONUtil` **根本处理不了 record**（实测见 4.4.1：序列化只吐出 `{"isNegative":false}`、
反序列化直接抛 `ConvertException`）。这段缓存读写必须用 Jackson：

```java
    @Resource
    private ObjectMapper objectMapper;   // 或 new ObjectMapper()

    private StructOutPut.EmotionAnalysis readCache(String json) {
        try {
            StructOutPut.EmotionAnalysis cached =
                    objectMapper.readValue(json, StructOutPut.EmotionAnalysis.class);
            return cached.overallMood() != null ? cached : null;   // "{}" 会被解析成全 null，得挡掉
        } catch (Exception e) {
            return null;
        }
    }
```

写入同理用的是 `objectMapper.writeValueAsString(analysis)`（7.5.3 的示例已经改好了）。

### 7.8 踩坑清单

| # | 坑 | 说明 |
|---|---|---|
| 1 | **`isNegative` 必须用 record** | 用 class + `@Data`，Jackson 可能序列化成 `"negative"`，前端读到 `undefined` |
| 2 | **`riskLevel` 必须是整数** | 前端 `riskTagMap[riskLevel]` 的 key 是数字；AI 若返回 `"1"`，对象匹配失败 → 显示「未知风险等级」 |
| 3 | **`emotionScore` 不要返回小数** | AI 偶尔返回 `20.0` 或 `"20"`，Jackson 转 Integer 可能报错。`normalize()` 已强转 int |
| 4 | **旧缓存要清** | 不改数据的话，`last_emotion_analysis` 里的旧格式 JSON 会被当成有效缓存返回空卡片 |
| 5 | **`json` 列必须合法** | `last_emotion_analysis` 是 json 类型，写入非法 JSON 直接报错 |
| 6 | **`timestamp` 不要交给 AI** | AI 不知道当前时间，会编一个。必须由后端 `System.currentTimeMillis()` 填 |
| 7 | **`icon` 别限制成单字节字符** | emoji 是代理对（surrogate pair），MySQL 需 `utf8mb4`——你的库已经是，没问题 |
| 8 | **`Result` 加了字段会不会影响别的接口** | 不会，是纯新增 key，前端不读就无影响 |
| 9 | **24h 缓存会让调试困惑** | 改完 prompt 后想立刻看效果，先执行 7.6 那条 SQL 清缓存 |
| 10 | **`JSONUtil` 处理 record 必炸** | Hutool 5.8.25 不支持 record：序列化丢字段、反序列化抛 `ConvertException`。**全程用 `ObjectMapper`**（4.4.1 有实测对照表） |

#### 7.9.2 调用时机：会打两次

```js
onmessage: (event) => {
  if (event.event === 'done') { isAiTyping=false; ctrl.abort(); loadSessionEmotion(...); return }
  ...
}
onclose: () => { loadSessionEmotion(...) }
```

后端确实会发 `event: done`（`PsychologicalChatController` 里 `concatWith` 追加的），
且**在 `doOnComplete` 保存 AI 消息之后**才发——所以分析时能读到最后一轮回复，时序是安全的 ✅。

但 `ctrl.abort()` 关闭连接后 `onclose` 又会触发一次 → **同一个 emotion 接口被并发打两次**。
两次都Miss缓存 = **两次 AI 调用，双倍 token**。

改法（前端）：

```js
let emotionRequested = false          // ← 新增标志位

const loadSessionEmotion = async (sessionId) => {
  if (emotionRequested) return        // ← 同一次流只拉一次
  emotionRequested = true
  const id = sessionId.toString().startsWith('session_') ? sessionId : `session_${sessionId}`
  const res = await getSeeionEmotion(id)
  currentEmotion.value = res
}

// 发新一轮前重置
const sendMessage = () => { emotionRequested = false; ... }
```

#### 7.9.3 ⚠️ 24h 缓存会让情绪花园「当天不刷新」

这是后端的问题。现有 `getEmotionAnalysis` 的缓存判据**只看时间**：

```java
if (lastEmotionAnalysis != null && lastEmotionUpdatedAt.isAfter(now.minusHours(24))) return cached;
```

**具体会怎么坏**（用一天的真实时间线走一遍）：

| 时间 | 用户动作 | 后端行为 | 用户看到 |
|---|---|---|---|
| 上午 09:00 | 聊完 8 条 | 缓存 Miss → 调 AI → 存下结果，记下"分析时 8 条" | 情绪花园正常 |
| 下午 15:00 | **又聊了 20 条**（共 28 条） | 看到"6 小时前分析过 < 24 小时" → **返回上午那份缓存** | ❌ **情绪花园还是上午的，跟刚聊的内容完全无关** |

即：**只要用户一天内还在聊，情绪花园就整天冻在第一次的结果上** —— 这跟"实时反馈"的体感直接冲突。

**「双判据」是什么意思**：把"要不要用缓存"从**1 个条件**改成**2 个条件同时满足**：

| 判据 | 作用 |
|---|---|
| ① 时间：距上次分析 < 24 小时 | 防止短时间内反复调用（比如刷新页面）烧 token |
| ② **消息条数：这次条数 == 上次分析时记下的条数** | 确认**内容没变**，缓存才有意义 |

**只要两条都满足才用缓存；条数一旦变了（= 用户又聊了），立刻重新分析。**
为什么用"条数"当第二条判据？因为「用户有没有说新话」最直接的证据就是**消息多了**：

- 条数没变 → 没发新消息 → 内容没变 → 缓存有效 ✔
- 条数变多 → 又聊了 → **必须重算** ✔

改动很小（**这就是"约 5 行"的意思**）：加一列 + 查一次 count + 判断里加 2 行 + 写回时记 1 行。

```java
    // ① 查当前消息条数（用项目已有的 getMessageCount，不要写 countBySession —— 那个方法不存在）
    Integer currentCount = consultationMessageService.getMessageCount(dbsession);

    // ② 两个判据都满足才用缓存
    if (session.getLastEmotionAnalysis() != null
            && session.getLastEmotionUpdatedAt() != null
            && session.getLastEmotionUpdatedAt().isAfter(LocalDateTime.now().minusHours(24))
            && Objects.equals(session.getLastEmotionMsgCount(), currentCount)   // ← 消息没变才用缓存
    ){
        StructOutPut.EmotionAnalysis cached = readCache(session.getLastEmotionAnalysis());
        if (cached != null) return cached;
    }

    // ③ 重新分析，并把"这次是几条消息时分析的"一起记下来
    StructOutPut.EmotionAnalysis analysis = normalize(analyzeSessionEmotion(dbsession));
    session.setLastEmotionAnalysis(objectMapper.writeValueAsString(analysis));   // ⚠️ 别用 JSONUtil
    session.setLastEmotionUpdatedAt(LocalDateTime.now());
    session.setLastEmotionMsgCount(currentCount);                // ← 记下来
    consultationSessionService.updateById(session);
```

> ⚠️ 比较用 `Objects.equals(...)` 而**不是** `==`：`getMessageCount` 和字段都是 `Integer`（包装类型），
> `Integer == Integer` 在超出 -128~127 时是**引用比较**，会算出"不相等"导致缓存永远 Miss（或反过来永远命中）。
> 需要 `import java.util.Objects;`。（两边都 `intValue()` 也行。）

需要在 `consultation_session` 表加一列：

```sql
ALTER TABLE consultation_session
  ADD COLUMN last_emotion_msg_count int DEFAULT 0 COMMENT '上次情绪分析时的消息条数'
  AFTER last_emotion_updated_at;
```

实体 `ConsultationSession` 同步加字段（MyBatis-Plus 默认开启驼峰转下划线，`lastEmotionMsgCount` → `last_emotion_msg_count`）：

```java
    // 上次情绪分析时的消息条数（用于判断是否需要重新分析）
    @TableField("last_emotion_msg_count")
    private Integer lastEmotionMsgCount;
```

> 这样既保留了「24 小时内不重复烧 token」的保护，又能保证**每多一轮对话就刷新一次**情绪花园。

#### 7.9.4 这段前端代码里另外 3 个问题

| # | 位置 | 问题 | 改法 |
|---|---|---|---|
| 1 | `const ctrl = new AbortController()` | **模块级单例**。`done` 里 `ctrl.abort()` 之后这个 signal 永久处于已中止状态，**第二次发消息起 SSE 很可能根本发不出去**（既没请求也没报错，输入框一直卡在「正在思考中」） | 改成每次请求内部新建：`const abort = () => {}; const ctrl = new AbortController()` 放进 `startAIResponse` 里，或每次赋值 `ctrl = new AbortController()` |

### 8.2 逐条说明

#### 8.2.1 路径对不上（先确认前端到底打的是哪条）

`EmotionDiaryController` 现在是：

```java
@RequestMapping("/api/emotion-diary")
@GetMapping                                // ← 没有子路径 → 实际路径是 /api/emotion-diary
public Result<Page<EmotionDiary>> adminPage(...)
```

而前端打的是 `/emotion-diary/admin/page`（前面再拼 `/api` 前缀）→ 完整路径 `/api/emotion-diary/admin/page`，
**当前后端没有这个映射，理论上应该 404**。

你能拿到数据，说明以下两种情况之一：

- 你本地跑的后端和这个工作区不一致（比如是参考项目/另一台机器）；
- 前端的 `baseURL` 不是 `/api`，或者网关/代理做了转发。

**不管哪种，路径按 `/admin/page` 挂上即可** —— 既然不再分页，就没必要再兼容原来那个裸路径：

```java
@GetMapping("/admin/page")
```

完整路径就是 `/api/emotion-diary/admin/page`，和前端一致。

> 想保留旧入口的话写 `@GetMapping({"", "/admin/page"})` 也行（两个路径返回同一个数组）。
> 但多一个入口以后容易忘，**没特殊需求就别留**。

#### 8.2.2 缺的 6 个字段怎么来的

这 6 个字段**数据库里都没有**，全是"算出来"或"联表带出来"的展示字段：

| 字段 | 来源 | 算法 |
|---|---|---|
| `username` | `user.username` | 按 `user_id` 关联 |
| `nickname` | `user.nickname` | 按 `user_id` 关联（可以为 null） |
| `diaryContentPreview` | `diary_content` | 取前 50 字，超长补 `…` |
| `contentLength` | `diary_content` | `content == null ? 0 : content.length()` |
| `hasAiEmotionAnalysis` | `ai_emotion_analysis` | `StringUtils.hasText(...)` |
| `aiAnalysisStatus` | 同上 | 有值 → `COMPLETED`，无值 → `PENDING` |

所以正确做法是**新建一个 VO**，不要往 `EmotionDiary` 实体上塞字段——实体加了 `@TableField(exist = false)` 会让用户端保存/详情接口也多出这些字段，污染其他接口。

#### 8.2.3 排序：现在是乱的（其实是主键升序）

你这份响应是 `1806, 1805, 1804, 1802, 1798`，明显**新的在前**。
但 `adminPage` 里一行 `orderBy` 都没有，靠 InnoDB 主键顺序返回，管理端看着就是"老的在前"。

加一行：

```java
qw.orderByDesc(EmotionDiary::getCreatedAt).orderByDesc(EmotionDiary::getId);
```

> 为什么两个都用：`createdAt` 精确到秒，同一秒写多条时会并列，靠 `id` 兜底保证顺序稳定。

#### 8.2.4 外层 `success` / `message`

你这份响应外层是：

```json
{ "code":"200", "msg":"操作成功", "data":{...}, "message":"操作成功", "success":true }
```

比现在的 `Result` 多了 `message` 和 `success`。改造代码在 **7.5.4** 已经写好了（`Result` 加两个字段），
这一章和它是同一件事：**只要前端有地方读 `res.success` 或 `res.message`，7.5.4 就必须做**。

#### 8.2.5 `null` 字段被省略（可选）

#### ② 改 `service/EmotionDiaryService.java`：`adminList`（**返回 List，不分页**）+ 补用户名 + 加倒序

```java
import com.lzc.mindaispringboot.entity.User;
import com.lzc.mindaispringboot.mappper.UserMapper;
import com.lzc.mindaispringboot.response.EmotionDiaryAdminVO;
import java.util.*;
import java.util.stream.Collectors;

/** 单次最多返回条数。返回 List 时必须有硬上限，否则全站日记会被一次性拉出来（放类顶部常量区） */
private static final int MAX_ROWS = 500;

@Resource
private UserMapper userMapper;          // ← 新增注入

/**
 * 管理端：情绪日志列表（**不分页**，直接返回 VO 列表）
 * 前端用滚动条展示，不需要页码。
 */
public List<EmotionDiaryAdminVO> adminList(EmotionDiaryAdminPageQuery query) {

    // ① 条件 + 排序（全都在数据库做，Java 不筛）
    LambdaQueryWrapper<EmotionDiary> qw = new LambdaQueryWrapper<>();
    if (query.getUserId() != null)       qw.eq(EmotionDiary::getUserId, query.getUserId());
    if (query.getStartDate() != null)    qw.ge(EmotionDiary::getDiaryDate, query.getStartDate());
    if (query.getEndDate() != null)      qw.le(EmotionDiary::getDiaryDate, query.getEndDate());
    if (query.getMinMoodScore() != null) qw.ge(EmotionDiary::getMoodScore, query.getMinMoodScore());
    if (query.getMaxMoodScore() != null) qw.le(EmotionDiary::getMoodScore, query.getMaxMoodScore());
    // 倒序：最新的在前；同一秒用 id 兜底，保证顺序稳定
    qw.orderByDesc(EmotionDiary::getCreatedAt).orderByDesc(EmotionDiary::getId);
    // ⚠️ 硬上限：MAX_ROWS 是常量，拼接无注入风险
    qw.last("LIMIT " + MAX_ROWS);

    // ② 查出实体
    List<EmotionDiary> list = emotionDiaryMapper.selectList(qw);
    if (list.isEmpty()) return List.of();     // 空就早返回（顺带避开 IN () 的坑）

    // ③ 批量补用户名：一条 select ... in (...)，避免 N+1
    Set<Long> userIds = list.stream()
            .map(EmotionDiary::getUserId)
            .filter(Objects::nonNull)
            .collect(Collectors.toSet());
    Map<Long, User> userMap = Collections.emptyMap();
    if (!userIds.isEmpty()) {
        userMap = userMapper.selectByIds(userIds).stream()
                .collect(Collectors.toMap(User::getId, u -> u, (a, b) -> a));
    }

    // ④ 实体 → VO
    Map<Long, User> finalUserMap = userMap;
    return list.stream()
            .map(d -> EmotionDiaryAdminVO.from(d, finalUserMap.get(d.getUserId())))
            .toList();
}
```

|---|---|---|
| 返回类型 | `Page<EmotionDiaryAdminVO>` | **`List<EmotionDiaryAdminVO>`** |
| 查全量 | `selectPage(new Page<>(...), qw)` | **`selectList(qw)`** |
| 取数据 | `page.getRecords()` | **`list`** |

> 但记住这条：以后别的分页接口要用 `convert` 时，得自己 `new Page<>(current,size,total)` + `setRecords(...)`。

### 8.7 踩坑清单

| 坑 | 后果 | 怎么避 |
|---|---|---|
| **返回 List 却忘了加 `LIMIT`** | 全站日记一次全查出来，数据量上来后首屏卡好几秒、响应体几十 MB | `qw.last("LIMIT " + MAX_ROWS)`（`MAX_ROWS` 是常量，无注入风险） |
| 前端还按 `const { records } = await ...` 解构 | `records` 是 `undefined` → 表格直接空/报错 | 改成 `const list = await ...`，见 8.5 |
| 返回数组后还留着 `<el-pagination>` | 页码点了没反应（`total` 也不存在了） | 删掉分页组件，改用 `el-table` 的 `height` 出滚动条 |
| `selectByIds` / `selectBatchIds` 传空集合 | 拼出 `IN ()`，MySQL 报语法错误 | 先判空：`if (!userIds.isEmpty())`（或像 8.3② 那样查不到就早返回） |
| `Collectors.toMap` 重复 key | `IllegalStateException: Duplicate key` | 第三个参数写 `(a, b) -> a` |
| 把 6 个展示字段加进 `EmotionDiary` 实体 | 用户端保存/详情接口也跟着多字段，且 MyBatis-Plus 可能拿去拼 SQL | 只加在 VO 上 |
| 全局配 `non_null` | 其他接口的 `null` 全没了，前端判空逻辑连锁出问题 | 只在 VO 上加 `@JsonInclude` |
| `Boolean hasAiEmotionAnalysis` | Lombok 生成 `getHasAiEmotionAnalysis()` → JSON key 正好是 `hasAiEmotionAnalysis` ✅ | 用包装类型 `Boolean`，别用 `boolean`（`boolean` 生成 `isHas...`，某些序列化器会多一个字段） |
| 排序方向写错 | `orderByAsc(createdAt)` 会变成"最旧的在前"，跟注释相反 | 两个都写 `OrderByDesc`：`createdAt` + `id` |
| （备查）`page.convert()` 的返回类型 | 分页版才会遇到：报「不兼容的类型: IPage<R> 与 Page<...> 不一致」 | 本接口已不用 `Page`；以后别处要用 `convert`，就自己 `new Page<>(current,size,total)` + `setRecords(...)`，或把签名改成 `IPage` |
| 只按 `diaryDate` 排序 | 同一天多条顺序不稳定 | `createdAt` + `id` 双字段，且**方向要一致**（都要 `Desc` 才是"最新在前"） |

## 9. 日记 AI 分析的两表联动（`ai_analysis_task` + `emotion_diary`）

> 这一章解决的是：**用户端每创建一条日记，后端就要产生一次 AI 分析，并且这次分析要作为一条任务被记录**。
> 第 4 章只写了「怎么调 AI」（`EmotionDiaryAnalysisService`），**没有写任务表**——而你的 DDL 里 `ai_analysis_task` 是一张完整的任务表。
> **这一章就是把第 4 章套进任务表的壳里。**

### 9.1 从 DDL 能读出的设计意图

| 字段 / 约束 | 说明什么 |
|---|---|
| `diary_id` **NOT NULL** + `FK → emotion_diary(id) ON DELETE CASCADE` | 一条日记对应一条任务，**删日记自动删任务** |
| `status` 四态 `PENDING / PROCESSING / COMPLETED / FAILED` | 这是**异步任务**设计（同步根本不需要 PROCESSING） |
| `task_type` `AUTO / MANUAL / ADMIN / BATCH` | 用户端保存日记 = `AUTO`；管理端点按钮 = `ADMIN`；补数据脚本 = `BATCH` |
| `priority` 1~4 | 管理端手动触发的任务可以插队 |
| `retry_count` / `max_retry_count` | 失败可重试，`retry_count < max` 时还能再捡起来 |
| `started_at` / `completed_at` / `error_message` | 要能回答「这条为什么没分析出来」 |

**结论：第 4 章保留，本章是它的外层。** 关系是：

```
第 4 章 = 怎么问 AI（Prompt、record、normalize、兜底）
第 9 章 = 这次问 AI 要留痕（任务行、状态流转、失败原因）
```

### 9.2 一次「用户创建日记」到底发生什么

```
用户端 POST /api/emotion-diary  (saveOrUpdate)
   │
   ├─① 写 emotion_diary（已实现：同一天幂等，user_date_unique）
   │
   ├─② 插一条 ai_analysis_task：status=PENDING, task_type=AUTO,
   │      diary_id=日记id, user_id, priority=2, retry_count=0, max_retry_count=3
   │
   ├─③ 执行分析（第 4 章的 EmotionDiaryAnalysisService.analyzeEmotionDiary）
   │      开始前 → status=PROCESSING, started_at=now
   │
   ├─④ 成功 → diary.ai_emotion_analysis=<11字段JSON>、ai_analysis_updated_at=now
   │         task.status=COMPLETED, completed_at=now, error_message=null
   │
   └─⑤ 失败 → task.status=FAILED, error_message=<异常摘要>,
                 retry_count+1（< max_retry_count 时可被重新捡起）
```

**多条日记 = 多条任务**：因为 `emotion_diary` 有唯一键 `(user_id, diary_date)`，
一个用户**同一天只有一条日记**，所以「一个用户多条日记」实际是**跨日期多条**，每条各对应一条任务 ✔

> ⚠️ **2026-09-20 补充：上面的 ②~⑤ 发生在"哪里"，取决用哪个模式。**
>
> | 模式 | ② 入队 | ③④⑤ 执行 / 记账 |
> |---|---|---|
> | 模式一（同步） | 保存请求里 | **同一个保存请求里**（❌ 前端 5s 超时会报错，**不用**） |
> | 模式二（异步扫描，**推荐**） | 保存请求里（只做这一步） | 后台 `@Scheduled` 每 30 秒捡任务时 |
> | 模式三（`@Async` 折中） | 保存请求里 | 后台线程（记账要一起搬进异步方法，见 9.6 末尾） |
>
> 也就是说：**"保存日记"这个动作只保证 ①② 完成**（日记已存 + 任务已入队），
> 用户点完保存立刻拿到响应；分析结果由 ③④⑤ 稍后写回。
> 前端打开详情时若还没有结果，就按 `hasAiEmotionAnalysis` / `aiAnalysisStatus` 显示「分析中」。

```java
import com.baomidou.mybatisplus.core.mapper.BaseMapper;
import com.lzc.mindaispringboot.entity.AiAnalysisTask;
import org.apache.ibatis.annotations.Mapper;
import org.apache.ibatis.annotations.Select;

import java.util.Map;

@Mapper

    @Select("SELECT status, COUNT(*) AS cnt FROM ai_analysis_task GROUP BY status")

    /** 待处理任务（异步模式用）：优先级高的先捡，同优先级按入队顺序 */
    @Select("SELECT * FROM ai_analysis_task WHERE status = 'PENDING' " +

    @Update("UPDATE ai_analysis_task SET status = 'PROCESSING', started_at = NOW(), updated_at = NOW() " +

                    @org.apache.ibatis.annotations.Param("msg") String msg);
```

### 9.5 Service：`AiService/AnalysisTaskService.java`（新建）

只做任务的生命周期，**不碰 AI**（AI 还是第 4 章的 `EmotionDiaryAnalysisService`）：

```java
package com.lzc.mindaispringboot.AiService;

import com.lzc.mindaispringboot.entity.AiAnalysisTask;
import com.lzc.mindaispringboot.mappper.AiAnalysisTaskMapper;
import jakarta.annotation.Resource;
import org.springframework.stereotype.Service;

import java.time.LocalDateTime;
import java.util.List;

@Service
public class AnalysisTaskService {

    @Resource
    private AiAnalysisTaskMapper aiAnalysisTaskMapper;

    /** ① 入队：每条日记一条任务 */
    public AiAnalysisTask createPending(Long diaryId, Long userId, String taskType) {
        AiAnalysisTask task = AiAnalysisTask.builder()
                .diaryId(diaryId)
                .userId(userId)
                .status(AiAnalysisTask.ST_PENDING)
                .taskType(taskType)
                .priority(2)
                .retryCount(0)
                .maxRetryCount(3)
                .createdAt(LocalDateTime.now())
                .updatedAt(LocalDateTime.now())
                .build();
        aiAnalysisTaskMapper.insert(task);
        return task;
    }

    /** ② 抢任务（异步模式用），返回 1 = 抢到 */
    public boolean markProcessing(Long taskId) {
        return aiAnalysisTaskMapper.markProcessing(taskId) == 1;
    }

    /** ③ 成功 */
    public void markCompleted(Long taskId) {
        AiAnalysisTask task = new AiAnalysisTask();
        task.setId(taskId);
        task.setStatus(AiAnalysisTask.ST_COMPLETED);
        task.setCompletedAt(LocalDateTime.now());
        task.setUpdatedAt(LocalDateTime.now());
        aiAnalysisTaskMapper.updateById(task);   // 只更新非 null 字段
    }

    /** ④ 失败：未超上限退回 PENDING，超了标记 FAILED */
    public void markFailed(Long taskId, String errorMessage) {
        String msg = errorMessage == null ? "未知错误"
                : errorMessage.substring(0, Math.min(errorMessage.length(), 1000));  // 别超 text 列
        aiAnalysisTaskMapper.retryOrFail(taskId, msg);
    }

    /** 异步模式用：捞一批待处理任务 */
    public List<AiAnalysisTask> pickPending(int limit) {
        return aiAnalysisTaskMapper.pickPendingTasks(limit);
    }
}
```

> `updateById` 用的是 MyBatis-Plus 默认策略：**只更新非 null 字段**，所以 `markCompleted` 只塞状态和时间是对的。
> 如果哪天在 yml 里配了 `update-strategy: not_null` 之外的值，这里要改成 `UpdateWrapper`。

### 9.6 接进 `EmotionDiaryService.saveOrUpdate`

**替换掉第 4.7 节写的调用代码**。分两种模式。

> 🔴 **2026-09-20 修正：直接做模式二。**
> 原因见 **4.7 的「同步 vs 异步的取舍」**：前端 `request.js` 的 `timeout` 只有 **5 秒**，
> 而一次 AI 分析要 5~15 秒 —— **模式一（同步）会让用户每次保存日记都超时报错**。
> 模式一保留在下面只是为了讲清"任务记账"的思路，实操请直接用模式二。

#### 模式一：同步执行 + 记录任务（❌ 与前端 5s 超时冲突，仅作参考）

保存接口会多等几秒（AI 调用时间），代码最简单、日志最清楚：

```java
    @Resource
    private AnalysisTaskService analysisTaskService;
    @Resource
    private EmotionDiaryAnalysisService emotionDiaryAnalysisService;

    /** 用户端：按 用户+日期 幂等创建或更新 */
    public EmotionDiary saveOrUpdate(Long userId, EmotionDiarySaveDTO dto) {
        // ... 前面查/插入/更新的逻辑保持不变 ...
        // 注意：插入分支末尾的 emotionDiaryMapper.insert(emotionDiary) 一定要在下面之前

        // 新增：写日记之后产生一次 AI 分析任务
        // exists 就是 4.7 改动 1 里那个变量：false=新建走缓存规则，true=修改强制重算
        if (emotionDiary.getId() != null) {
            runAnalysisTask(emotionDiary, exists);
        }
        return emotionDiary;
    }

    /** 一次分析 = 一条任务：入队 → 执行 → 记账。AI 出错不能影响日记保存 */
    private void runAnalysisTask(EmotionDiary diary, boolean force) {
        AiAnalysisTask task = null;
        try {
            task = analysisTaskService.createPending(
                    diary.getId(), diary.getUserId(), AiAnalysisTask.TYPE_AUTO);
            analysisTaskService.markProcessing(task.getId());   // 同步模式下立刻进入 PROCESSING
            // force=false：24 小时内分析过就复用缓存；force=true：内容改过，强制重算
            emotionDiaryAnalysisService.analyzeEmotionDiary(diary.getId(), force);
            analysisTaskService.markCompleted(task.getId());
        } catch (Exception e) {
            // 关键：吞掉异常，日记已经保存成功了，不能因为 AI 失败让用户看到 500
            if (task != null) {
                analysisTaskService.markFailed(task.getId(), e.getMessage());
            }
            log.warn("日记 AI 分析失败，diaryId={}", diary.getId(), e);
        }
    }
```

> ⚠️ **两个容易踩的点**
> ① `analyzeEmotionDiary` 自己也要 try-catch（第 4.6 节已经写了），这里再包一层是双保险；
> ② **不要**给 `saveOrUpdate` 加 `@Transactional` 后又让 AI 异常往外抛——那会把日记一起回滚。
> 这也是「先插任务、再执行、失败改状态」这个顺序的意义：任务行本身就是记账凭据。

#### 模式二：异步 + 定时扫描（正式版，模式一跑通后再升级）

三步改造：

```java
// ① 启动类加 @EnableAsync（如果你想用 @Async）

// ② saveOrUpdate 里只入队，不等结果
    AiAnalysisTask task = analysisTaskService.createPending(
            diary.getId(), diary.getUserId(), AiAnalysisTask.TYPE_AUTO);
    // 不在这里调 AI，交给下面的定时任务

// ③ 新增定时扫描：每 30 秒捞一批待处理任务
@Component
public class AnalysisTaskScheduler {

    @Resource private AnalysisTaskService taskService;
    @Resource private AiAnalysisTaskMapper taskMapper;
    @Resource private EmotionDiaryMapper emotionDiaryMapper;
    @Resource private EmotionDiaryAnalysisService analysisService;

    @Scheduled(fixedDelay = 30_000)
    public void scan() {
        for (AiAnalysisTask task : taskService.pickPending(20)) {
            if (!taskService.markProcessing(task.getId())) continue;   // 抢不到就跳过（多实例安全）
            try {
                EmotionDiary diary = emotionDiaryMapper.selectById(task.getDiaryId());
                if (diary == null) {          // 日记被删了（FK 级联其实会删任务，这里是兜底）
                    taskService.markCompleted(task.getId());
                    continue;
                }
                // 定时扫描统一传 false：任务重复入队时直接吃缓存，不重复烧 token
                analysisService.analyzeEmotionDiary(diary.getId(), false);
                taskService.markCompleted(task.getId());
            } catch (Exception e) {
                taskService.markFailed(task.getId(), e.getMessage());
            }
        }
    }
}
```

启动类同时要加 `@EnableScheduling`。

**模式一 vs 模式二 vs 折中方案**

| | 模式一（同步记账） | **模式三：模式一 + `@Async`（折中，改动最小）** | 模式二（异步扫描） |
|---|---|---|---|
| 保存接口耗时 | 多几秒~十几秒 | **立刻返回** | 立刻返回 |
| 与前端 5s 超时 | ❌ **必然超时报错** | ✅ 不冲突 | ✅ 不冲突 |
| 管理端能否看到 PROCESSING | 只在执行的一瞬间 | 很短（执行期） | 能稳定看到 |
| 失败能否自动重试 | 不能（只标 FAILED） | 不能（只标 FAILED） | ✅ 能（`retry_count < max` 自动退回 PENDING） |
| 新增代码 | ~40 行 | 上面那段 + 1 个 `@Async` + 1 个 `@EnableAsync` | ~90 行 + 启动类 2 个注解 |
| 风险 | AI 慢会把保存请求拖住 | 应用重启时正在跑的任务会丢（留 PROCESSING 不动） | 定时任务没起来就一直 PENDING |

**模式三怎么做**（就是模式一的代码，加两个注解）：

```java
// ① 启动类（或任意 @Configuration 类）加：
@EnableAsync

// ② EmotionDiaryAnalysisService.analyzeEmotionDiary 加 @Async，并把返回值改成 void
//    ⚠️ 必须跨类调用才生效（EmotionDiaryService → EmotionDiaryAnalysisService 是两个 Bean，OK）
@Async
public void analyzeEmotionDiary(Long diaryId, boolean force) { ... }
```

> 但注意：模式三下 `runAnalysisTask` 里 **`markProcessing` → `analyzeEmotionDiary` → `markCompleted` 的时序会乱**
> （`@Async` 方法立刻返回，`markCompleted` 会在 AI 还没跑完时就执行）。
> 所以模式三的写法是：**把三个动作都搬进 `analyzeEmotionDiary` 内部**，或者**直接用模式二**。
> 综合看：**想最省事选模式二**（逻辑最干净、还有自动重试），**想改动最小选模式三但要把记账一起搬进去**。
> 总之 —— **不要用模式一**。

### 9.9 踩坑清单

| 坑 | 后果 | 怎么避 |
|---|---|---|
| 同一天重复提交时又插一条任务 | 任务表按提交次数膨胀（不是按日记数） | 先查该 diaryId 有没有 `PENDING`/`PROCESSING` 任务，有就跳过 |
| 给 `saveOrUpdate` 加了 `@Transactional` 且 AI 异常外抛 | **日记一起回滚**，用户以为没保存成功 | AI 调用必须被 try-catch 吞掉（9.6 已包） |
| `task.getId()` 在 `insert` 前取 | 拿到 null → 后续更新全失效 | 自增 id 是 insert 之后才回填的 |
| `error_message` 直接塞完整堆栈 | 超过 text 也算长，日志难读 | 截断到 1000 字符（9.5 已做） |
| 忘了 `@EnableScheduling` | 模式二的任务永远 PENDING | 启动类注解别忘了 |
| 定时任务里不抢锁直接处理 | 多实例部署时同一条任务被两个节点跑 | 用 `markProcessing` 的乐观锁（返回 1 才算抢到） |
| `pickPendingTasks` 没索引 | 任务多了之后每 30 秒全表扫 | 加 `idx_status_priority` 索引 |
| 删用户/日记时期望任务保留 | 被 `ON DELETE CASCADE` 一起删了 | 这是 DDL 的设计，不是 bug；要留档就先改约束 |

## 附录 A：建议顺手修的 4 处技术债

这些不影响上面 6 个接口的功能，但**越早修越好**，尤其是 A.1。

### A.1 `JwtTokenUtil` 不读 yaml 配置（高优先）

**问题**：`application.yml` 配了 `header: Authorization` + `token-prefix: "Bearer "`，
但 `extractTokenFromRequest` 写死读 `token` 头，这两个配置**完全是摆设**。
前端如果按标准写法发 `Authorization: Bearer xxx`，会**全部 401**。

**改法**（`util/JwtTokenUtil.java`）：

```java
    public static String extractTokenFromRequest(HttpServletRequest request){
        if (request == null) return null;
        JwtConfig jwtConfig = getJwtConfig();

        // 优先读配置的请求头（Authorization）
        String header = request.getHeader(jwtConfig.getHeader());
        if (StringUtils.hasText(header)) {
            // 去掉前缀 "Bearer "
            String prefix = jwtConfig.getTokenPrefix();
            if (prefix != null && !prefix.isEmpty() && header.startsWith(prefix)) {
                header = header.substring(prefix.length()).trim();
            }
            if (StringUtils.hasText(header)) return header;
        }
        // 兼容旧的 token 头（老前端还在用，保留一段时间）
        String legacy = request.getHeader("token");
        return StringUtils.hasText(legacy) ? legacy : null;
    }
```

这样两种写法都能用，**前端不用改**，等你确认统一后可以把兼容分支删掉。
（需要先确认 `JwtConfig` 里有 `getHeader()` / `getTokenPrefix()` 这两个 getter，没有就补上。）

### A.4 会话分页参数名：一个接口，两端传的名不一样（高优先，2026-09-20 修正）

**这条比原来记的更严重**：不只是 `pargeNum` 拼错，而是**同一个 `/sessions` 接口，用户端和管理端发的页码参数名根本不同**。

```java
// 现状：common/Dto/SessionPageQuery.java
private Long pargeNum = 1L;        // ← 拼错（应为 pageNum），且两端都不是这个名字
```

| 端 | 前端代码 | 实际发出 | 后端能接住吗 |
|---|---|---|---|
| 用户端 | `getSessionList({ pageNum: 1, pageSize: 10 })`（`Consultation.vue`） | `?pageNum=1` | ❌ 字段叫 `pargeNum` |
| 管理端 | `pagination = { currentPage: 1, pageSize: 10 }` → `getConsultationPage(pagination)`（`Consultations.vue`） | `?currentPage=1` | ❌ 字段叫 `pargeNum` |

**后果：两端都绑不上，页码永远用默认值 1 → 点第 2 页拿到的还是第 1 页。**
（`pageSize` 两端名字都对得上，所以"每页 10 条"看起来正常，最容易忽略。）

改法：**删掉 `pargeNum`，同时接住两个名字**（完整 DTO 见 **2.5.3**）：

```java
public class SessionPageQuery {
    private Long currentPage;      // 管理端
    private Long pageNum;          // 用户端
    private Long pageSize = 10L;
    private Long userId;
    private String keyword;

    /** 两端兼容取页码 */
    public Long resolvePage() {
        if (currentPage != null) return currentPage;
        if (pageNum != null) return pageNum;
        return 1L;
    }
}
```

```java
// service/ConsultationSessionService.java：把 getPargeNum() 换成 resolvePage()
return consultationSessionMapper.selectPage(new Page<>(query.resolvePage(), query.getPageSize()), qw);
```

> **不要**用「保留 `pargeNum` 做兼容」的写法——那是上一版的建议，现已确认**两端都不传这个名**，留着只会误导。
>
> ~~同类问题在 `EmotionDiaryAdminPageQuery` 上是另一种表现（前端发 `current`/`size`）~~ ——
> **这条已不适用**：管理端情绪日志**已改成返回 `List`、不做分页**（见 8.3② / 8.8），
> 所以那边不再有页码参数，`current`/`size` 也不该再发。**只有本节的 `/sessions` 还有分页参数问题**。
>
> 一句话：**分页参数名不统一，是"翻页看着没反应"的头号原因** —— 要么两端对齐名字，要么干脆别分页。
