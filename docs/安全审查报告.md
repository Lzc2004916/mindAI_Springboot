## 1. 🔴 P0：可被未授权者直接利用

### S-01 JWT 签名密钥用了仓库里的硬编码默认值 → 任何人都能伪造管理员身份

**位置**
- `src/main/resources/application.yml:31`
  ```yaml
  jwt:
    secret: ${JWT_SECRET:MySecretKeyForJWT2026_dev_only}   # ← 冒号后面就是兜底默认值
  ```
- `util/JwtTokenUtil.java:59`（签发）与 `:133`（验签）都用这个值做 `Algorithm.HMAC256(secret)`。

**风险类型与影响范围**
- 类型：**认证绕过 / 越权（CWE-798 使用硬编码凭据）**，OWASP A02:2021 加密机制失效 + A07:2021 认证失效。
- 影响范围：**全站、全数据、全角色**。攻击者只需一份源码（本仓库已推送 GitHub），即可离线签发一个 `roleType=2` 的 token，无需知道任何密码。拿到后可：
  - 读取**所有用户**的情绪日记、AI 情绪分析、完整咨询对话（敏感心理健康数据）
  - 读取管理端全站统计 `GET /api/data-analytics/overview`
  - 删除/篡改知识库文章、删除任意用户情绪日记
  - 以任意用户身份发消息、删除他人会话
- **真实触发条件已具备**：本机注册表里 `JWT_SECRET` **未设置**（仅设了 `AI_API_KEY`），也就是说你现在运行的实例**正在使用这个公开密钥**。

**证据（动态实测，非推断）**
```
[基线-受保护接口] GET /api/user/current 无 token       -> HTTP 401 {"code":"A0301"}
[伪造-管理员]     用默认密钥伪造 admin 的 JWT 打管理端   -> HTTP 200 {"code":"200","data":{"systemOverview":{"totalUsers":6,...}}}
[伪造-管理员]     伪造 admin 打 /api/emotion-diary/admin/page -> HTTP 200，返回 wangwu 等人的日记明细
[对照-错误密钥]   换成非仓库里的密钥签同一个 token        -> HTTP 401 {"code":"A0230","msg":"token无效"}
```
> 第三行是关键对照：**换掉密钥就 401，用仓库默认值就 200** —— 证明这条路径的成败完全取决于"密钥是否可猜"。

**修改建议（按顺序做，三步都要）**

**① 代码层：让"没有强密钥"变成启动失败**（杜绝以后静默回落到默认值）

```java
// config/JwtConfig.java —— 加一段启动自检
@PostConstruct
void validate() {
    if (secret == null || secret.isBlank() || secret.length() < 32) {
        throw new IllegalStateException(
                "JWT_SECRET 未配置或长度不足 32 位，拒绝启动。请设置环境变量 JWT_SECRET。");
    }
}
```

```yaml
# application.yml —— 去掉 ": 默认值"，让缺配置直接暴露
jwt:
  secret: ${JWT_SECRET}
```

**② 运维层：轮换密钥并配置环境变量**

```bash
# 生成 48 字节随机密钥
python -c "import secrets; print(secrets.token_urlsafe(48))"
# 写入用户级环境变量（IDE 里跑也要能读到；IDEA 运行配置里也建议显式加一条）
setx JWT_SECRET "<上一步生成的值>"
```
> 轮换后**所有已签发的 token 立即失效（全员需重新登录）**——这是一次性的预期代价，不是 bug。

**③ 仓库层：把旧密钥从 Git 历史里清掉**

```bash
# 旧值有两个：MySecretKeyForJWT2026_dev_only（当前兜底）、
#              MySecretKeyForJWT2026!@#$%^&*()_+SecureKeyHere（更早的版本，git log -p 可见）
echo 'literal:MySecretKeyForJWT2026_dev_only==>***REMOVED***' >> replacements.txt
echo 'literal:MySecretKeyForJWT2026!@#$%^&*()_+SecureKeyHere==>***REMOVED***' >> replacements.txt
pip install git-filter-repo
git filter-repo --replace-text replacements.txt
git push --force --all        # ⚠️ 会重写历史，其他协作者必须重新 clone
```
> 即便不做历史清理，**也必须认定这两个旧密钥已永久泄露、不可再使用**。

### S-04 登录接口没有任何失败限流 → 可无限撞库

**位置**
- `service/UserService.java:32-59`（`login()` 只做「查用户 + 校验密码」，无失败计数）
- 说明：早期版本曾有 `LOGIN_FAIL` / `MAX_FAIL_COUNT=5` / 5 分钟锁定，在提交 `fac1753` 中被**整体删除**（`git log -S` 可确认），现在完全没有防爆破逻辑。
- 相关弱点叠加：注册只要求密码 **6~50 位、无复杂度校验**（`UserRegisterCommandDTO:29-31`），弱口令概率高。

**风险类型与影响范围**
- 类型：**认证失效 / 撞库（CWE-307 对认证尝试次数无限制）**
- 影响范围：任意账号。管理员账号 `admin` 是高价值目标——一旦被登录，等价于拿到后台全部数据。
  单机 12 次尝试仅耗时 0.9s，估算可持续约 13 次/秒；若有字典（弱口令 top1000 + 常见变形），分钟级即可覆盖。

**证据（动态实测）**
```
[爆破] 连续 12 次错误密码登录 admin -> HTTP 集合=[200]（全部 200），耗时 0.9s，无 429、无锁定
```

> 正面：登录失败的**提示语是统一的**（"用户名或密码错误"），未暴露"用户是否存在" ✅ —— 见第 6 节。

**修改建议**

新增 `security/LoginAttemptGuard.java`（**不引入新依赖**，用 `ConcurrentHashMap` 即可，与项目现有风格一致）：

```java
package com.lzc.mindaispringboot.security;

import com.lzc.mindaispringboot.exception.BusionessException;
import org.springframework.stereotype.Component;

import java.time.Duration;
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;

/** 登录失败限流：同一账号连续失败 5 次锁定 15 分钟（进程内计数，重启清零） */
@Component
public class LoginAttemptGuard {
    private static final int MAX_FAIL = 5;
    private static final Duration LOCK = Duration.ofMinutes(15);
    private static final int CAP = 10_000;            // 防止被刷爆内存

    private record Rec(int fails, long lockedUntil) {}
    private final Map<String, Rec> map = new ConcurrentHashMap<>();

    /** 登录前调用：已锁则直接拒绝 */
    public void assertAllowed(String key) {
        Rec r = map.get(key);
        if (r == null) return;
        long now = System.currentTimeMillis();
        if (r.lockedUntil() > now) {
            long minutes = (r.lockedUntil() - now) / 60_000 + 1;
            throw new BusionessException("尝试次数过多，请 " + minutes + " 分钟后再试");
        }
    }

    /** 密码错误时调用 */
    public void onFail(String key) {
        if (map.size() > CAP) map.clear();
        map.compute(key, (k, v) -> {
            int fails = (v == null ? 0 : v.fails()) + 1;
            long lock = fails >= MAX_FAIL ? System.currentTimeMillis() + LOCK.toMillis() : 0L;
            return new Rec(fails, lock);
        });
    }

    /** 登录成功时调用 */
    public void onSuccess(String key) { map.remove(key); }
}
```

`UserService.login()` 里接入：

```java
public UserLoginResponseDTO login(UserLoginCommandDTO dto) {
    String account = dto.getUsername();
    attemptGuard.assertAllowed(account);                 // ① 先看是否已锁
    ...
    if (user == null || !passwordEncoder.matches(inputPassword, user.getPassword())) {
        attemptGuard.onFail(account);                    // ② 记一次失败
        throw new BusionessException("用户名或密码错误");
    }
    ...
    attemptGuard.onSuccess(account);                     // ③ 成功清零
    String token = JwtTokenUtil.generateToken(...);
```
> 生产环境建议把 key 换成 `账号 + 客户端 IP`，并把计数放到 Redis（多实例共享）；单实例用上面这版就够。
> ⚠️ 取 IP 时不要直接信 `X-Forwarded-For`（可伪造），应从 `request.getRemoteAddr()` 取，或只在有可信反代时读 XFF。

### S-05 注册接口公开且无限流 + 新账号即可调用付费 AI → 成本型 DoS

**位置**
- `config/SecurityConfig.java:23-25`：`/api/user/add` 在 `PUBLIC_MATCHERS`（免登录）
- `service/UserService.java:62-85`：无频率限制、无验证码、无邮箱验证
- 新注册用户立即可用：`POST /api/psychological-chat/stream`（流式对话）、`GET .../emotion`（情绪分析）、`POST /api/emotion-diary`（触发 AI 分析）——**每一个都是真实计费的第三方调用**

**风险类型与影响范围**
- 类型：**资源滥用 / 成本型拒绝服务（CWE-770 无节制的资源分配）**
- 影响范围：脚本可批量注册账号 → 每个账号持续刷 AI 接口 → **AI 账单失控**，同时拖垮服务（与 S-06 叠加）。
  另外还会污染 `user` 表（垃圾账号），并成为后续撞库的"合法入口"。

**修改建议（三选一或叠加）**
1. **注册限流**：按 IP 限制，如"每 IP 每小时 5 个"（复用 S-04 的 `LoginAttemptGuard` 思路，改个 key 即可）。
2. **人机校验**：接入滑块/图形验证码（可放前端，后端校验 ticket）。
3. **AI 配额**：给每个用户每天可调用的 AI 次数设上限（如对话 50 条/天），超限返回业务错误。
   实现上可复用已有的 `ai_analysis_task` 表思路，或直接按 `consultation_message` 当日条数统计：

  - Tomcat 默认 200 个工作线程。`getEmotionAnalysis` 未命中缓存时单次占用线程 **约 10 秒**（缓存未命中即触发一次 AI 调用），
    因此**约 20 个并发请求就能把线程池占满**，此后全站所有接口（包括登录）都无法响应。
  - 一个已登录的普通账号就能发起这些请求——**不需要管理员权限**。
  - 同时产生 20 次真实 AI 调用 → 费用同步放大。

**证据**
- 动态：本轮实测中该路径当前 DB 已全部命中缓存，未复现 10s 阻塞；
- 代码级：`.call()` 为阻塞式调用（对比 `stream()` 的响应式路径），
  且历史实测记录（2026-09-27，`session_4` 仅 1 条消息）为 **10.2 秒**，命中缓存时为 **0.01 秒**。
- 计算：200 线程 ÷ 10 秒 ≈ 20 并发即可打满。

**修改建议**
1. **止血（改动最小）**：给这两个接口加"每用户并发闸门"。
   ```java
   // 放到一个可复用的小工具类里
   private static final Map<Long, Semaphore> AI_GATES = new ConcurrentHashMap<>();
   private static Semaphore gate(Long userId) {
       return AI_GATES.computeIfAbsent(userId, k -> new Semaphore(2));   // 每用户最多 2 个并发 AI 请求
   }
   // 调用前
   if (!gate(userId).tryAcquire()) throw new BusionessException("操作过于频繁，请稍后再试");
   try { /* ...AI 调用... */ } finally { gate(userId).release(); }
   ```
   再叠加全站级别的信号量（如总并发 AI ≤ 30），防止多账号联合打满。
2. **根治**：把情绪分析改为**异步任务**（复用已有的 `ai_analysis_task` 表 + `AnalysisTaskScheduler`），
   接口立即返回「分析中」或上一次缓存结果，由调度器后台跑 —— 这样接口耗时从 10s 降到毫秒级，
   线程占用问题自然消失。顺带能修掉前端的 10s 超时与"网络异常"误报。
3. 给 `/stream` 设置**连接超时与最大时长**（如 60s），避免慢连接长期占用线程。

### S-07 上传的文件**完全没有鉴权**就能被任何人在浏览器里打开

**位置**
- `config/SecurityConfig.java:26`：`"/files/**"` 被列入 `PUBLIC_MATCHERS`
- `security/JwtAuthticationFilter.java:29-33`：`shouldNotFilter` 对公开路径**直接跳过整个 JWT 过滤器**
- `config/WebMvcConfig.java:16-19`：把该路径映射到磁盘上传目录
  ```java
  registry.addResourceHandler(accessPrefix)          // /files/**
          .addResourceLocations("file:" + uploadDir); // D:\mindAI_Springboot\file
  ```

**风险类型与影响范围**
- 类型：**未授权访问（CWE-306 关键功能缺少身份认证）**
- 影响范围：**任何上传过的文件，只要知道路径就可被任何人读取**，无需登录。
  影响面覆盖：用户头像、文章封面、以及业务上已支持上传的 **pdf/doc/xls 文档**（`ALLOWED_EXT` 含这些），
  这类"资料"往往是实名/病例/证明类内容。
  缓解因素：文件名是 UUID v4（不可猜），但路径会通过参考来源（Referer）、聊天转发、
  日志、浏览器历史等渠道外泄；且**一旦泄露就是永久公开**（无过期、无撤销）。

**证据（动态实测）**
```
写文件 D:\mindAI_Springboot\file\2026-09\_sec_probe_readonly.txt（内容 SECURITY-PROBE-CONTENT-12345）
无 token 直接请求 /files/2026-09/_sec_probe_readonly.txt
  -> HTTP 200, Content-Type: text/plain, 响应体 = 'SECURITY-PROBE-CONTENT-12345'
对照：无 token 请求 /files/2026-09/anything.png（文件不存在）-> HTTP 500（不是 401/403）
     说明请求**根本没经过鉴权过滤器**，而是直接进了静态资源处理器
测试文件与目录已删除，未留残留
```

**修改建议**
1. **首选：把 `/files/**` 从 `PUBLIC_MATCHERS` 移除**，改为经鉴权接口下载，并校验归属：
   ```java
   @GetToken
   @GetMapping("/api/file/{id}/download")
   public ResponseEntity<Resource> download(@PathVariable Long id) {
       SysFileInfo info = fileService.getForDownload(id, Token_Aspect.getUserId()); // 内部校验 upload_user_id
       Resource res = new FileSystemResource(Paths.get(uploadDir, info.getFilePath()));
       return ResponseEntity.ok()
               .contentType(MediaType.APPLICATION_OCTET_STREAM)
               // 强制下载而不是内联渲染，进一步降低内容嗅探风险
               .header(HttpHeaders.CONTENT_DISPOSITION,
                       ContentDisposition.attachment().filename(info.getOriginalName(),
                               StandardCharsets.UTF_8).build().toString())
               .header("X-Content-Type-Options", "nosniff")
               .body(res);
   }
   ```
2. **若确实需要公开访问**（如前台文章封面图），则把"公开文件"与"私有文件"分开：
   - 公开：仅 `IMG` 类型、仅 `status=1`、放在独立目录（如 `/files/public/**`）
   - 私有：走上面的鉴权接口
3. **兜底**：无论如何都给静态资源加 `Content-Disposition: attachment` 与 `nosniff`，避免同源下被当作 HTML/JS 渲染。

### S-08 上传只按**扩展名**判断类型，不校验真实内容

**位置**
`service/FileService.java:29-33, 52-57, 102-116`
```java
private static final List<String> ALLOWED_EXT = List.of(
        "jpg","jpeg","png","gif","webp","bmp","pdf","txt","doc","docx","xls","xlsx","ppt","pptx");
...
String ext = getExt(originalName);          // 仅取最后一个 ".", 之后的小写字符串
if (!ALLOWED_EXT.contains(ext)) throw new BusionessException("不支持文件类型：" + ext);
...
.fileType(resolveFileType(ext))             // 类型也由扩展名推得
```
`getExt()` 只看文件名，**没有读取任何字节做魔数（magic number）校验**。

**风险类型与影响范围**
- 类型：**不受限文件上传（CWE-434）/ 内容欺骗**
- 影响范围（按严重度）：
  - **文件托管滥用**：把 exe/压缩包/钓鱼页面改名为 `.txt`/`.pdf` 就能上传成功，
    配合 S-07 得到一个"免登录、以你域名为信任背书"的分发点。
  - **存储耗尽**：单文件 10MB，但**没有总量/频率限制**，可反复上传填满磁盘（叠加 S-04 的多账号）。
  - **XSS 已基本被阻断**（重要澄清，不要过度担心）：
    `.svg`/`.html`/`.js` 不在白名单；且 `/files/**` 的 `Content-Type` 由扩展名决定
    （实测 `.txt` → `text/plain`），浏览器不会把 `text/plain` 当 HTML 渲染。
    所以**当前不存在可直接利用的存储型 XSS**。但如果以后有人往白名单里加了 `svg`/`html`，
    或改了资源响应的 Content-Type，就会立刻变成高危 —— 建议现在就加防护（见下）。
- 附带：`originalName` 原样入库（`FileService:73`），若管理端用 `v-html` 渲染文件名，则存在前端侧的存储型 XSS 风险（**前端问题，本轮未验证**）。

**修改建议**
1. **内容校验**（扩展名 + 魔数双重校验，两者都要）：
   ```java
   /** 各类型文件头的"魔术字节"；只校验前若干字节 */
   private static final Map<String, byte[]> MAGIC = Map.of(
           "jpg",  new byte[]{(byte) 0xFF, (byte) 0xD8, (byte) 0xFF},
           "png",  new byte[]{(byte) 0x89, 'P', 'N', 'G'},
           "gif",  new byte[]{'G', 'I', 'F', '8'},
           "webp", new byte[]{'R', 'I', 'F', 'F'},          // RIFF....WEBP
           "pdf",  new byte[]{'%', 'P', 'D', 'F'}
   );

   private void assertContentMatches(String ext, MultipartFile file) throws IOException {
       byte[] head = new byte[8];
       try (var in = file.getInputStream()) {
           int n = in.read(head);
           if (n <= 0) throw new BusionessException("文件内容为空");
       }
       byte[] expected = MAGIC.get(ext);
       if (expected == null) return;                    // doc/xls/ppt 属 ZIP 容器，建议用 Tika 判定
       for (int i = 0; i < expected.length; i++) {
           if (head[i] != expected[i]) throw new BusionessException("文件内容与扩展名不符");
       }
   }
   ```
   > Office 系列（docx/xlsx/pptx）与 doc/xls 建议引入 **Apache Tika**（`org.apache.tika:tika-core`）做统一检测，
   > `new Tika().detect(inputStream)` 一行即可，比手写魔数表更可靠。
2. **重命名 + 二次编码**：文件名已经用 UUID ✅ 保持；对图片建议用 `ImageIO` 读一遍再重新写出，
   可顺带剥离恶意元数据（EXIF 里的脚本）。
3. **总量与频率限制**：每用户每日上传次数/总大小的配额；对私有文件保留 `expire_time` 并**实现定时清理**（目前临时文件有有效期字段但无清理任务，会无限堆积）。

public void invalidateTokens(Long userId) {

### S-10 `/api/user/renew` 凭一个有效 token 就能无限续期

**位置**
`service/UserService.java:122-127`
```java
public String renewToken(Long userId){
    User user = userMapper.selectById(userId);
    if (user == null) throw new BusionessException("用户不存在");
    if (!user.isActive()) throw new BusionessException("用户已经被禁用，请联系管理员");
    return JwtTokenUtil.generateToken(user.getId(), user.getUsername(), user.getUserType(),
            userId.intValue());      // ← 把 userId 当成了 tokenVersion
}
```
两个问题叠加：
1. **认证强度**：续期只凭"当前 token 有效"，不校验密码、不校验二次因子 → 令牌一旦泄露，可不断续期，**会话没有绝对上限**。
2. **功能性 bug**：第 4 个参数应是 `user.getTokenVersion()`，这里传了 `userId.intValue()`，
   导致续出的 token 里 `tokenVersion != 库里的值`，会被过滤器判定为 `A0230 token无效` ——
   **也就是说 `/renew` 接口目前实际是坏的**。这个 bug 反而临时挡住了问题 1，但一旦被修好就会立刻暴露。

**风险类型与影响范围**
- 类型：**会话无绝对期限（CWE-613）**，配合 token 泄露场景放大伤害
- 影响范围：单个被窃取的 token 可被无限延寿（修好 bug 之后）；当前表现为接口不可用（功能缺陷）。

**修改建议**
1. **先修 bug**（无论如何都要修）：
   ```java
   return JwtTokenUtil.generateToken(user.getId(), user.getUsername(),
           user.getUserType(), user.getTokenVersion());   // ← 用库里的版本号
   ```
2. **再加强制约束**：
   - 引入 `refresh_expiration`（yml 里已有 7 天的配置，但代码没用到）作为**绝对上限**：
     为每个 token 记一个"首次签发时间"（可放 `tokenVersion` 旁新增 `session_started_at`），
     超过 7 天强制要求重新登录。
   - 更规范的做法是 **access token（短，15~30 分钟）+ refresh token（长，存库、可撤销）**，
     并让 refresh token 在改密/登出时失效。
3. 如果暂时不做刷新机制，就把 `expiration` 从 24 小时降到 2~4 小时，配合前端静默续期（风险更低）。

**位置** `exception/GlobarExceptionHandler.java:51-56`

**风险类型与影响**：**错误处理不当（CWE-755）**。它会把本应 404 的 `NoResourceFoundException`、
本应 405 的 `HttpRequestMethodNotSupportedException`、本应 400 的 `HttpMessageNotReadableException`
统统吞成 500，导致：① 前后端联调时错误语义失真；② 攻击者扫描目录/探测接口时**看不到 404 与 401 的差异**，
反而更难被发现（对防守方是坏事，对攻击者是便利）。

**证据（动态实测）**
```
无 token GET /files/2026-09/anything.png  -> HTTP 500 {"code":"500","msg":"系统错误"}
日志：org.springframework.web.servlet.resource.NoResourceFoundException:
      No static resource 2026-09/anything.png for request '/files/2026-09/anything.png'.
```
（正确应为 404）

**修改建议**：让带状态码的异常原样透传，放在兜底之前：
```java
@ExceptionHandler(ErrorResponseException.class)   // 含 NoResourceFoundException / ResponseStatusException 等
public ResponseEntity<Result<Void>> handleStatusException(ErrorResponseException e) {
    HttpStatusCode status = e.getStatusCode();
    return ResponseEntity.status(status)
            .body(Result.error(String.valueOf(status.value()), e.getMessage(), null));
}
```
> ⚠️ 前端要同步：目前前端可能把 500 当作"服务异常"，改成 404/405 后注意提示语不要变怪。

### S-17 会话 ID 解析有两份实现，其中一份没做异常保护

**位置**
- `controller/PsychologicalChatController.java:133-141` —— 用 `try/catch` 包住 `Long.parseLong` ✅
- `service/AI/PsychologicalSupportService.java:106-109` —— **裸 `Long.parseLong`**：
  ```java
  private Long extractSessionId(String sessionId){
      if (sessionId == null || !sessionId.startsWith("session_")) return null;
      return Long.parseLong(sessionId.replace("session_",""));   // session_abc -> NumberFormatException -> 500
  }
  ```
**风险类型与影响**：**输入校验不一致（CWE-20）**。`GET /api/psychological-chat/session/session_abc/emotion`
会走到这里抛 `NumberFormatException`，被兜底处理器变成 500（叠加 S-14），既影响可用性也污染日志。

**修改建议**：只保留一份解析工具（建议放 `security` 或 `util` 里作为静态方法），两处都调用它：
```java
public static Long parseSessionId(String raw) {
    if (!StringUtils.hasText(raw)) throw new BusionessException("会话ID不能为空");
    String s = raw.startsWith("session_") ? raw.substring("session_".length()) : raw;
    try { return Long.parseLong(s); }
    catch (NumberFormatException e) { throw new BusionessException("会话ID格式错误"); }
}
```

### S-18 安全响应头 / CORS / 数据库连接配置

**位置与现状（实测响应头）**
```
✅ X-Content-Type-Options: nosniff        （Spring Security 默认提供）
✅ X-Frame-Options: DENY                  （Spring Security 默认提供）
✅ Cache-Control: no-cache, no-store, max-age=0, must-revalidate
❌ Content-Security-Policy        缺失
❌ Strict-Transport-Security      缺失
❌ Referrer-Policy                缺失
❌ Access-Control-Allow-Origin    未配置（无 CORS 策略）
```
- **风险类型**：**安全配置缺失（CWE-693）**
- 说明：当前后端只返回 JSON + 静态文件，CSP/HSTS 的即时收益有限（所以列 P3）；
  但 S-07/S-08 一旦让同源下托管了任意内容，CSP 就是最后一道防线，建议现在就加上。
- 另外 `application.yml:8-10`：`useSSL=false&allowPublicKeyRetrieval=true`，且 `DB_USER`/`DB_PASSWORD`
  默认值是 `root/root`（本机安全，**但若部署到远端 DB 且忘记设环境变量，等于用 root/root 明文连库**）。

**修改建议**
```java
// SecurityConfig —— 补安全响应头
.headers(h -> h
        .contentSecurityPolicy(csp -> csp.policyDirectives("default-src 'none'; frame-ancestors 'none'"))
        .referrerPolicy(r -> r.policy(ReferrerPolicyHeaderWriter.ReferrerPolicy.NO_REFERRER))
        .httpStrictTransportSecurity(hsts -> hsts.includeSubDomains(true).maxAgeInSeconds(31536000)));
```
```yaml
# 生产环境：去掉默认值 + 开启 TLS + 专用最小权限账号（不要用 root）
spring:
  datasource:
    url: jdbc:mysql://<host>:3306/mental_health_assistant?useSSL=true&requireSSL=true&serverTimezone=Asia/Shanghai
    username: ${DB_USER}
    password: ${DB_PASSWORD}
```
CORS 若前端走 Vite 代理（当前就是），**保持不配置**即可；将来若前后端分域部署，
必须用**明确白名单**而不是 `allowedOrigins("*")`，并且不能与 `allowCredentials(true)` 同时用。
