## 0. 怎么读这份文档

- **「调用关系」** 用箭头表示：`A → B` 表示 A 会调用 B。
- **「要点」** 是「写这段代码时为什么这么做、不注意会踩什么坑」。
- **「可优化」** 是建议，不是 bug。编号 `O-xx` 全项目唯一，可单独拎出来当任务做。
- **「本章代码答案」**（每章最后一节）给每个 `O-xx` 一份**可直接粘贴的实现**：
  - 「改哪里」= 文件位置；给出的代码是**整段可替换**的完整方法/类，不是伪代码。
  - 需要改 DDL 的会先给 SQL —— **务必先跑 DDL 再改实体**（否则该表所有查询直接 `ERROR 1054`）。
  - 需要前端联动的会标 **⚠️ 前端要同步**，请与前端一起发版，避免「后端改了前端炸」。

**关于「可运行」的边界**（避免误解）：
- 代码基于当前仓库的真实类名、字段名、方法签名写成，**粘贴即可编译**。
- 少数方案需要先加依赖（文中会给出 pom 片段）或加表/加列（文中会给出 SQL）。
- 标了「方案 A / 方案 B」的是**二选一**，不要两个都上。
- `JdbcChatMemoryRepository` 这类第三方类，类路径以**你本地依赖实际内容**为准（文中已注明）。

项目坐标速查：

| 项 | 值 |
|---|---|
| 包名 | `com.lzc.mindaispringboot`（**`mappper` 是三个 p，故意的**） |
| 端口 | 1236 ｜ 库 `mental_health_assistant`（MySQL 5.7） |
| 技术栈 | Spring Boot 4.1.1 / JDK 17 / MyBatis-Plus 3.5.17 / Spring Security / java-jwt / Spring AI 2.0.1 / Hutool |

## 1. 公共基础件（每个模块都会用到，先看这里）

### 1.1 `common/Result.java` —— 统一响应外壳

**作用**：所有接口的返回值都套这一层，前端只需要认 `code`。

```
{ "code": "200", "msg": "操作成功", "message": "操作成功", "success": true, "data": {...} }
```

**调用关系**：`所有 Controller` → `Result.success()/error()`；`ResponseUtil` 也用它给过滤器写错误响应。

**要点**
- `code` 是**字符串**（`"200"` 而不是 `200`）。前端用 `data.code == 200` 宽松比较，Python 脚本验证时必须写 `str(code) == "200"`，否则会把有数据的响应判成空。
- `success()` 同时塞了 `msg` 和 `message`，是为了兼容前端两种读法。

**可优化**
- **O-01**：`msg` 和 `message` 是同义字段，`success` 也能由 code 推出，属于冗余。建议只留 `code/msg/data`（改之前要同步前端，它现在是 `msg || message` 兜底）。

### 1.2 `common/ResultCode.java` —— 错误码字典

**作用**：集中定义「码 → 文案」。分 5 组：成功/系统、参数、文件、业务、token。

**token 组的含义（排查鉴权问题时必背）**

| code | 含义 | 什么时候出现 |
|---|---|---|
| `A0230` | token 无效 | 签名错 / 过期 / **`tokenVersion` 不符** |
| `A0231` | token 被禁止访问 | 用户被禁用 / 已删除 |
| `A0232` | token 已过期 | 预留（当前过期也走 A0230） |
| `A0233` | token 已加入黑名单 | 预留（未实现黑名单） |
| `A0300` | 访问权限异常 | 预留 |
| `A0301` | **访问未授权** | **请求头里完全没有 token**（这个码很窄，能直接排除「过期/越权」） |

**要点**：`A0301` 与 `A0230` 的区别是排查时最常搞混的一对。前者是「没带证件」，后者是「证件是假的/过期了」。
另外注意：**`BUSINESS_ERROR` 不在这个枚举里** —— 它是 `BusionessException` 里硬编码的字符串（见 1.3）。

**可优化**
- **O-02**：把 `BUSINESS_ERROR` 等业务码收进 `ResultCode`，避免「同一个项目两套码」。
- **O-03**：`A0232/A0233/A0300` 目前没有任何代码产生它们（死码）。要么实现对应功能，要么删掉防止误读。

### 1.3 `exception/BusionessException.java` —— 业务异常

**作用**：业务层「可以预期的错误」统一抛它（比如「原密码错误」「无权操作该会话」）。

**要点**
- `code` **固定为 `"BUSINESS_ERROR"`**，不是 `ResultCode` 里的值。
- 它是 `RuntimeException`，所以 service 方法签名不用写 `throws`。
- 抛出后由 `GlobarExceptionHandler` 接住 → **HTTP 状态码仍然是 200**，靠 body 里的 `code` 表达错误。这一条很重要：前端 `request.js` 的响应错误分支不会触发，而是走「成功分支里 code != 200」那条路。

**可优化**
- **O-04**：类名拼写应为 `BusinessException`。全项目引用点很多，建议和包名重构一起做。
- **O-05**：固定 code 让前端无法区分「密码错」和「无权限」，只能靠文案。建议增加 `code` 构造参数。

### 1.4 `GlobarException/GlobarExceptionHandler.java` —— 全局异常翻译层

**作用**：把抛出来的异常翻译成统一的 `Result`。

**当前只处理 4 种**

| 异常 | 返回 |
|---|---|
| `MethodArgumentNotValidException` | `code="400"`，`data` 是所有字段错误信息拼接（`@Valid` 校验失败时） |
| `BusionessException` | 用它自己的 code/message/data |
| `MaxUploadSizeExceededException` | `code="5004"`「最大支持10MB」 |
| `AccessDeniedException` | **HTTP 403** + `code="A0300"`「没有权限访问该资源」（`@PreAuthorize` 失败时） |

**要点**
- 只有 `AccessDeniedException` 这一支显式设了 HTTP 403，其余都是默认 200。
- 过滤器里抛的异常**不归它管**（过滤器在 DispatcherServlet 之前执行），所以 `JwtAuthticationFilter` 必须自己 try/catch 或直接写响应。

**可优化**
- **O-06（较重要）**：**缺少 `@ExceptionHandler(Exception.class)` 兜底**。现在未预期异常（比如空指针）会返回 Spring 默认的 `{"timestamp","status","error","path"}`——**没有 `code` 字段**，前端只能显示「请求失败（500）」，排查体验差。建议恢复兜底并返回 `Result.error(ResultCode.SYSTEM_ERROR…)`，同时 `log.error` 打全栈。
- **O-07**：`GlobarException` 这个包名与 `exception` 包职责重叠（一个放处理器、一个放异常类）。建议合并为 `common/exception/`。

### 1.5 `config/JwtConfig.java` + `util/JwtTokenUtil.java` —— JWT 的配置与工具

**`JwtConfig`**：`@ConfigurationProperties(prefix="jwt")`，把 yml 里的 `secret / expiration / refreshExpiration / header / tokenPrefix` 映射成对象。

**`JwtTokenUtil`** 的 4 个能力：

| 方法 | 作用 | 要点 |
|---|---|---|
| `generateToken(userId, username, roleType, tokenVersion)` | 造 token | 4 个 claim 全塞进去；issuer 固定 `L-Z-C`；有效期 24 小时 |
| `extractTokenFromRequest(request)` | **全项目唯一的取 token 入口** | 先读 yml 配的 `Authorization` 头并去掉 `Bearer ` 前缀；读不到再兼容旧的 `token` 头 |
| `validateToken(token)` | 验签 + 取 claim | 返回 `TokenVerificationResult`；**4 个 claim 缺任何一个都返回 null** |
| `verifyToken(token)` | 只验签名/签发者/过期 | 失败抛 `JWTVerificationException` |

**要点（很容易踩）**
- 它是 `static` 工具类，但需要 Spring 的 `JwtConfig`，所以实现了 `ApplicationContextAware` 把上下文存成静态字段。**这是「静态工具类要读配置」的常见折中写法**，理解这一点就不会奇怪「为什么一个 util 要实现 Aware 接口」。
- `extractTokenFromRequest` **只负责把字符串拿出来，不判断合法性** —— 合法性在 `validateToken`。职责分得很干净，别把两者混起来。

**可优化**
- **O-08**：`refreshExpiration` 配了 7 天但**全项目无人使用**，容易让人误以为「token 能刷新」。要么实现刷新接口，要么删掉这个配置。
- **O-09**：静态字段持有 `ApplicationContext` 不利于单元测试。可改为构造注入的 `@Component`（但会牵动所有静态调用点，优先级低）。

### 1.6 `util/JwtAuthticationFilter.java` —— 鉴权第一道闸门

**作用**：每个请求进来先「认人」。`OncePerRequestFilter` 保证一次请求只跑一次。

**流程（顺序不能乱）**

```
shouldNotFilter？ → 是公开路径（SecurityConfig.isPublicPATH）直接放行，不进 doFilterInternal
  ↓ 不是公开路径
① extractTokenFromRequest → 没取到 → 401 A0301（清 SecurityContext 后直接写响应返回）
② validateToken → 无效/claim 残缺 → 401 A0230
③ getUserById（try/catch 包住，用户被删会抛异常）→ 用户不存在 or status != 正常 → 403 A0231
④ tokenVersion 比对：JWT 里的 vs 数据库里的 → 不等 → 401 A0230   ← 改密码就靠这一步生效
⑤ 通过 → 往 SecurityContext 放 Authentication，权限 = "ROLE_" + roleType
  ↓
filterChain.doFilter() 继续走后面的链路
```

**要点**
- **第 ③ 步必须 try/catch**：`getUserById` 在「用户已被删除」时会抛 `BusionessException`，而过滤器执行在 `DispatcherServlet` 之前，**全局异常处理器接不到**，不接住就会变成 500 而不是干净的 401/403。
- **第 ④ 步是 `token_version` 机制的核心**：改密码 → 数据库版本 +1 → 旧 token 里还是旧版本号 → 立刻失效。
- 代码里注释编号是乱的（`//6.` 出现在 `//5.` 前面），纯粹是改动留下的痕迹，不代表执行顺序。
- 它通过 `SecurityConfig.isPublicPATH()` 判断是否放行，所以**白名单是全局唯一一份**（`PUBLIC_MATCHERS`），改白名单只改那一个数组。

**可优化**
- **O-10**：类名 `AuthticationFilter` 拼错，应为 `Auth**en**ticationFilter`。
- **O-11**：解析了两遍 JWT —— 这里验一次，`Token_Aspect` 又验一次（见 1.8）。可把这里解析出的 `userId` 放进 Authentication 的 principal，AOP 直接用。

### 1.7 `util/AuthUtil.java` —— 「是不是管理员」

**作用**：一行 `AuthUtil.isAdmin()` 判断当前请求是不是管理员。

**实现**：从 `SecurityContextHolder` 取 Authentication，遍历权限里有没有 `ROLE_2`。

**要点**：它是**约定式**的 —— `ROLE_2` 里的 `2` 就是 `user_type=2`（管理员）。这个字符串在 `JwtAuthticationFilter` 里拼、在 `AuthUtil` 里比、在 `@PreAuthorize("hasRole('2')")` 里用，**三处硬编码同一个约定**，改的时候必须一起改。

**可优化**
- **O-12**：把 `"ROLE_" + UserType.ADMIN.getCode()` 抽成常量，避免三处魔法值。

### 1.8 `Aop/GetToken.java` + `Aop/Token_Aspect.java` —— 取当前登录用户

**作用**：让 Controller 能拿到「当前是谁在请求」。
用法是两步：方法上打 `@GetToken`，方法体里调 `Token_Aspect.getUserId()`。

**流程**：切面环绕拦截 → 取 token → 没 token 抛「未登录」 → `verifyToken` 解析 → `userId` 存进 `ThreadLocal` → 执行目标方法 → **finally 里 remove**。

**要点**
- `ThreadLocal` 用 `remove()` 清理是**必须的**：Tomcat 线程会被复用，不清就会「上一个人的 userId 串到下一个请求」。
- **隐藏契约**：忘了打 `@GetToken` 也能编译通过，但 `getUserId()` 返回 null，接口会出现「查不到自己的数据」这种诡异现象。这是这套设计的最大缺点。

**可优化**
- **O-13（较重要）**：改用 `HandlerMethodArgumentResolver`，Controller 直接写 `@CurrentUserId Long userId`。好处：① 忘写注解编译期就报错；② 不用手动 try/finally；③ 不依赖 ThreadLocal。
- **O-14**：`getUserId()` 里 token 无效时抛的是「未登录」（业务异常），而过滤器已经处理过鉴权，这里实际上是重复劳动（见 O-11）。

### 1.9 `util/ResponseUtil.java` —— 过滤器专用的响应写出

**作用**：过滤器/切面里不能返回 `Result`（不是 Controller），只能直接往 `HttpServletResponse` 写 JSON。它就干这件事。

**要点**
- 它维护了「`ResultCode` → HTTP 状态码」的映射：`UNAUTHORIZED / ACCESS_UNAUTHORIZED / TOKEN_INVALID / TOKEN_EXPIRED / TOKEN_BLOCKED` → **401**；`TOKEN_ACCESS_FORBIDDEN` → **403**；其他 → 400。
- 用 try-with-resources 拿 `PrintWriter`，写完 `flush()`。**不 flush 客户端可能收不到**。

**可优化**
- **O-15**：`catch` 里用 `System.out.println`，应改 `log.error`（项目其他地方已经统一用 Slf4j 了）。

### 1.10 `config/ChatClientConfig.java` —— 两个 AI 客户端（本项目的关键设计）

**作用**：Spring AI 的 `ChatClient` 是调大模型的入口。这里声明了**两个**：

| bean 名 | 带什么 | 谁在用 | 必须传 `chat_memory_conversation_id`？ |
|---|---|---|---|
| `open-ai` | `MessageChatMemoryAdvisor` + 默认 system 提示词 | 流式心理对话 | **是** |
| `analysis` | 什么都没带 | 情绪日记分析、会话情绪分析 | 否 |

**为什么要分两个（这是最容易踩的坑）**
- `MessageChatMemoryAdvisor` 的父类 `BaseChatMemoryAdvisor.getConversationId()` 里有一句硬断言：
  `Assert.notNull(context.get("chat_memory_conversation_id"), "conversationId cannot be null")`。
  **只要走 `open-ai` 而不传这个参数，就一定抛异常**。
- 而「喂一段文本 → 出 JSON」的一次性分析**没有多轮上下文**，不该往会话记忆里塞日记正文，更不该为了绕过断言硬编一个 conversationId。
- 所以正确做法就是：**一次性分析用 `@Qualifier("analysis")` 注入**。
- ⚠️ 不要给分析"补"一个 conversationId：`MessageWindowChatMemory` 底层是 `InMemoryChatMemoryRepository`（一个 `Map<String,List<Message>>`，**key 只增不减**）。所有分析共用一个 key 会让日记之间串味；每篇日记一个 key 就是内存泄漏。

**另外两点**
- `chatMemory()` 保留最新 30 条消息。
- `.system(x)` 是**覆盖**而不是追加（`DefaultChatClientRequestSpec.system()` 直接给 `systemText` 赋值），所以 `analysis` 不设默认 system 不影响调用方自己传的 system。
- 项目里有多个 `ChatClient` bean，**按类型裸注入会报 `NoUniqueBeanDefinitionException`**，新增注入点必须带 `@Qualifier`。

**可优化**
- **O-16**：ChatMemory 是内存实现 → **服务重启上下文全丢**，且 key 永不释放。建议换 `JdbcChatMemoryRepository`（Spring AI 自带）或 Redis 实现。
- **O-17**：`open-ai` 的默认 system 提示词写死了「面向大学生」，而产品定位是通用心理陪伴。建议按场景动态传 system，或把提示词外置到配置文件/数据库便于调整。

### 1.11 `AiService/PromptManage.java` —— 三份提示词

| 常量 | 用途 | 要点 |
|---|---|---|
| `PSYCHOLOGICAL_SUPPORT_SYSTEM_PROMPT` | 流式对话的角色设定 | 明确了「共情优先、不急于建议、检测到自杀倾向要引导求助」 |
| `EMOTION_ANALYSIS_PROMPT` | **会话**情绪分析 | 要求输出 10 个字段；**强制 `primaryEmotion` 只能从 10 个词里选**（避免 AI 自造词导致前端匹配不上） |
| `DIARY_ANALYSIS_PROMPT` | **日记**分析 | 特别强调「自评情绪可能与正文不一致，以正文为准」「注意 `moodScore`(越高越好) 与 `emotionScore`(越高越负面) 方向相反，别混用」 |

**要点**：提示词里反复出现的「riskLevel=2/3 时 isNegative 必须 true」「必须是整数」这些约束，是**为了减少后端 `normalize()` 兜底的次数**——但兜底仍然必须写，因为 AI 不保证遵守。

**可优化**
- **O-18**：提示词是 Java 字符串拼接，改一次要重新编译。建议外置到 `resources/prompts/*.txt` 或数据库，便于运营侧调整。

### 1.13 本章代码答案（O-01 ～ O-19）

> 阅读约定：每个 O-xx 与正文 1.x 的条目**同号一一对应**。
> 「改哪里」= 文件位置；代码即**可直接整段替换/粘贴**的实现。

#### O-01 · 精简 `Result`（去掉冗余字段）

**问题**：`msg` / `message` 同义，`success` 可由 code 推出。

改哪里：`common/Result.java`（整文件替换）

```java
package com.lzc.mindaispringboot.common;

import lombok.Data;

import java.io.Serializable;

@Data
public class Result<T> implements Serializable {
    private String code;
    private String msg;
    private T data;
    /** 保留 success：前端存在 `if (!res.success)` 兜底判断，删它必须同步改前端 */
    private Boolean success;

    public static <T> Result<T> success() {
        Result<T> result = new Result<>();
        result.setCode(ResultCode.SUCCESS.getCode());
        result.setMsg(ResultCode.SUCCESS.getMessage());
        result.setSuccess(true);
        return result;
    }

    public static <T> Result<T> success(T data) {
        Result<T> result = success();
        result.setData(data);
        return result;
    }

    public static <T> Result<T> error(String code, String msg, T data) {
        Result<T> result = new Result<>();
        result.setCode(code);
        result.setMsg(msg);
        result.setSuccess(false);
        result.setData(data);
        return result;
    }

    public static <T> Result<T> error() {
        return error(ResultCode.ERROR.getCode(), ResultCode.ERROR.getMessage(), null);
    }
}
```

```java
package com.lzc.mindaispringboot.util;

import com.auth0.jwt.JWT;
import com.auth0.jwt.JWTVerifier;
import com.auth0.jwt.algorithms.Algorithm;
import com.auth0.jwt.exceptions.JWTVerificationException;
import com.auth0.jwt.interfaces.DecodedJWT;
import com.lzc.mindaispringboot.config.JwtConfig;
import jakarta.servlet.http.HttpServletRequest;
import lombok.Getter;
import org.springframework.stereotype.Component;
import org.springframework.util.StringUtils;

import java.util.Date;

@Component
public class JwtTokenUtil {
    private static final String ISSUER = "L-Z-C";

    private final JwtConfig jwtConfig;

    public JwtTokenUtil(JwtConfig jwtConfig) {   // 构造注入，单测可直接 new JwtTokenUtil(mockConfig)
        this.jwtConfig = jwtConfig;
    }

    @Getter
    public static class TokenVerificationResult {
        private final Long userId;
        private final String username;
        private final Integer roleType;
        private final Integer tokenVersion;
        private final boolean token;

        public TokenVerificationResult(Long userId, String username, Integer roleType,
                                       Integer tokenVersion, boolean token) {
            this.userId = userId;
            this.username = username;
            this.roleType = roleType;
            this.tokenVersion = tokenVersion;
            this.token = token;
        }
    }

    public String generateToken(Long userId, String username, Integer roleType, Integer tokenVersion) {
        Algorithm algorithm = Algorithm.HMAC256(jwtConfig.getSecret());
        Date expiration = new Date(System.currentTimeMillis() + jwtConfig.getExpiration());
        return JWT.create()
                .withClaim("userId", userId)
                .withClaim("username", username)
                .withClaim("roleType", roleType)
                .withClaim("tokenVersion", tokenVersion)
                .withExpiresAt(expiration)
                .withIssuedAt(new Date())
                .withIssuer(ISSUER)
                .sign(algorithm);
    }

    public String extractTokenFromRequest(HttpServletRequest request) {
        if (request == null) return null;
        String headerName = jwtConfig.getHeader();
        if (StringUtils.hasText(headerName)) {
            String header = request.getHeader(headerName);
            if (StringUtils.hasText(header)) {
                String prefix = jwtConfig.getTokenPrefix();
                if (prefix != null && !prefix.isEmpty() && header.startsWith(prefix)) {
                    header = header.substring(prefix.length()).trim();
                }
                if (StringUtils.hasText(header)) return header;
            }
        }
        String legacy = request.getHeader("token");
        return StringUtils.hasText(legacy) ? legacy : null;
    }

    public TokenVerificationResult validateToken(String token) {
        try {
            DecodedJWT jwt = verifyToken(token);
            Long userId = jwt.getClaim("userId").asLong();
            String username = jwt.getClaim("username").asString();
            Integer roleType = jwt.getClaim("roleType").asInt();
            Integer tokenVersion = jwt.getClaim("tokenVersion").asInt();
            if (userId != null && StringUtils.hasText(username)
                    && roleType != null && tokenVersion != null) {
                return new TokenVerificationResult(userId, username, roleType, tokenVersion, true);
            }
            return null;
        } catch (Exception e) {
            return null;
        }
    }

    public DecodedJWT verifyToken(String token) {
        if (!StringUtils.hasText(token)) throw new JWTVerificationException("Token不能为空");
        Algorithm algorithm = Algorithm.HMAC256(jwtConfig.getSecret());
        JWTVerifier verifier = JWT.require(algorithm).withIssuer(ISSUER).build();
        return verifier.verify(token);
    }
}
```

### 2.1 实体与枚举

| 类 | 说明 |

### 2.2 `UserService` —— 四个核心方法

#### `login(UserLoginCommandDTO)` → `UserLoginResponseDTO`

见架构文档 2.1 的流程图。这里只补**代码里的 4 个设计决策**：

1. **先查限流**（`isLocked`）：同一账号 5 分钟内失败满 5 次 → 直接拒，不再查库。
2. **按用户名、再按邮箱分两次查**，而不是 `eq(username).or().eq(email)`。原因写在注释里：若甲的用户名恰好等于乙的邮箱，`selectOne` 会因命中两行直接抛 `TooManyResultsException`。
3. **「用户不存在」和「密码错误」返回同一句提示**：防止攻击者用提示差异枚举出哪些用户名真实存在。
4. **先验密码、再验状态**：顺序反过来，「用户已被禁用」这句话本身就泄露了「这个账号存在」。

**限流实现细节**：`ConcurrentHashMap<String, long[]>`，`long[0]`=失败次数、`long[1]`=首次失败时间戳。`compute()` 里判断「距上次失败超 5 分钟」就重置计数。

**可优化**
- **O-20**：限流是**纯内存**的 → 重启即清零、多实例部署时各算各的。建议 Caffeine（带过期）或 Redis。
- **O-21**：登录成功只清计数，没有记录登录日志（IP、时间、UA），排查异常登录时无据可查。

#### `register(UserRegisterCommandDTO)` → `UserDetailResponseDTO`

流程：两次密码一致 → 用户名/邮箱查重 → BCrypt 加密 → 存库。

**要点**
- **`user.setUserType(UserType.USER.getCode())` 是写死的**（注释写了「防止自行提权成管理员」）——请求体里就算传 `userType=2` 也没用。这是安全设计，别"优化"掉。
- 日志只打 `username` 和 `userId`，**不打整个 DTO**（DTO 里有明文密码，会一路进日志）。

**可优化**
- **O-22**：注册接口 `/api/user/add` 在 `PUBLIC_MATCHERS` 里，任何人都能注册；且**没有验证码/频率限制**，可被批量刷号。建议加图形验证码或 IP 限流。

#### `getUserById(Long)` → `UserDetailResponseDTO`

只做「查 + 转换 + 不存在则抛异常」。**被过滤器调用**（每请求一次），所以它必须足够快——目前是一次 `selectById` 主键查询，没问题。

**可优化**
- **O-23**：每请求都查一次用户表拿 `status` 和 `tokenVersion`。高并发下可加本地缓存（带短 TTL），但要权衡「禁用用户即时生效」的要求。

#### `changes(userId, ChangesPassword_Username)` → `String`（新 token）

流程：查用户 → BCrypt 校验原密码 → 两次新密码一致 → 加密 → **`tokenVersion + 1`** → 更新 → **用新版本号重新签发 token 并返回**。

**要点**
- `tokenVersion` 自增是「旧 token 立即失效」的唯一开关。
- 返回值类型从「字符串提示」改成了「新 token」，前端目前忽略它，仍走「清登录态 + 回登录页」。
- 入参类名 `ChangesPassword_Username` 用下划线连接，不符合 Java 命名规范。

**可优化**
- **O-24**：不校验复杂度，也不拦「新旧密码相同」。建议加最小复杂度要求（前端已有强度校验，后端应兜底）。
- **O-25**：前端可以做到「无感续期」——直接用返回的新 token 替换本地 token，省掉一次重新登录。前端改一行 `auth.login(newToken, userInfo)` 即可。
- **O-26**：类名改 `ChangePasswordRequest`；方法名 `changes` → `changePassword`；路由 `/api/user/Changes` → `/api/user/password`。

#### O-20 · 登录限流从 `ConcurrentHashMap` 换成 Caffeine

**问题**：纯内存 Map 重启清零、多实例各算各的、key 永不释放。

改哪里：新增 `service/LoginAttemptService.java`

```java
package com.lzc.mindaispringboot.service;

import com.github.benmanes.caffeine.cache.Cache;
import com.github.benmanes.caffeine.cache.Caffeine;
import org.springframework.stereotype.Service;

import java.util.concurrent.TimeUnit;
import java.util.concurrent.atomic.AtomicInteger;

/**
 * 登录失败计数（带自动过期）。
 * 语义：某账号连续失败满 MAX_FAIL 次后，在 LOCK_MINUTES 分钟内拒绝登录；
 *      该窗口内不再有新的失败记录时，缓存条目自动过期 → 计数归零。
 */
@Service
public class LoginAttemptService {

    private static final int MAX_FAIL = 5;
    private static final int LOCK_MINUTES = 5;

    /** expireAfterWrite：每次写入（含失败 +1）都重置 5 分钟窗口；窗口内没新失败就自动释放 */
    private final Cache<String, AtomicInteger> failCache = Caffeine.newBuilder()
            .expireAfterWrite(LOCK_MINUTES, TimeUnit.MINUTES)
            .maximumSize(100_000)                  // 兜住缓存无限增长
            .build();

    public boolean isLocked(String account) {
        if (account == null || account.isBlank()) return false;
        AtomicInteger c = failCache.getIfPresent(account);
        return c != null && c.get() >= MAX_FAIL;
    }

    public void recordFail(String account) {
        if (account == null || account.isBlank()) return;
        failCache.get(account, k -> new AtomicInteger(0)).incrementAndGet();
    }

    public void reset(String account) {
        if (account != null) failCache.invalidate(account);
    }

    /** 给 O-22 复用：按 IP 限流，返回 true 表示超频 */
    public boolean tooManyRegisterFrom(String ip) {
        AtomicInteger c = registerIpCache.get(ip, k -> new AtomicInteger(0));
        return c.incrementAndGet() > 10;           // 1 小时内同 IP 最多 10 次注册
    }

    private final Cache<String, AtomicInteger> registerIpCache = Caffeine.newBuilder()
            .expireAfterWrite(1, TimeUnit.HOURS)
            .maximumSize(100_000)
            .build();
}
```

### 3.4 `AiService/PsychologicalSupportService` —— 本模块的核心

#### `startSession(userId, dto)` → `StreamChatSession`

建会话记录 → **把 `initialMessage` 存成第一条用户消息** → 返回 `sessionId="session_"+id`。

**要点**：返回值里的 `expiryTime`（+24 小时）、`messageCount=1`、`status="ACTIVE"` 都是**给前端看的展示信息**，后端不据此做任何判断。

#### `streamPsychologicalChat(sessionId, userMessage)` → `Flux<String>`

**这是全项目最需要理解的一段**，用 `Flux.create` 手动推流：

```
① extractSessionId → 解析失败直接 sink.error
② 判断「是不是 startSession 时已经存过的初始消息」：
     messageCount == 1 且 最后一条是用户消息 且 内容 == 本次 userMessage
     → 是：isInitMessage = true
③ 不是初始消息 → saveUserMessage 入库
④ conversationId = "conversation_" + sessionId
⑤ chatClient("open-ai").prompt().user(userMessage)
      .advisors(spec -> spec.param("chat_memory_conversation_id", conversationId))
      .stream().content()
      .doOnNext(片段 -> 追加到 fullResponse + sink.next(片段))
      .doOnComplete(把完整回复 saveAiMessage + sink.complete())
      .doOnError(sink::error)
```

**要点**
- **② 这个「初始消息去重」判断很脆弱**：它依赖「消息数 == 1」+「内容字符串完全相等」。如果用户在 startSession 之后、第一次 stream 之前用别的路径改了消息表，判断就会失效并产生重复消息。更稳的做法是在会话上记一个「初始消息已存」的标志，或者直接由前端只用 stream（不传 initialMessage）。
- **`conversationId` 的命名是 `"conversation_session_3"`**，而 ChatMemory 是内存的 → 重启后 AI 会"忘记"之前的对话，但对**数据库里的历史消息**没影响（历史消息是另外查的）。
- AI 回复落库发生在 `doOnComplete` —— 也就是说**流中断时不会保存半截回复**（对，也意味着用户看到的内容如果没走完，库里就没有）。

**可优化**
- **O-35**：`fullResponse` 用 `StrBuilder` 拼接。若 AI 单次回复很长，字符串拼接有开销（可以用 `StringBuilder`，Hutool 的 `StrBuilder` 内部也是数组，问题不大，属微优化）。
- **O-36**：**流失败时用户消息已经入库了**，会造成「用户说了话但 AI 没回」的记录。建议失败时把该条消息标记为失败态（需加列），或前端提示「本条未送达」。
- **O-37**：没有对 `userMessage` 做敏感词/长度兜底缓冲（DTO 限了 2000 字，够了）。
- **O-38**：`isInitMessage` 的判定逻辑建议改为「会话表加一列 initial_message_saved」或「由前端统一只调 stream」。

#### `getEmotionAnalysis(sessionId, userId, isAdmin)` → `EmotionAnalysis`

见架构文档 2.3。这里补充**代码级要点**：

- 缓存三条件：`last_emotion_analysis != null`、`last_emotion_updated_at` 在 24h 内、`last_emotion_msg_count == 当前消息条数`。
- `readCache()` 除了 try/catch，还**额外校验 `primaryEmotion() != null`**。为什么必须校验：Jackson 3 默认关闭 `FAIL_ON_UNKNOWN_PROPERTIES`，**`readValue("{}")` 不会抛异常**，会返回字段全 null 的 record → 不校验就会把空壳当有效缓存返回，前端满屏 undefined。
- `normalize()` 做了 5 类兜底：主情绪缺失→「平静」、分数夹在 0-100、风险等级夹在 0-3、**riskLevel 与 isNegative 的矛盾修正**（≥2 强制 true、=0 强制 false）、列表字段 null→空列表、文案缺失给默认。
- `analyzeSessionEmotion()`：拼「用户：…／AI：…」的对话文本，**只取最后 8000 字**（`subString(dialogue.length() - 8000)`，因为越靠后的对话越能反映当前情绪）。

**可优化**
- **O-39（P0 级）**：`.call()` 是**同步阻塞**，实测 1 条消息 ~10 秒、消息多更久。前端 axios 默认超时 10 秒 → **「AI 对话后第一次刷新情绪花园」必然超时**。建议改成异步：命中旧缓存但内容已过期时，**先返回旧结果 + 入队一个 `ai_analysis_task`**，前端稍后再拉一次。（前端已临时把该接口超时放宽到 60 秒止血。）
- **O-40**：缓存的失效条件是「消息条数变了」。但**用户编辑历史消息**（当前没有该功能）或**删除消息**时条数可能不变/变少，判断会失准。可换成「最后一条消息的 id 或 created_at」。
- **O-41**：`normalize` 与 `EmotionDiaryAnalysisService.normalize` 逻辑高度重复（一个管会话、一个管日记）。可抽公共方法。

#### `StructOutPut` —— 出参结构

两个 record：`StreamChatSession`、`EmotionAnalysis`（11 个字段）、`DiaryEmotionAnalysis`（7 个字段）。

**要点**：用 `record` 是「只读数据载体」的现代写法，天然不可变。**`timestamp` 字段由后端填**（`System.currentTimeMillis()`），不是 AI 生成的 —— AI 生成时间戳不可信。

**可优化**
- **O-42**：类名 `StructOutPut`（`OutPut` 大小写）不规范；建议拆成 `ai/model/` 包下的 `EmotionAnalysisResult`、`DiaryAnalysisResult` 等独立文件，避免一个类里塞多个 record。

### 3.6 本章代码答案（O-31 ～ O-46）

#### O-31 · 给 `deleteSession` 加事务（P0）

改哪里：`service/ConsultationSessionService.java`

```java
import org.springframework.transaction.annotation.Transactional;

    /**
     * 删会话 + 删全部消息。
     * 这两步必须一起成功：否则一旦「消息删了、会话没删」，就会留下一个打不开也删不掉的空壳会话。
     * rollbackFor = Exception.class：默认只回滚 RuntimeException，
     * 这里显式声明，连受检异常也回滚。
     */
    @Transactional(rollbackFor = Exception.class)
    public void deleteSession(Long sessionId) {
        if (consultationSessionMapper.selectById(sessionId) == null) {
            throw new BusionessException("会话不存在");
        }
        consultationMessageService.deleteBySessionId(sessionId);   // 先删消息
        consultationSessionMapper.deleteById(sessionId);          // 再删会话
    }
```

> 注意 `@Transactional` 靠代理生效：**同类内部自调用不生效**。这里由 `PsychologicalChatController`
> 调进来，是跨 bean 调用，没问题。（若以后有 `this.deleteSession(...)` 的写法就会失效。）

#### O-32 · `pageSessions` 不再把「全部消息」拉进内存

**问题**：只为了拿「最后一条 + 条数」，却把这批会话的所有消息都查了出来。

改哪里：`mappper/ConsultionMessageMapper.java`（新增两个方法）

```java
    /** 每批会话的：消息条数 + 最后一条消息时间（不拉内容） */
    @Select("<script>" +
            "select session_id as sessionId, count(*) as messageCount, max(created_at) as lastMessageTime " +
            "from consultation_message where session_id in " +
            "<foreach collection='ids' item='id' open='(' separator=',' close=')'>#{id}</foreach> " +
            "group by session_id" +
            "</script>")
    List<Map<String, Object>> countAndLastTime(@Param("ids") List<Long> ids);

    /** 每批会话「最后一条消息」的完整内容（用 max(id) 定位，比按时间更稳） */
    @Select("<script>" +
            "select m.* from consultation_message m " +
            "join (select session_id, max(id) as mid from consultation_message " +
            "      where session_id in " +
            "<foreach collection='ids' item='id' open='(' separator=',' close=')'>#{id}</foreach> " +
            "      group by session_id) t on m.id = t.mid" +
            "</script>")
    List<ConsultationMessage> selectLastBySessionIds(@Param("ids") List<Long> ids);
```

改哪里：`service/ConsultationSessionService.java` 的 `pageSessions`，把 ② 那一段换掉：

```java

        Map<Long, Map<String, Object>> statMap = consultionMessageMapper.countAndLastTime(sessionIds)
                .stream().collect(Collectors.toMap(
                        r -> ((Number) r.get("sessionId")).longValue(),
                        r -> r));

        Map<Long, ConsultationMessage> lastMsgMap = consultionMessageMapper
                .selectLastBySessionIds(sessionIds)
                .stream()
                .collect(Collectors.toMap(ConsultationMessage::getSessionId, m -> m, (a, b) -> a));
```

组装 VO 时改成读这两张 map：

```java

            Map<String, Object> stat = statMap.get(s.getId());
            ConsultationMessage last = lastMsgMap.get(s.getId());
            User u = userMap.get(s.getUserId());
            voList.add(SessionAdminVO.builder()
                    .id(s.getId())
```

```java
    /** 正在异步刷新的会话集合：避免同一个会话被并发重复分析 */
    private final Set<Long> refreshing = ConcurrentHashMap.newKeySet();

    @Resource
    @Qualifier("aiAnalyzeExecutor")
    private Executor aiAnalyzeExecutor;

    public StructOutPut.EmotionAnalysis getEmotionAnalysis(String sessionId, Long userId, boolean isAdmin) {
        Long dbsession = extractSessionId(sessionId);
        if (dbsession == null) throw new BusionessException("会话Id格式错误");
        ConsultationSession session = consultationSessionService.getById(dbsession);
        if (session == null) throw new BusionessException("会话不存在");
        if (!isAdmin && !session.getUserId().equals(userId)) throw new BusionessException("无权访问该会话");

        Integer currentCount = consultationMessageService.getMessageCount(dbsession);

        // ① 命中缓存 → 秒回
        if (session.getLastEmotionAnalysis() != null
                && session.getLastEmotionUpdatedAt() != null
                && session.getLastEmotionUpdatedAt().isAfter(LocalDateTime.now().minusHours(24))
                && Objects.equals(session.getLastEmotionMsgCount(), currentCount)) {
            StructOutPut.EmotionAnalysis cached = readCache(session.getLastEmotionAnalysis());
            if (cached != null) return cached;
        }

        // ② 缓存过期/脏，但「有旧结果」→ 先返回旧的，后台异步刷新（前端过几秒再拉一次就能拿到新值）
        StructOutPut.EmotionAnalysis stale = readCache(session.getLastEmotionAnalysis());
        if (stale != null) {
            triggerRefresh(dbsession, currentCount);
            return stale;
        }

        // ③ 完全没结果（首次）→ 只能同步算，但这是「每会话一次」的开销
        return analyzeAndSave(session, dbsession, currentCount);
    }

    /** 异步刷新：同一会话同一时刻只允许一个在跑 */
    private void triggerRefresh(Long dbSessionId, Integer msgCount) {
        if (!refreshing.add(dbSessionId)) return;                 // 已在跑，直接跳过
        CompletableFuture.runAsync(() -> {
            try {
                ConsultationSession s = consultationSessionService.getById(dbSessionId);
                if (s != null) analyzeAndSave(s, dbSessionId, msgCount);
            } catch (Exception e) {
                log.warn("异步刷新会话情绪失败，sessionId={}", dbSessionId, e);
            } finally {
                refreshing.remove(dbSessionId);
            }
        }, aiAnalyzeExecutor);
    }

    /** 调 AI + 兜底 + 写回缓存（原来是 getEmotionAnalysis 里内联的那几行，抽出来复用） */
    private StructOutPut.EmotionAnalysis analyzeAndSave(ConsultationSession session, Long dbSessionId, Integer msgCount) {
        StructOutPut.EmotionAnalysis analysis = normalize(analyzeSessionEmotion(dbSessionId));
        session.setLastEmotionAnalysis(objectMapper.writeValueAsString(analysis));
        session.setLastEmotionUpdatedAt(LocalDateTime.now());
        session.setLastEmotionMsgCount(msgCount);
        consultationSessionService.updateById(session);
        return analysis;
    }
```

```java
    public AiResultNormalizer(ObjectMapper objectMapper) { this.objectMapper = objectMapper; }

    /** 情绪强度夹到 0-100，null 给 50 */
    public int score(Integer v) { return v == null ? 50 : Math.max(0, Math.min(100, v)); }

    public List<String> list(List<String> v) { return v == null ? List.of() : v; }

            return (key != null && !key.isBlank()) ? parsed : null;
        } catch (Exception e) {

        }
    }
```

### 4.2 `EmotionDiaryService`

#### `saveOrUpdate(userId, dto)` → `EmotionDiary`

### 4.3 `AnalysisTaskService` —— 任务的生命周期管理

| 方法 | 作用 | SQL 关键点 |
|---|---|---|
| `enqueue(diaryId, userId)` | 入队（去重） | 先查有没有 PENDING，有就复用，不新建 |
| `createPending(...)` | 建任务 | 默认 `priority=2`、`retry_count=0`、`max_retry_count=3` |
| `markProcessing(taskId)` | PENDING→PROCESSING | **`where id=? and status='PENDING'`**，返回 1 才算抢到 |
| `markCompleted(taskId)` | 完成 | 用 `updateById`，同时写 `completed_at` |
| `markFailed(taskId, msg)` | 失败 | 走 `retryOrFail`，错误信息截断到 1000 字 |
| `pickPending(limit)` | 捞待处理 | `ORDER BY priority DESC, id ASC LIMIT n` |
| `recycleStuck()` | 回收卡死 | 见下 |
| `markStuckAsFailed()` | 卡死且重试耗尽 → FAILED | 见下 |

**`markProcessing` 为什么必须带 `where status='PENDING'`**：这是**乐观锁/抢占**写法。多个调度线程（或未来多实例部署）同时捞到同一条任务时，只有第一个执行条件更新的会把行从 PENDING 改成 PROCESSING 并返回 1，其余返回 0 直接跳过。**没有这个条件，同一条任务会被重复执行、重复调 AI**。

**`retryOrFail` 的 SQL 有一个隐蔽坑（已修）**

```sql
update ai_analysis_task set retry_count = retry_count + 1,
       status = if(retry_count + 1 < max_retry_count,'PENDING','FAILED'), ...
```

MySQL 的 `SET a=?, b=?` 是**从左到右求值**的：后面的表达式读到的是前面刚改过的**新值**。
原写法把自增放在前面，导致 if 里的 `retry_count` 已经是自增后的值，等价于 `new+1 < max`，`max=3` 时**只重试 2 次就判 FAILED**。
现在的写法（自增在前、条件里再 `+1` 补偿）是等效正确的；**更直观的写法是把自增挪到条件之后**：`set status = if(retry_count + 1 < max_retry_count, ...), retry_count = retry_count + 1`。
> 记住这条通用规则：**同一个 UPDATE 里既改计数又按计数判状态时，一定要确认求值顺序。**

**两个「自愈」SQL**

| 方法 | 条件 | 动作 |
|---|---|---|
| `recycleStuck` | `status='PROCESSING'` 且 `started_at < now-5min` 且 `retry_count < max` | 退回 `PENDING`，`retry_count+1`，写入错误说明 |
| `markStuckAsFailed` | 同上但 `retry_count >= max` | 直接 `FAILED` + `completed_at` |

**它们解决什么问题**：服务在任务执行中途被杀（重启/崩溃），任务永远停在 `PROCESSING`，没人再管它。5 分钟后这两条 SQL 会把它捞出来重试或判死。

### 4.4 `AiService/EmotionDiaryAnalysisService`

#### `analyzeEmotionDiary(diaryId, force)` → `DiaryEmotionAnalysis`

流程：查日记 → **未过期且非强制**则读缓存 → `buildText()` 组装文本 → `chatClient("analysis")` 调 AI → `normalize()` → 写回 `ai_emotion_analysis` + `ai_analysis_updated_at`。

**`buildText()` 的细节**：只取日记自身内容（不去读会话消息），格式带【】标记：

```
【日记日期】2026-09-27
【自评情绪】焦虑
【情绪评分(1-10，越高越好)】3
【睡眠质量(1-5)】2
【压力水平(1-5)】4
【情绪触发因素】…
【日记内容】…
```

超 8000 字取**尾部**（`subString(length - 8000)`）。

**要点**
- `normalize` 与 `readCache` 的逻辑和会话情绪那套几乎一样，是**有意的重复**（两个 record 类型不同）。
- `readCache` 里判断 `hasText(cached.primaryEmotion())` —— 注释说明：旧格式脏数据（Hutool 只会写出 `{"isNegative":false}`）会被判为无效缓存，触发重新分析。

**可优化**
- **O-52**：与 `PsychologicalSupportService` 的 `normalize/readCache` 重复度很高。可抽 `AiResultNormalizer` 工具类，两处共用（注意两个 record 字段不同，需要一点适配）。
- **O-53**：`analyzeEmotionDiary` 里「查日记 → 调 AI → 写回」是一个事务边界模糊的操作（AI 调用不能放进事务，否则长事务占连接）。当前写法（事务外调 AI、之后再写回）是正确的，但**没有任何注释说明**，容易被后人"优化"成 `@Transactional`。建议补注释。

### 4.5 `AiService/AnalysisTaskScheduler` —— 后台消费者

**作用**：`@Scheduled(fixedDelay = 30_000, initialDelay = 10_100)`，每 30 秒干一轮。

**一轮的 3 步**
1. `recycleStuck()` → 回收卡死任务（打 info 日志）
2. `markStuckAsFailed()` → 重试耗尽的判死（打 warn 日志）
3. 捞最多 20 条 PENDING，逐条：`markProcessing` 抢锁 → 查日记 → 分析（`force=true`）→ `markCompleted`；**任何异常都 catch 住**，`markFailed` 后继续下一条（一条失败不连累整批）。

**要点**
- `initialDelay = 10_100`（10.1 秒）是**故意错开**的：给 Spring 容器完成 bean 初始化的时间，避免启动瞬间就访问数据库。
- `fixedDelay` 而不是 `fixedRate`：**上一轮跑完才开始计 30 秒**，避免任务堆积时重叠执行。
- `force=true` 表示「忽略缓存直接重算」——因为任务本身就是被创建来分析新内容的。
- 日记被删（`diary == null`）也会 `markCompleted`，避免任务永远 PENDING。

**可优化**
- **O-54**：**单线程串行执行**（`@Scheduled` 默认单线程池）。20 条任务 × 每条 10 秒 = 一轮要 200 秒，远大于 30 秒周期 → 会一直积压。建议改用 `@Async` + 线程池，或 `fixedDelay` 调大并配合批量并发。
- **O-55**：**多实例部署时重复执行的风险已被 `markProcessing` 的条件更新挡住**（见 4.3），所以当前是安全的。真正缺的是**可观测性**：任务表没有「执行者」标识，排查问题时分不清是哪个实例在处理。可加一列 `worker_id`（实例 ID / IP）。
- **O-56**：没有任何**任务监控/告警**信号（比如「连续 N 轮失败率 > X%」）。`countGroupByStatus()` 这个 mapper 方法已经写好了但**没有调用点**，可以接一个管理端接口暴露任务健康度。

### 4.7 本章代码答案（O-47 ～ O-58）

#### O-47 · `saveOrUpdate` + `enqueue` 的一致性（P0）

**先想清楚要哪一种语义，再决定是否加 `@Transactional`：**

| 目标 | 做法 |
|---|---|
| **A. 日记存不上就整体失败，入了队就一定有日记** | 加 `@Transactional`，并把 `try/catch` 去掉（异常必须往外抛，否则事务照常提交） |
| **B. 日记必须存上；AI 分析入队失败只记日志**（当前设计意图） | 保持 `try/catch`，**不要**加 `@Transactional` |

**方案 A 的代码**：

```java
    /**
     * 写日记 + 入队 AI 分析，两者要么都成功、要么都回滚。
     * 注意：加了 @Transactional 之后，就不能再在方法内部 catch 掉 enqueue 的异常 ——
     * 自己吞掉异常等于「事务照常提交」，等于白加注解。
     */
    @Transactional(rollbackFor = Exception.class)
    public EmotionDiary saveOrUpdate(Long userId, EmotionDiarySaveDTO dto) {
        // ...（查/插/更新的逻辑不变）
        analysisTaskService.enqueue(emotionDiary.getId(), userId);   // 不再 try/catch
        return emotionDiary;
    }
```

**方案 B 的代码（推荐，保住「日记一定能存」）**：结构不动，只在注释里把语义写清楚，
同时把入队的异常降级为 warn（现有代码已如此），无需改代码 —— 但要在文档/注释里明确：

```java
    /**
     * ⚠️ 这里刻意不加 @Transactional：写日记是用户的核心诉求，AI 分析是增强功能。
     * 入队失败只记 warn，绝不能让「AI 挂了」导致日记存不上。
     * 若要改成强一致（日记与任务同生共死），见文档 O-47 方案 A。
     */
```

#### O-48 · 更新日记会重复入队 —— 明确行为并做去重

**问题**：用户每改一次日记就多一条任务；若上一次已 `COMPLETED`，`enqueue` 的「复用 PENDING」不生效 → 会重新分析。

**策略**：改为「同一篇日记只保留一条未完成任务；已完成的不再重复建」，
并在内容未变化时直接跳过入队。

改哪里：`service/AnalysisTaskService.java`

```java
    /**
     * 入队（去重增强版）：
     * ① 已有 PENDING/PROCESSING → 复用，不新建；
     * ② 最近一条已 COMPLETED 且没超过冷却时间 → 也不新建（避免用户反复保存引发反复分析）。
     */
    public AiAnalysisTask enqueue(Long diaryId, Long userId) {
        AiAnalysisTask running = aiAnalysisTaskMapper.selectOne(
                new LambdaQueryWrapper<AiAnalysisTask>()
                        .eq(AiAnalysisTask::getDiaryId, diaryId)
                        .in(AiAnalysisTask::getStatus,
                            AiReturnResult.PENDING.getCode(), AiReturnResult.PROCESSING.getCode())
                        .orderByDesc(AiAnalysisTask::getId)
                        .last("LIMIT 1"));
        if (running != null) return running;

        AiAnalysisTask lastDone = aiAnalysisTaskMapper.selectOne(
                new LambdaQueryWrapper<AiAnalysisTask>()
                        .eq(AiAnalysisTask::getDiaryId, diaryId)
                        .eq(AiAnalysisTask::getStatus, AiReturnResult.COMPLETED.getCode())
                        .orderByDesc(AiAnalysisTask::getId)
                        .last("LIMIT 1"));
        if (lastDone != null && lastDone.getCompletedAt() != null
                && lastDone.getCompletedAt().isAfter(LocalDateTime.now().minusMinutes(1))) {
            return lastDone;                     // 1 分钟内刚分析过，直接复用
        }
        return createPending(diaryId, userId, AiReturnResult.TYPE_AUTO.getCode());
    }
```

**更精确的做法**：在 `EmotionDiaryService.saveOrUpdate` 里比对「内容有没有真的变」：

```java
        boolean contentChanged = emotionDiary == null                                  // 新建必入队
                || !Objects.equals(oldContent, dto.getDiaryContent())
                || !Objects.equals(oldTriggers, dto.getEmotionTriggers())
                || !Objects.equals(oldMoodScore, dto.getMoodScore());
        if (contentChanged) {
            try { analysisTaskService.enqueue(emotionDiary.getId(), userId); }
            catch (Exception e) { log.warn("AI分析任务入队失败，diaryId={}", emotionDiary.getId(), e); }

```

#### O-50 · `aiAnalysisStatus` 读真实任务状态

#### O-54 · 调度器不再单线程串行

**问题**：20 条 × 10 秒 = 200 秒/轮，远超 30 秒周期 → 任务持续积压。

改哪里：`AiService/AnalysisTaskScheduler.java`

```java
@Slf4j
@Component
public class AnalysisTaskScheduler {
    private static final int BATCH_SIZE = 20;
    /** 每轮最多并发处理多少条（避免把 AI 接口打爆） */
    private static final int CONCURRENCY = 4;

    @Resource private AnalysisTaskService analysisTaskService;
    @Resource private EmotionDiaryMapper emotionDiaryMapper;
    @Resource private EmotionDiaryAnalysisService emotionDiaryAnalysisService;
    @Resource @Qualifier("aiAnalyzeExecutor") private Executor executor;   // 见 O-39 的 AsyncConfig

    @Scheduled(fixedDelay = 30_000, initialDelay = 10_100)
    public void scan() {
        int recycled = analysisTaskService.recycleStuck();
        if (recycled > 0) log.info("回收卡死的 PROCESSING 任务 {} 条", recycled);
        int dead = analysisTaskService.markStuckAsFailed();
        if (dead > 0) log.warn("僵死且重试耗尽的 PROCESSING 任务 {} 条已标记 FAILED", dead);

        List<AiAnalysisTask> tasks = analysisTaskService.pickPending(BATCH_SIZE);
        if (tasks.isEmpty()) return;

        // 用固定并发度跑：每 CONCURRENCY 条一组，组内并行、组间等待
        Semaphore semaphore = new Semaphore(CONCURRENCY);
        List<CompletableFuture<Void>> futures = tasks.stream()
                .map(t -> CompletableFuture.runAsync(() -> {
                    try {
                        semaphore.acquire();
                        handleOne(t);
                    } catch (InterruptedException e) {
                        Thread.currentThread().interrupt();
                    } finally {
                        semaphore.release();
                    }
                }, executor))
                .toList();
        CompletableFuture.allOf(futures.toArray(new CompletableFuture[0])).join();
        log.info("本轮 AI 分析完成，共处理 {} 条", tasks.size());
    }

    /** 单条任务：抢锁 → 分析 → 标记结果；异常只影响这一条 */
    private void handleOne(AiAnalysisTask task) {
        if (!analysisTaskService.markProcessing(task.getId())) return;   // 没抢到就跳过
        try {
            EmotionDiary diary = emotionDiaryMapper.selectById(task.getDiaryId());
            if (diary == null) { analysisTaskService.markCompleted(task.getId()); return; }
            emotionDiaryAnalysisService.analyzeEmotionDiary(diary.getId(), true);
            analysisTaskService.markCompleted(task.getId());
        } catch (Exception e) {
            log.warn("AI 分析任务失败，taskId={}, diaryId={}", task.getId(), task.getDiaryId(), e);
            analysisTaskService.markFailed(task.getId(), e.getMessage());
        }
    }
}
```

需要的 import：`java.util.List`、`java.util.concurrent.*`、`org.springframework.beans.factory.annotation.Qualifier`。

> 因为 `@Scheduled` 是 `fixedDelay`（上一轮跑完才计时），并发后一轮 20 条 ≈ 50 秒，
> 仍大于 30 秒周期，但**不再无限积压**；若任务量继续涨，把 `BATCH_SIZE` 提到 50 或再加实例即可。
> 多实例安全：靠 `markProcessing` 的 `where status='PENDING'` 条件更新兜底（见正文 4.3）。

### 5.1 两张表

| 表 | 关键点 |
|---|---|
| `knowledge_article` | **主键是 String（`IdType.INPUT`，业务侧用 `UUID.randomUUID()` 生成）**；`category_id`、`author_id` 都是外键且 **RESTRICT** → 有文章的分类/作者删不掉 |

### 5.2 `KnowledgeArticleService`

| 方法 | 要点 |
|---|---|
| `page(query, skipPublishFilter)` | 用户端（`skipPublishFilter=false`）**强制只看 `status=1`**；管理端可传 status 筛选。关键词同时匹配标题或摘要（用 `and(w -> ...or()...)` 保证优先级正确）。排序 `published_at DESC, created_at DESC` |
| `create(dto, userId)` | 校验分类存在 → 生成 UUID 主键 → `status=1` 时同时写 `published_at` |
| `update(id, dto)` | 校验文章/分类存在 → **`BeanUtil.copyProperties(dto, entity, ignoreNullValue())`** → 只覆盖非 null 字段 |
| `updateStatus(id, status)` | 校验 status 只能是 0/1 → 用 `LambdaUpdateWrapper` 更新；**发布时才写 `published_at`** |
| `detail(id, skipPublishFilter)` | 未发布且非管理员 → 抛「文章未发布」；**普通用户查看时 `read_count + 1`**（SQL 原子自增 + 内存值同步 +1） |
| `delete(id)` | 存在性校验后删除 |

**要点**
- `page()` 里那个关键词条件必须写成 `wrapper.and(w -> w.like(title, kw).or().like(summary, kw))`。如果直接 `.like(title,kw).or().like(summary,kw)`，`or` 会和前面的 `status=1` 平级，导致「绕过发布状态过滤」——**这是 MP 条件构造最经典的坑**。
- `ignoreNullValue()` 是「部分更新」的实现方式：前端只传要改的字段，没传的保持原值。

**可优化**
- **O-59**：`BeanUtil.copyProperties` 是**反射 + 运行时报错**，字段改名时不会编译报错。字段不多，手写 set 更安全。
- **O-60**：`read_count` 每次查看都写库 → 热点文章频繁写。可改为「异步累加」或直接上 Redis 计数器。
- **O-61**：`update` 后没有清缓存/刷新 `updated_at` 之外的逻辑（目前无缓存，暂无问题）。
- **O-62**：`delete` 只删文章，**没有清理关联的 `sys_file_info`（封面图）** → 会留下孤儿文件记录。

### 5.3 `KnowledgeCategoryService`

```java
    public List<CategoryTreeVO> getCategoryTree() {

                new LambdaQueryWrapper<KnowledgeCategory>()
                        .eq(KnowledgeCategory::getStatus, 1)
                        .orderByAsc(KnowledgeCategory::getSortOrder));

        Map<Long, CategoryTreeVO> index = new LinkedHashMap<>();
        for (KnowledgeCategory c : all) index.put(c.getId(), toVo(c));

        List<CategoryTreeVO> roots = new ArrayList<>();
        for (KnowledgeCategory c : all) {

            Long parentId = (c.getParentId() == null || c.getParentId() == 0L) ? null : c.getParentId();
            CategoryTreeVO parent = parentId == null ? null : index.get(parentId);
            if (parent == null) {

            } else {
                parent.getChildren().add(node);
            }
        }
        return roots;
```

## 6. 模块五：文件上传

**涉及文件**：`entity/SysFileInfo`、`service/FileService`、`response/FileUploadVO`、`controller/FileController`、`config/WebMvcConfig`

### 6.1 `FileService.upload(...)`

**校验链（顺序即代码顺序）**：非空 → 大小 ≤ 10MB → 扩展名白名单（图片 + pdf/txt/doc/docx/xls/xlsx/ppt/pptx）。

**存储**：`{uploadDir}/yyyy-MM/{UUID}.{ext}`，入库 `file_path = "/files/yyyy-MM/uuid.ext"`。

**`business_type` / `business_id` 是多态字段**：同一张表存头像、文章封面、附件，靠这两个字段区分归属。

**要点**
- 大小限制**双保险**（yml 里 10MB + 代码里 10MB）。
- 扩展名白名单是关键安全措施 —— 没有它，上传 `.jsp`/`.exe` 可能被利用。
- `is_temp=1` 时会写 `expire_time = now + 24h`，**但没有任何清理任务在跑**。

**可优化**
- **O-69（P0 级）**：**先写盘、后入库**。入库失败（如数据库抖动）→ 磁盘留下没人管的文件。反过来先入库后写盘则会有「记录指向不存在的文件」。建议：写盘成功但入库失败时，在 catch 里删掉刚落盘的文件。
- **O-70**：`is_temp` 的 `expire_time` 字段形同虚设 —— **没有定时清理任务**。库里实测存在孤儿文件记录（`id=1`、`business_type='avatar'`、指向不存在的文件）。建议加一个复用 `@Scheduled` 的清理任务。
- **O-71**：`business_type` 取值大小写不统一（`ARTICLE` / `article_cover` / `USER_AVATAR`）。建议定义枚举常量统一。
- **O-72**：**只校验扩展名，不校验文件头（magic number）** → 改后缀就能绕过。建议加文件魔数校验。
- **O-73**：`resolveFileType` 的 switch **缺少 `ppt/pptx`** 分支（白名单允许 ppt，但类型会落到 `OTHER`）。补上或者从白名单移除。

### 6.2 `FileController` / `WebMvcConfig`

`POST /api/file/upload`，参数：`file`（必须）、`businessType`、`businessId`、`businessField`、`isTemp`（均可选）。

**访问路径**：`/files/**` 由 `WebMvcConfig` 映射到磁盘目录，且**在 SecurityConfig 白名单里 → 无需登录即可访问**。

**可优化**
- **O-74**：上传目录完全公开。若未来存隐私图片（如用户上传的私密内容），需改为鉴权访问或签名 URL。
- **O-75**：文件名包含中文/特殊字符时，`file_path` 用的是 UUID 所以安全；但 `original_name` 原样入库 → 展示时需前端转义。

```java
    public FileUploadVO upload(MultipartFile file, String businessType, String businessId,
                               String businessField, Boolean isTemp, Long userId) {
        if (file == null || file.isEmpty()) throw new BusionessException("请选择要上传的文件");
        if (file.getSize() > MAX_SIZE)      throw new BusionessException("文件大小不能超过 10MB");

        String originalName = file.getOriginalFilename();
        String ext = getExt(originalName);
        if (!ALLOWED_EXT.contains(ext)) throw new BusionessException("不支持文件类型：" + ext);
        validateMagic(file, ext);                                   // 见 O-72

        Path target = Paths.get(uploadDir).resolve(relative);

        try {
            Files.createDirectories(target.getParent());
            try (var in = file.getInputStream()) {
                Files.copy(in, target, StandardCopyOption.REPLACE_EXISTING);      // ① 先落盘
            }
        } catch (IOException e) {
            throw new BusionessException("文件保存失败：" + e.getMessage());
        }

        try {
            SysFileInfo info = SysFileInfo.builder()
                    .originalName(safeOriginalName(originalName))                 // 见 O-75

                    .fileSize(file.getSize())

                    .businessField(businessField)
                    .uploadUserId(userId)
                    .businessId(businessId)
                    .isTemp(Boolean.TRUE.equals(isTemp) ? 1 : 0)
                    .status(1)
                    .createTime(LocalDateTime.now())
                    .expireTime(Boolean.TRUE.equals(isTemp) ? LocalDateTime.now().plusHours(24) : null)
                    .build();
            sysFileInfoMapper.insert(info);                                   // ② 再入库

                    .originalName(info.getOriginalName())
                    .filePath(info.getFilePath())
                    .businessType(info.getBusinessType())
                    .fileSize(info.getFileSize())
                    .fileType(info.getFileType())
                    .build();
        } catch (Exception dbEx) {
            // ③ 入库失败 → 把刚落盘的文件删掉，避免留下孤儿文件

                log.warn("回滚磁盘文件失败，可能残留孤儿文件：{}", target, ioEx);

            log.error("文件入库失败，已回滚磁盘文件：{}", relative, dbEx);
            throw new BusionessException("文件保存失败，请稍后重试");
```

#### O-70 · 加一个定时清理任务（临时文件 + 孤儿记录）

新增 `AiService/FileCleanupTask.java`（放 `AiService` 包外也行，比如 `config` 或新建 `task` 包）：

```java
package com.lzc.mindaispringboot.AiService;

import com.baomidou.mybatisplus.core.conditions.query.LambdaQueryWrapper;
import com.lzc.mindaispringboot.entity.SysFileInfo;
import com.lzc.mindaispringboot.mappper.SysFileInfoMapper;
import jakarta.annotation.Resource;
import lombok.extern.slf4j.Slf4j;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.scheduling.annotation.Scheduled;
import org.springframework.stereotype.Component;

import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;
import java.nio.file.Paths;
import java.time.LocalDateTime;
import java.util.List;

@Slf4j
@Component
public class FileCleanupTask {

    @Value("${file.upload-dir}")
    private String uploadDir;

    @Resource
    private SysFileInfoMapper sysFileInfoMapper;

    /** 每天凌晨 3 点清理：① 已过期的临时文件 ② 记录存在但磁盘文件已丢失的孤儿记录 */
    @Scheduled(cron = "0 0 3 * * ?")
    public void clean() {
        int deleted = cleanExpiredTemp();
        int marked = markMissingFiles();
        if (deleted > 0 || marked > 0) {
            log.info("文件清理完成：删除临时文件 {} 个，标记失效记录 {} 条", deleted, marked);
        }
    }

    /** ① 过期临时文件：is_temp=1 且 expire_time < now → 删磁盘 + 软删记录 */
    private int cleanExpiredTemp() {
        List<SysFileInfo> list = sysFileInfoMapper.selectList(new LambdaQueryWrapper<SysFileInfo>()
                .eq(SysFileInfo::getIsTemp, 1)
                .eq(SysFileInfo::getStatus, 1)
                .lt(SysFileInfo::getExpireTime, LocalDateTime.now())
                .last("LIMIT 500"));
        int n = 0;
        for (SysFileInfo info : list) {
            deleteDiskFile(info.getFilePath());
            info.setStatus(0);
            sysFileInfoMapper.updateById(info);
            n++;
        }
        return n;
    }

    /** ② 数据库有记录、磁盘没文件 → 标记 status=0，避免前端一直 404 */
    private int markMissingFiles() {
        List<SysFileInfo> list = sysFileInfoMapper.selectList(new LambdaQueryWrapper<SysFileInfo>()
                .eq(SysFileInfo::getStatus, 1)
                .orderByDesc(SysFileInfo::getId)
                .last("LIMIT 500"));
        int n = 0;
        for (SysFileInfo info : list) {
            Path p = toPath(info.getFilePath());
            if (p != null && !Files.exists(p)) {
                info.setStatus(0);
                sysFileInfoMapper.updateById(info);
                n++;
            }
        }
        return n;
    }

    private void deleteDiskFile(String filePath) {
        Path p = toPath(filePath);
        if (p == null) return;
        try {
            Files.deleteIfExists(p);
        } catch (IOException e) {
            log.warn("删除磁盘文件失败：{}", p, e);
        }
    }

    /** "/files/2026-09/xxx.png" → {uploadDir}/2026-09/xxx.png */
    private Path toPath(String filePath) {
        if (filePath == null || filePath.isBlank()) return null;
        return Paths.get(uploadDir).resolve(filePath.replaceFirst("^/files/", ""));
    }
}
```

#### O-72 · 加文件头（魔数）校验

改哪里：`service/FileService.java` 新增

```java
    /**
     * 扩展名白名单只能拦「老实人」—— 把 shell.jsp 改名成 a.png 就能绕过。
     * 这里再核对文件头（magic number）：扩展名和真实类型不匹配就拒绝。
     * 覆盖白名单里最常见的几类；zip 系容器可识别 docx/xlsx/pptx。
     */
    private void validateMagic(MultipartFile file, String ext) {
        byte[] head = new byte[8];
        try (var in = file.getInputStream()) {
            int read = in.read(head);
            if (read < 4) throw new BusionessException("文件内容不合法");
        } catch (IOException e) {
            throw new BusionessException("文件读取失败：" + e.getMessage());
        }
        boolean ok = switch (ext) {
            case "jpg", "jpeg" -> startsWith(head, 0xFF, 0xD8, 0xFF);
            case "png"         -> startsWith(head, 0x89, 0x50, 0x4E, 0x47);
            case "gif"         -> startsWith(head, 0x47, 0x49, 0x46, 0x38);
            case "bmp"         -> startsWith(head, 0x42, 0x4D);
            case "webp"        -> startsWith(head, 0x52, 0x49, 0x46, 0x46);      // RIFF
            case "pdf"         -> startsWith(head, 0x25, 0x50, 0x44, 0x46);      // %PDF
            // OOXML（docx/xlsx/pptx）本质是 zip：50 4B 03 04
            case "docx", "xlsx", "pptx" -> startsWith(head, 0x50, 0x4B, 0x03, 0x04);
            // 老二进制格式：D0 CF 11 E0
            case "doc", "xls", "ppt"    -> startsWith(head, 0xD0, 0xCF, 0x11, 0xE0);
            case "txt"         -> true;                                          // 纯文本无固定头，放行
            default            -> false;
        };
        if (!ok) throw new BusionessException("文件内容与后缀不符，已拒绝上传");
    }

    private boolean startsWith(byte[] head, int... magic) {
        if (head.length < magic.length) return false;
        for (int i = 0; i < magic.length; i++) {
            if ((head[i] & 0xFF) != magic[i]) return false;
        }
        return true;
    }
```

> `new Tika().detect(file.getInputStream())` 拿真实 MIME，再和扩展名比对。

#### O-75 · `original_name` 入库前清洗

```java
    /**
     * 原始文件名要「展示」也要「落库」，所以两头都要防：
     * ① StringUtils.cleanPath 去掉 ../ 之类的路径穿越；
     * ② 干掉控制字符与 HTML 敏感符号，避免前端直接 innerHTML 时被注入。
     * 注意：磁盘上用的是 UUID，所以文件名脏不会影响存储安全。
     */
    private String safeOriginalName(String name) {
        if (name == null || name.isBlank()) return "unnamed";
        String cleaned = org.springframework.util.StringUtils.cleanPath(name)
                .replaceAll("[\\p{Cntrl}]", "")
                .replaceAll("[<>\"'&]", "_");
        if (cleaned.contains("../")) cleaned = cleaned.replace("../", "_");
        return cleaned.length() > 255 ? cleaned.substring(cleaned.length() - 255) : cleaned;
    }
```

- **先造出 7 个日期骨架**（`for (i = 6; i >= 0; i--)`），再往骨架里填数据。这样**没有数据的日期也会出现在数组里**，ECharts 折线不会断。

**可优化**
- **O-76**：`avgDurationMinutes` **恒为 0**（没有任何数据来源）。建议用「会话最后一条消息时间 − `started_at`」算出来，或从 VO 里删掉这个字段。
- **O-77**：一次请求共 **7 次数据库往返**。管理端页面刷新频繁时可加短 TTL 缓存（如 60 秒）。
- **O-78**：所有统计都是**实时全表聚合**，数据量大后（百万级）会慢。可考虑定时预聚合到统计表。

#### O-76 · 让 `avgDurationMinutes` 真正有值

**口径**：单次会话时长 = 「该会话最后一条消息时间 − `started_at`」，取所有会话的平均值。

**① Mapper 加方法**（`mappper/ConsultationSessionMapper.java`）

```java
    /**
     * 平均咨询时长（分钟）：
     * 用「最后一条消息时间 - 会话开始时间」当单次时长，只统计有消息的会话。
     * 单位换算成分钟并四舍五入；没有任何可统计会话时返回 null。
     */
    @Select("select round(avg(duration_min)) from ( " +
            "  select timestampdiff(minute, s.started_at, m.last_at) as duration_min " +
            "  from consultation_session s " +
            "  join (select session_id, max(created_at) as last_at " +
            "        from consultation_message group by session_id) m " +
            "    on m.session_id = s.id " +
            "  where m.last_at > s.started_at " +
            ") t")
    Long selectAvgDurationMinutes();
```

## 10. 最后：三个「看代码时最容易困惑」的点

1. **为什么同一个接口的返回有时是 `Page`、有时是裸数组？**
   因为历史改动。`/knowledge/article/page`、`/sessions` 返回 `Page`（有 `records/total`）；`/emotion-diary/admin/page` 返回**裸数组**。前端统一按 `records` 解构就会拿不到数据。**判断依据永远是看 Controller 的返回类型，不要看路径名。**

2. **为什么错误有时是 HTTP 401、有时是 200 却带 error code？**
   - 过滤器/权限层（`JwtAuthticationFilter`、`AccessDeniedException`）→ 用 **HTTP 状态码**（401/403）。
   - 业务层（`BusionessException`）→ **HTTP 200**，靠 body 里的 `code` 表达。
   所以前端必须两处都处理：axios 的 `error` 分支（看 status）+ 成功分支里的 `code != 200` 判断。项目的前端确实两处都写了。

3. **`Result.code` 为什么是字符串 `"200"`？**
   因为 `ResultCode` 枚举的 code 定义为 `String`，其中还混着 `"200"`（纯数字）和 `"A0230"`（带字母）两类值。用字符串能统一放，代价是任何比较都要注意类型。**写脚本验证接口时，一定用 `str(code) == "200"`，用数字比较会把有数据的响应误判成空。**
